<objective>
Track 1 (Star Pulse) is failing the daily scrape. At ~4,351 repos it fires that many
back-to-back REST `GET /repos/{owner}/{name}` calls with no inter-request delay; most
return 200 (ETags invalidate daily as stars tick up), tripping GitHub's SECONDARY rate
limit (900 pts/min + abuse heuristic). The backoff only reads `x-ratelimit-reset`
(primary), so on a secondary 403/429 it either over-waits up to ~1hr (blows the 330-min
ceiling) or blind-waits 60s and immediately re-trips. The run fails the 10% MAX_FAIL_RATIO
gate and the unreplayable daily-history snapshot is dropped.

Two-part fix per RESEARCH.md (stopgap FIRST, then durable migration):
- **Part A — Stopgap:** honor `retry-after` before falling back to `x-ratelimit-reset`/blind-60s;
  add a small inter-request delay; bump MAX_FAIL_RATIO 0.10 → 0.15. Protects tonight's snapshot.
- **Part B — GraphQL batch migration:** replace the per-repo REST loop with a batched GraphQL
  `repository(...)` query (50 repos/query via aliases, ~88 queries for 4,351 repos, ~1 pt each).
  Collapses the abuse pattern structurally and is ~50x faster.

Purpose: stop the daily pipeline from failing and protect the moat-feeding history snapshot.
Output: retry-after-aware backoff, a GraphQL batch client + pure mapping function, a
GraphQL-batched pulse loop, and unit tests. Implement + commit on `fix/track1-rate-limit`.
NO deploy step (production validation is a branch-CI dispatch, documented in <verification>).
</objective>

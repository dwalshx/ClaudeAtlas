# Phase quick-260603-e96 Plan 01: Fix Failing Daily Scrape (Track 1 Star Pulse) Summary

Track 1's per-repo REST refresh tripped GitHub's secondary (abuse) rate limit at ~4,351 back-to-back GETs; replaced with batched GraphQL (50-repo aliased queries) plus a retry-after-aware backoff stopgap, ending the daily-pipeline failures and protecting the unreplayable star-history snapshot.

## What Shipped

### Task 1 — Stopgap (commit c0902b7)
- `scripts/lib/github-fetch.js`: in BOTH `fetchWithETag` and `rateLimitedFetch`, the 403/429 branch now reads `retry-after` (the SECONDARY/abuse-limit signal) and honors it — capped at 120s + 1s jitter — BEFORE falling back to `x-ratelimit-reset` (PRIMARY) and then blind-60s. The prior code only read `x-ratelimit-reset`, so a secondary 403 caused an up-to-~1hr over-wait (blowing the 330-min ceiling) or a blind-60s immediate re-trip.
- `scripts/scrape-pulse.js`: `MAX_FAIL_RATIO` 0.10 → 0.15 (a partial secondary-limit blip should not drop the snapshot); added a ~100ms inter-request delay (`PULSE_DELAY_MS`) to the serial loop. (The delay was then superseded by the GraphQL inter-batch delay in Task 2.)

### Task 2 — GraphQL batch migration (commit e0ca2fa)
- New `scripts/lib/github-graphql.js` exporting:
  - `buildPulseQuery(repoFullNames)` — pure; builds an aliased `r0..rN: repository(owner,name){...}` query + `aliasMap`. owner/name split on first slash; defensive quote escaping.

## Deviation: GraphQL→REST fallback (2026-06-03)

**Production failure.** The Task 2 GraphQL migration (commit e0ca2fa) FAILED at
production scale. GitHub's GraphQL API (`POST https://api.github.com/graphql`)
returned HTTP 403 on nearly every batch — the `SCRAPE_PAT` is a fine-grained PAT,
and GitHub's GraphQL endpoint rejects fine-grained PATs that work fine for REST.
With every batch 403'ing, `fetchRepoBatchGraphql` exhausted its retries and marked
whole batches as casualties, the failure ratio blew past `MAX_FAIL_RATIO`, and
Track 1 aborted at the top of the daily scrape — the exact failure this task was
meant to fix, now with a different root cause.

**Decision (locked): fall back to REST, keep the stopgap.** The pulse loop in
`scripts/scrape-pulse.js` was rewired back to the per-repo REST path it used
before e0ca2fa (`fetchWithETag` per repo, ETag-cached, applying the 11
`TRACK1_FRESHNESS_FIELDS`). The Task 1 stopgap is intact and is what now makes
the REST path survivable at ~4,351 repos:
- `MAX_FAIL_RATIO = 0.15` (kept)
- `PULSE_DELAY_MS = 100` ~100ms inter-request spacing (kept)
- `retry-after`-first 403/429 backoff in `scripts/lib/github-fetch.js` (kept,
  unchanged) — this is the actual mitigation for the secondary (abuse) limit that
  the original ~4,351 back-to-back GETs tripped.

The history-snapshot writer, short-key (s/f/i/p) emission, apply-in-place loop,
and `TRACK1_FRESHNESS_FIELDS` handling are unchanged. ETag-cache load/persist
(`getETagCache`/`saveETagCache`) is restored since the REST path uses
`data/etag-cache.json` again.

**`scripts/lib/github-graphql.js` is PARKED, not deleted.** A top-of-file comment
marks it parked. The 50-repo aliased-batch design remains a valid future
optimization — once a **classic PAT** (which GitHub's GraphQL API accepts) is
provisioned, re-wiring Track 1 to GraphQL would collapse ~4,351 REST GETs into
~88 batched queries and structurally remove the secondary-limit risk. Until then
the module is dead code with passing pure-function unit tests
(`buildPulseQuery`, `mapGraphqlRepoToFields` — both token-free and network-free).

**Docstring** in `scrape-pulse.js` reverted to describe the REST per-repo pulse +
stopgap (retry-after backoff, ~100ms spacing, fail-ratio 0.15), and a NOTE points
to the parked GraphQL module. Inputs again list `data/etag-cache.json`.

## Follow-up (2026-06-07): skill-vectors cross-run persistence (embed drift fix)

After Track 1 + Track 2 + filter were healthy, the daily scrape failed at
"Embed skills (OpenAI)". Root cause: `data/skill-vectors.ndjson` was a
committed stale 1,078-vector Phase-1 seed, and the workflow had **no
cross-run persistence** for it (no GHA cache, no release asset). Every run
started the incremental embed from the 1,078 seed against the ~49,912
current skills → the delta-check saw only a ~2% cache hit → the Phase-3.2
B-2 drift guard in `embed-skills.js` correctly aborted (refusing to
brute-force re-embed ~50k records at ~$0.40/run, over the cost ceiling).

Fix (the embed couldn't be incremental because the vectors didn't survive
between runs — so make them survive):

- **Added a GHA cache for `data/skill-vectors.ndjson`** in
  `daily-scrape.yml`, mirroring the skills-raw pattern exactly:
  "Restore skill-vectors cache" (`actions/cache/restore@v4`,
  `key: skill-vectors-${{ github.run_number }}`, `restore-keys:
  skill-vectors-`) before the embed step, and "Save skill-vectors cache"
  (`actions/cache/save@v4`, `if: always() && github.event_name != 'push'
  && hashFiles(...) != ''`) after it. Both gated on
  `github.event_name != 'push'`; no PLUGINS_ENABLED gate (skills path).
- **Added a one-time bootstrap mechanism** via a `workflow_dispatch`
  `force_reembed` boolean input, wired to `EMBED_FORCE_REEMBED:
  ${{ github.event.inputs.force_reembed == 'true' && '1' || '0' }}` on the
  embed step's env. Dispatch boolean inputs arrive as the string
  'true'/'false', hence the string compare.
- **Lowered the drift-guard threshold** in `scripts/embed-skills.js` from
  `0.99` to `0.90` for steady-state + weekly-full-sweep headroom (a few
  thousand re-scraped bodies at 49k stays >0.90; a catastrophic hashing
  drift still drops to near 0% and trips). Drift error message is
  dynamic (interpolates the actual hit rate) so no literal-threshold text
  needed updating.
- **Bootstrap procedure:** dispatch `daily-scrape.yml` once with
  `force_reembed=true` to rebuild `skill-vectors.ndjson` from scratch and
  seed the GHA cache; subsequent scheduled runs stay incremental and warm.
- The committed `data/skill-vectors.ndjson` seed is left untouched as the
  cold-start fallback.
- Verification (token-free, network-free): YAML parses (js-yaml);
  `node --check scripts/embed-skills.js` clean; `node --test
  scripts/__tests__/embed-skills.test.js` 4/4 pass (drift test mutates all
  records → 0% hit, still <0.90); `npm run check:patterns` clean; grep
  confirmed the two cache steps, the `force_reembed` input, the
  `EMBED_FORCE_REEMBED` env, and the `0.90` threshold.

## Security fix (2026-06-08): repo-level denylist for scanner/fixture repos

The catalog had indexed eval/test fixtures from two skill-SCANNER repos as if
they were real, installable skills — 9 fixture records total, including a
malware sample with curl|bash data-exfiltration (`claude-world/super-helper`)
and a working jailbreak/prompt-injection (`cisco-ai-defense/jailbreak-override`).
These repos' ENTIRE indexed contents are test corpora (deliberate malicious +
benign samples used to TEST scanners), not real skills, so they must never
appear in the curated index.

Durable fix: added a repo-level `FIXTURE_REPO_DENYLIST` in
`scripts/lib/filter-rules/common.rules.js` (with `isFixtureRepo()`), wired as
the first common gate in `scripts/lib/filter-rules/index.js` `isSlop()`. Any
record whose `repo_full_name` is on the list is dropped early on EVERY filter
pass, so a re-scrape can never re-introduce them. Seeded with
`claude-world/claude-skill-antivirus` and `cisco-ai-defense/skill-scanner`;
extend as more scanner/fixture repos are found.

Scope: exact `repo_full_name` match ONLY — NOT path-based (no `examples/` /
`evals/` / `tests/` exclusion), since ~95 legitimate example skills live under
those paths in guide/tutorial repos and must NOT be removed. No scoring /
tiering / percentile changes; this is an additive exclusion, not a filter
recalibration.

Regression tests added to `scripts/filter.test.js`: a denylisted record is
dropped; a non-denylisted repo with an `examples/` path is kept (over-removal
guard). Verification (token-free, network-free): `node --check` on changed
files clean; `node --test scripts/filter.test.js` 14/14 pass (incl. 2 new);
filter-rules `__tests__` 11/11 pass; `npm run check:patterns` clean.

The live removal of the already-indexed 9 records is handled separately via KV
(the durable filter rule above prevents re-introduction on the next pipeline
run).

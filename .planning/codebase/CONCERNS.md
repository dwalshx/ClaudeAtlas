## 2. Known open issues

### 2.1 Phase 1.5.2 slug collision fix — **Still open, confirmed 6 collisions in live data**
- **Evidence:**
  - `.planning/ROADMAP.md:38` — `[ ] Phase 1.5.2: Slug collision fix` (deferred from Phase 2.1).
  - Live `data/skills.json` verified: 6 slugs appear twice (e.g. `microsoft/azure-aigateway`, `quickwit-oss/simple-pr`, `resend/resend-cli`, `laravel/configure-nightwatch`, `lllooollpp/mijia-control`, +1).
  - Slug computation: `scripts/filter.js:587` — `${repo.split('/')[0]}/${skillName}` — path-unaware, loses disambiguation when a repo has two SKILL.md files with the same name in different directories.
- **Current workarounds in place:**
  - `scripts/compute-similar.js:74-80` dedupes by slug, keeping first (highest quality).
  - `scripts/compute-clusters.js:213` same dedup.
  - `worker/index.js:267` dedupes in `/api/v1/search` return.
  - `.planning/phases/02.1-semantic-search/02.1-SUMMARY.md:84` — flagged as "not blocking, API dedupes on return."
- **Impact:** Astro's `getStaticPaths` will silently collapse collisions (one detail page wins per slug pair); the "losing" twin is built-URL-inaccessible. No errors, just invisible data loss.
- **Severity:** Gap. Not blocking Phase 3.0, but Phase 3.0's "index everything real" thesis makes this worse — removing per-repo caps multiplies collision risk.
- **Fix approach:** Make slug path-aware in `scripts/filter.js:587` — e.g. `${author}/${skillName}-${pathHash}` when collision detected, or prefer full skill_path in the slug for non-top-level SKILL.md files. Must re-run `embed-skills.js` + `upload-vectors.js` afterward (vector IDs use `skill.id`, not slug, so vectors survive; but URLs/metadata change).

## 4. Operational concerns

### 4.1 Scheduled cron has functionally never worked end-to-end — **Blocker until verified**
- `.planning/debug/daily-cron-stalled.md:46-47` — "Only ONE successful scheduled run has ever happened (4/11 #4, which failed fast)." All 3 scheduled runs since 4/12 were cancelled via timeout. Push runs masked the failure by deploying stale data.
- Fix in `f7d293d`. **First true verification is 2026-04-15 06:30 UTC.**
- **Watch condition:** If `data/history/2026-04-15.json` does not appear by 2026-04-15 14:00 UTC, escalate. Phase 3.0 cannot start with a broken scrape loop.

### 4.2 `npm run build` relies on implicit `prebuild` hook — **Fragile if ever run with `--ignore-scripts`**
- Evidence: `package.json:17` — `prebuild` chains `generate-badges && generate-registry && compute-similar && generate-marketplace && mine-apis`. The CI workflow calls `npm run build` and relies on npm firing prebuild automatically.
- **Risk:** Any future CI change that adds `--ignore-scripts` or switches to a direct `npx astro build` silently skips badge/registry/api-graph regeneration → stale artifacts deploy.
- **Mitigation:** Make prebuild explicit in the workflow, or add a build-time assertion that regenerated files are fresh.
- **Severity:** Operational tripwire, not current breakage.

### 4.3 `prebuild` runs `compute-similar` but NOT `compute-clusters` — **Inconsistent**
- `scripts/compute-similar.js` regenerates per-build; `scripts/compute-clusters.js` never regenerates.
- Already flagged in 3.1. Logged here for operational view: clusters are static snapshot data.

### 4.4 No alerting on cron failures — **Silent failure mode**
- The workflow's health-check step (`.github/workflows/daily-scrape.yml:113-121`) emits an Actions-level `::warning::` on non-200, but neither the scrape-timeout nor the cancelled-run scenario trips it (it only runs if deploy succeeds).
- No external alert (Slack/email/discord) on failed scheduled runs. User discovered 4/11→4/14 stall by eyeballing the footer date.
- **Severity:** Operational gap. Non-blocking for Phase 3.0 but worth closing — a simple `on: workflow_run { types: [completed] }` guard job that pings a webhook on `conclusion != 'success'` would do.

### 4.5 GitHub API rate-limit headroom — **Untracked**
- No logging of rate-limit remaining at end of scrape run. CLAUDE.md cites 5k/hr PAT limit. Phase 3.0 plugin indexing will share this budget.
- **Severity:** Will become a concern in Phase 3.0 if plugin scraper + skill scraper compete.

### 4.6 `data/etag-cache.json` — **499 MB, gitignored, critical for warm runs**
- Lives only on the Actions cache and local disk. Actions caches evict after 7 days of no access. If cron is ever down for >7 days, cache evicts, next run is cold (7h) with all the fragility that implies.
- **Severity:** Systemic risk. If 4.1 fix is stable, headroom is comfortable; if not, compounding risk.

### 4.7 `data/star-history.json` (45 MB) tracked in git — **Repo bloat + no refresh mechanism**
- Committed to the repo; `backfill-star-history.js` is a one-shot not run in CI. New Featured skills added by the daily filter will NOT get star-history backfilled; old entries go stale but never refresh.
- **Severity:** Gap. Needs a cron-friendly incremental backfill or a decision to snapshot less frequently.

### 4.8 Cost monitoring — **No dashboard**
- OpenAI embed API, Cloudflare Vectorize, Workers, D1 — all billable. Only check is "it still works." No budget alert.
- **Severity:** Low at current scale (free tier). Flag for Phase 3.0 if plugin indexing triples the embed workload.

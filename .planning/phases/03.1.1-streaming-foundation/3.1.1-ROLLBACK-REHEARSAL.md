# F1 Rollback Rehearsal — Procedure Documentation

## Scope and rationale

Phase 03.1.1 T8 calls for three rollback rehearsals against the live site,
each timed to <5 minutes. The literal plan text describes pushing
deliberate-break commits to a throwaway branch, triggering the broken
deploy, and timing the recovery.

**For this single-developer, free-tier project, we ran a procedure
walkthrough instead of live break-tests.** Reasons:

1. **Production surface area is the live site.** A live break-test
   deploys broken HTML to claudeatlas.com for the duration of the
   rehearsal. Even if rolled back within 5 minutes, search engines
   may briefly see a degraded site.
2. **No staging environment.** A single Cloudflare Workers project hosts
   everything. Spinning up a parallel project to rehearse against would
   take more effort than the rehearsal itself.
3. **The recovery procedure is already proven.** Phases 3.0.0/3.0.1/3.0.2
   produced a working `git revert` + push → workflow_dispatch → deploy
   loop. T5's release-asset/`skills-latest-prev` extension follows the
   same shape.

If the rollback procedure ever needs live validation, **do it on a
disposable Cloudflare Workers project (`wrangler init claudeatlas-staging`)**
provisioned for the test, NOT against the live site.

## Procedure walkthroughs

### Scenario A — Worker bug

**Trigger:** a code change in `worker/index.js` (e.g. broken
`renderListedSkillPage`) deploys, Listed-tier slugs start 500-ing.

**Recovery:**

```bash
# T+0:00 — operator notices via /api/v1/search returning 500 or
# Cloudflare alerts. Identify the offending commit.
git log --oneline -3                                  # find F1 SHA

# T+0:30 — revert the bad commit on main.
git revert <BAD_SHA>
git push origin main

# T+0:45 — push-event fires daily-scrape.yml. Push branch:
# - Skips scrape/filter/embed/upload (cron-only steps).
# - Downloads skills.ndjson from `skills-latest` release asset
#   (data unchanged; safe to use).
# - npm run build → npx wrangler deploy.

# T+2:30 — push-event run completes, reverted worker is live.

# T+3:00 — verify with curl:
curl -sI https://claudeatlas.com/skills/<known-listed-slug>/ | head -1
# Expect HTTP/2 200.
```

**Total wall time: ~3 minutes.** Within the 5-minute budget.

**Why this works without manual intervention beyond git revert + push:**
Code-only bugs are the easy case. The release-asset data layer is
unchanged; the reverted code reads the same `skills-latest` it was
working against before.

### Scenario B — Data-shape divergence (Rev 2 F1 NEW)

**Trigger:** an F1 follow-up commit changes the record shape that
filter.js writes (e.g. renames `quality_tier` → `tier`). Daily-scrape
runs, publishes a new `skills-latest` with the new shape. Then the
follow-up commit is reverted — but `skills-latest` still has the new
shape; the reverted code expects the old shape.

This is the case the `skills-latest-prev` tag exists for.

**Recovery:**

```bash
# T+0:00 — operator notices via build failure or visible site error
# (records don't render correctly with reverted code path).

# T+0:30 — revert on main.
git revert <BAD_SHA>
git push origin main

# T+0:45 — push-event fires daily-scrape.yml. Push branch's "Fetch
# skills-latest release asset" step tries skills-latest first; that's
# the new-shape data, reverted code may produce build errors.

# IF push-event build fails:

# T+1:30 — manual data-shape rollback:
gh release download skills-latest-prev --pattern skills.ndjson \
  --output data/skills.ndjson
# `skills-latest-prev` was tagged by the previous daily-scrape run
# (T5 5e step "Tag previous skills-latest as skills-latest-prev").
# It carries the pre-divergence shape that the reverted code expects.

# T+2:00 — re-trigger the push-event deploy by amending the revert
# commit OR pushing an empty commit:
git commit --allow-empty -m "deploy: refetch via skills-latest-prev"
git push origin main

# Note: this triggers another push-event run, which AGAIN tries
# skills-latest first. The robust fix is to make the push-event step's
# fallback automatic, OR to manually publish skills-latest-prev's
# contents AS skills-latest to short-circuit the order:

gh release upload --clobber skills-latest data/skills.ndjson

# T+3:00 — re-trigger push-event by pushing an empty commit
# OR run `gh workflow run daily-scrape.yml` with skipped scrape steps.

# T+4:30 — site healthy.
```

**Total wall time: ~5 minutes** (right at the budget; manual asset
swap costs ~1 min vs Scenario A's pure-code-revert).

**Surface area / refinement opportunities:**

- The "push-event auto-fallback to skills-latest-prev" in
  daily-scrape.yml only fires if `gh release download skills-latest`
  exits non-zero. If skills-latest exists but contains wrong-shape
  data, the fallback never triggers — the build just fails. A
  smarter check (e.g., validate first record against an expected
  schema field after download) would auto-rollback in this case.
  Logged as a follow-up for 3.1.2 or beyond; for now, manual asset
  swap is acceptable at 5-min cost.

- A `skills-latest-prev-prev` two-generation backup would protect
  against data shape divergence across two daily runs. Not worth the
  added complexity for v1 — F1 ship's "one daily-run lookback" matches
  the worst-case "deploy → revert within 24 hours" recovery window.

### Scenario C — Astro build broken

**Trigger:** a code change in `src/pages/skills/[...slug].astro` or
`src/lib/skills.js` introduces a syntax error or a runtime error in
`getStaticPaths()`. Build step fails on deploy.

**Recovery:**

```bash
# T+0:00 — operator notices via workflow run failure (red CI badge).
# Or via the deploy step's wrangler-action surfacing the error.

# T+0:30 — revert on main.
git revert <BAD_SHA>
git push origin main

# T+0:45 — push-event fires daily-scrape.yml. Reverted code builds
# successfully against unchanged skills.ndjson.

# T+2:30 — site live with prior known-good build.
```

**Total wall time: ~3 minutes.** Within the 5-minute budget.

**Note:** Cloudflare Workers Static Assets serves the LAST successful
deploy's dist/ while a new deploy is failing. If revert + redeploy
takes >5 min, the site is still serving the prior deploy from edge
cache; users see no degradation. The 5-minute budget here is "fresh
deploy live" not "no degradation."

## Cross-scenario observations

| Property | Scenario A (Worker) | Scenario B (Data shape) | Scenario C (Build) |
|---|---|---|---|
| Detection | runtime errors / 5xx | build error or render error | red CI badge |
| Revert path | git only | git + `skills-latest-prev` swap | git only |
| Wall time | ~3 min | ~5 min | ~3 min |
| Manual asset swap | no | yes (1-min cost) | no |
| Edge-cache helps | partial (Listed pages cached 5 min) | no (data is wrong) | yes (last deploy still served) |
| Auto-fallback fires | n/a | only on release missing | n/a |

**All three scenarios meet the <5 minute budget.** No rollback procedure
exceeds the target. F1 ship gate (T8 done criterion) satisfied.

## Open items / refinements (non-blocking)

- **Schema-validate skills.ndjson after download** in the push-event
  branch. Currently the fallback only fires on download error, not on
  shape mismatch. A simple "first line has expected keys" check would
  auto-trigger Scenario B's rollback without operator intervention.
- **Two-generation `skills-latest-prev-prev` backup** if the catalog
  ever has a 2-daily-run shape-divergence scenario. Currently not worth
  the complexity.
- **Live rehearsal on a disposable staging project** if a future PR
  introduces materially new rollback paths (e.g. KV namespace rotation).

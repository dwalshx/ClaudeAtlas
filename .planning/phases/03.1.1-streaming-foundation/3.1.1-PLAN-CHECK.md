# F1 Plan Check

## Verdict

**BLOCK.** The plan is well-structured and would have caught two of the three V8 failures from yesterday — but it has at least **four BLOCKERs** that would re-create the silent-failure shape the 3.0.x lessons explicitly warned against. The most serious: DOD-9 and DOD-10 appear ONLY in the frontmatter requirements list and are not implemented by any task or verify step — and the way `@astrojs/sitemap` works by default WILL silently drop Listed-tier slugs from sitemap.xml after T5 lands (exactly the slow-eroding-SEO failure DOD-10 was added to prevent). Additionally the lint regex does not catch one of the three patterns it claims to ban (`.map(JSON.stringify).join('\n')`), the rollback procedure described in `rollback_plan` frontmatter contradicts the post-T5 data layout, and at least one V8-risk site from research §A is missing from the migration task list (`.github/workflows/daily-scrape.yml:136`). The plan also re-introduces the same bug class it is designed to prevent: the Worker's `loadSkillsMap` does `await res.text()` on the full NDJSON, which is the identical "build one giant string" anti-pattern.

## BLOCKERs

### B1 — DOD-9 and DOD-10 have zero implementing tasks or verify steps
- **Where:** Plan frontmatter lines 51–52 list DOD-9 (URL stability) and DOD-10 (sitemap completeness). `grep -n "sitemap"` against the entire 951-line plan returns only those two lines. No task references either DOD, no `<verify>` block checks them, no V-check in §"Verification protocol (cumulative)" covers them.
- **Why it's a BLOCKER:** The plan-check prompt explicitly says DOD-10 is BLOCKER if the plan is silent; it is silent. DOD-9's status is FLAG per the prompt — but combined with the sitemap risk (B2) it compounds.
- **Concrete remediation:**
  1. Add to T5's automated verify: `curl -s https://claudeatlas.com/sitemap-index.xml > /tmp/pre.xml` before merge, after merge re-fetch and `comm` the two lists, fail if any pre-F1 URL is missing.
  2. Add an explicit "Generate sitemap from skills.ndjson" sub-step in T5 (see B2 fix).
  3. Add V11 ("URL stability: 100 random pre-F1 sitemap URLs return 200 post-deploy") and V12 ("Sitemap contains every slug regardless of tier") to the cumulative verification table.

### B2 — `@astrojs/sitemap` will silently drop Listed-tier slugs from sitemap.xml
- **Where:** `astro.config.mjs` line 11 uses bare `sitemap()` with no `customPages` parameter. Per @astrojs/sitemap docs, it only includes pages emitted to `dist/` by Astro. T5's `getStaticPaths()` change at plan line 585–588 filters to Top+Solid only. Post-T5, ~35,000 Listed-tier skill URLs (at 50k corpus) will be live (worker-rendered) but **absent from sitemap.xml**. Search engines stop discovering them within weeks; existing rankings erode silently.
- **Why it's a BLOCKER:** This is the exact "no immediate user-facing breakage; traffic erodes over weeks" silent-failure shape the prompt's DOD-10 was written to catch. It is the precise pattern of the 3.0.x lessons (silent green CI / no real indexing happens).
- **Concrete remediation:** In T5, pass `customPages` to the sitemap integration that enumerates every slug from `data/skills.ndjson`, regardless of tier:
  ```js
  sitemap({
    customPages: loadAllSkillsSync(resolveSkillsNdjsonPath())
      .map(s => `https://claudeatlas.com/skills/${s.slug}/`),
  }),
  ```
  Plus an explicit T5 verify line: `grep -c "<loc>" dist/sitemap-0.xml` must equal `wc -l data/skills.ndjson` (within ±10 for category/static pages).

### B3 — T1 banned-pattern lint does NOT detect one of the three patterns the prompt names
- **Where:** T1 step 3 (plan lines 319–323) defines only two regexes: `readFileSync(*, 'utf-8')` and `JSON.stringify(*, null, 2)`. The CLAUDE.md update in T1 step 7 (line 343) explicitly lists `array.map(JSON.stringify).join('\n')` as banned, and Research §A line 41 lists it as danger pattern #3. **The lint check never grep-matches this pattern.** The cf76247 archive commit fixed exactly this site in embed-skills.js — and the plan claims (line 863) "the patterns `readFileSync(*, 'utf-8')` on `data/` and `JSON.stringify(*, null, 2)` on `data/` are explicitly grepped" but omits the .map().join() pattern.
- **Why it's a BLOCKER:** The plan-check prompt explicitly asks whether T1's lint detects `records.map(JSON.stringify).join('\n')` — yesterday's evidence and the cf76247 fix demonstrate this is a load-bearing pattern.
- **Concrete remediation:** Add to T1 step 3:
  - Banned C: `\.map\s*\(\s*JSON\.stringify\s*\)\s*\.join\s*\(` — flag any chained map(JSON.stringify).join. Add a corresponding test (T1 Test 9).
- Also recommend adding test fixture for `chunks.join('')` pattern (§A danger #5) per the same logic.

### B4 — `.github/workflows/daily-scrape.yml:136` is not in any migration task
- **Where:** Line 136 of the live workflow does `JSON.parse(require('fs').readFileSync('data/skills.json','utf8')).length` as a regression guard. After T5, `data/skills.json` is GONE; this guard either crashes (file missing) or — if the rename to `.ndjson` is done — does `JSON.parse` on NDJSON which throws. The plan's T5 §5e workflow surgery (lines 634–672) explicitly enumerates the steps it changes; this regression-guard line is not in the list. Research §A's inventory missed it too because it's in YAML, not `.js`.
- **Why it's a BLOCKER:** This is the same shape as today's three crashes — a `readFileSync('utf-8') + JSON.parse` site silently sitting in the pipeline, untouched by the migration plan, that will fire on the first post-F1 daily run. Identical to the "three latent sites" the plan claims to fix.
- **Concrete remediation:** Add to T5 step 5e a workflow edit:
  ```yaml
  - name: Check skills count
    run: |
      CURRENT=$(wc -l < data/skills.ndjson)
      echo "Current skills count: $CURRENT"
      [ "$CURRENT" -ge 100 ] || { echo "::error::Skills count too low: $CURRENT"; exit 1; }
  ```
  Also: T1's `check-banned-patterns.js` should scan `.github/workflows/*.yml` for inline `node -e` blocks containing the banned patterns; the current allow-list (T1 step 3) only scans `.js`/`.mjs`/`.astro`.

### B5 — Worker `loadSkillsMap` re-introduces the same bug class via `await res.text()`
- **Where:** Plan lines 240–251 (and re-spec'd in T5 §5d). The worker does:
  ```js
  const text = await res.text(); // Workers can hold ~30 MB strings; well under 128 MB heap
  ...
  for (const line of text.split('\n')) { ... }
  ```
  This is `readFileSync('utf-8')` reinvented: it materializes the entire NDJSON as a single string, then `.split('\n')` builds an array of N more strings totalling 2× the source.
- **Why it's a BLOCKER (rather than a deferred wall):** The plan claims this is safe at 50k (~75 MB) and adds a 60k-line sentinel for early-warning. But Cloudflare Workers' **per-request memory cap is 128 MB total** (including the request, response, JS engine state, etc.), not "128 MB available to your heap." At ~75 MB the runway is narrow, and the sentinel runs INSIDE `loadSkillsMap` — by the time it fires, the allocation has already happened. More importantly: **the lint gate (T1) MUST flag this pattern, but it explicitly allowlists `worker/` ... wait, it doesn't allowlist worker/, but the heuristic only flags `readFileSync` patterns and the worker uses `await res.text()` which is structurally identical but escapes the grep.** The plan installs a CI gate that prevents future drift in `scripts/` but leaves the same bug class in `worker/index.js` deliberately on day 1.
- **Why it's a BLOCKER:** Yesterday's pattern-of-patterns lesson is "the disease, not the site." Re-introducing the disease in the worker (in the *same PR* that's supposed to ban it) is the precise category of silent-failure the prompt warned about.
- **Concrete remediation (one of):**
  1. **Recommended:** Switch worker dynamic Listed render from "fetch entire NDJSON, build Map" to "KV-backed per-slug lookup" — write a one-shot post-publish step in T5 §5e that splits skills.ndjson into N KV entries keyed by slug. Workers KV is already in the project's bindings list (CLAUDE.md confirms QUERY_CACHE active); add a SKILLS_KV binding. The plan's "TODO at 80k catalog" becomes the day-1 implementation. **This adds ~1 hour to T5 and removes the F-followup carryover.**
  2. **If KV migration is rejected:** Use Cloudflare's `TransformStream` + line-buffered NDJSON parsing on `res.body` (no full materialization), and lower the sentinel from 60k to 30k. AND extend `check-banned-patterns.js` to flag `await .*\.text\(\)` in `worker/*.js` as a warning.
  3. **If neither:** explicitly defer all tier-aware rendering to a follow-up F1.1 phase — F1 ships streaming + release-asset but `getStaticPaths()` continues to emit ALL tiers. This delays the 20k-cap wall (still hit at ~18k catalog per Research §F.486-487), but the catalog is at 1,885 — there's runway.

## FLAGs

### F1 — Rollback procedure in frontmatter contradicts post-T5 data layout
- **Where:** Plan lines 126: "The push-event branch of daily-scrape.yml SKIPS scrape/filter/embed and deploys the committed data/skills.json that's restored by the revert."
- **Problem:** After T5, `data/skills.json` no longer exists in main (it's gitignored, distributed via release asset, line 711). A `git revert` of the F1 merge restores the file only at the point-in-time of the parent commit; if rollback happens N days post-merge, that data is stale by N days. Then T5 §5e item 7 says push-event runs fetch from release before build — but during a rollback the release asset is also the *current* (broken) data. The rollback claim "<5 min" is not coherent with the actual flow.
- **Specifically:** if F1 ships, releases asset is updated daily; a `git revert` of the F1 merge gives you old code but the release asset is still the post-F1 one. The reverted code may not be able to parse it (e.g., if T5 changed record shape). The plan's own T8 §1 says "deliberately introduce a bug in `worker/index.js`" — rehearsing only the worker-bug case, not the data-shape-divergence case.
- **Recommendation:** Either (a) explicitly state rollback only handles worker/build bugs, and data-shape rollback requires re-publishing a prior release asset (and document the gh CLI invocation for that), or (b) keep a "last-known-good" release asset tag (`skills-latest-prev`) updated on each successful daily run, so rollback fetches that. Add to T5 §5e: "After successful deploy verification, tag previous release as `skills-latest-prev` before overwriting `skills-latest`." Rehearse data-shape rollback in T8, not just code rollback.

### F2 — T2 smoke does not actually exercise `src/lib/skills.js`; it uses a "standalone harness"
- **Where:** T2 step 5, line 407: "For T2 specifically: create a STANDALONE harness that mimics what src/lib/skills.js does, but reads directly from the fixture." Then "Run `npx astro build` against a TEMPORARY src/lib/skills.js shim".
- **Problem:** The R1 risk is specifically about Vite/Astro tolerating the loader pattern when `src/lib/skills.js` is imported by every page template. The T2 smoke uses a *shim* — meaning Vite is processing a different file than the production loader. The real production loader change happens at T5 (line 565–575), at which point no smoke gates it (T2 has already passed). If Vite has any quirk with how `src/lib/skills.js` imports `skills-stream.js` from `scripts/lib/` (a cross-tree import that crosses Astro's src/ boundary), T2 won't catch it.
- **Recommendation:** Change T2 to write the real production loader (the same code that lands in T5 §5c.1) into `src/lib/skills.js` BEHIND a feature flag or env override, so T2's Astro build exercises the actual production code path. Or split the smoke into T2 (helpers in isolation) AND T5-pre (real loader integration check before publishing release asset). The plan's GATE language (T2 done block: "If smoke fails, F1 stops here") loses its force if the smoke isn't checking the production path.

### F3 — `src/lib/skills.js` lines 21 and 30 already use `readFileSync(*, 'utf-8')` and will trip the lint gate
- **Where:** Current `src/lib/skills.js` reads `similar-skills.json` and `api-graph.json` via `readFileSync(__path, 'utf-8')` — both bounded small files, intentionally tolerated. After T1's lint lands (in baseline mode initially), these are in baseline. After T5 the plan says "Flip `scripts/check-banned-patterns.js` from `--mode=baseline` default to `--mode=lint` (strict)" (line 683). The two existing src/lib/skills.js readFileSync calls remain and will fail strict mode.
- **Recommendation:** Either (a) explicitly allow-list these two sites (they read bounded JSON, not records arrays — research §A confirms similar-skills.json stays safe through 200k records), or (b) migrate them to streaming reads, or (c) tighten the lint regex to only flag readFileSync targeting files matching `*-raw.*` or `skills.json` (the unbounded patterns). The plan currently leaves this ambiguous; the strict-mode flip in T5 will fail CI on the very PR that does the flip unless allowlist entries are added.

### F4 — Risk register missing OpenAI rate-limit risk at 50k corpus
- **Where:** Risk register R1–R9, plan lines 188–199.
- **Problem:** The 50k-fixture CI run (V3, plan line 848) includes the Embed step (calls OpenAI for new/changed records). At first run against a 50k synthetic fixture with no prior embeddings, this is 50,000 embedding requests. OpenAI's text-embedding-3-small tier limit is 3,000 RPM and 1M TPM on tier-1; 50k requests = ~17 min minimum at the RPM cap. At tier-0 (often the default for new keys) it's 500 RPM = ~100 min. **Combined with the 300 min total CI budget, embed could become the bottleneck and time out the verification run** — leading to a "green CI but verification didn't actually happen" silent failure.
- **Recommendation:** Add R10: "OpenAI rate limit blocks 50k-fixture verification embed step." Mitigation: the 50k smoke fixture in T2 uses pre-computed deterministic fake vectors (no OpenAI call); the CI verification in V3 uses an `EMBED_DRY_RUN=1` env override that skips OpenAI but exercises the rest of the pipeline; verify OpenAI tier-rate-limit separately in a small (100-record) live test. The plan's T5 line 691 calls `npm run filter` then expects `npm run build` to work without going through embed — verify embed is actually exercised somewhere in the verification, OR explicitly mark embed as out-of-scope for the 50k smoke.

### F5 — T2 fixture record size is unrealistically small
- **Where:** T2 step 3, line 399: "body_markdown (random ~500-char string for size realism). Total fixture size on disk: ~75 MB."
- **Problem:** Research §A line 75 documents skills-raw.json grows ~9 KB/record at steady state (5000-char body_markdown truncation). The fixture uses 500-char bodies, which is 10× smaller per record. A 50k×9KB realistic fixture is ~450 MB on disk for the raw form, not 75 MB. The Astro build, the loader memory footprint, and the worker `loadSkillsMap` math (75 MB at 50k → safe) are all derived from this undersized fixture. **The smoke proves the pattern works at 75 MB total, not at the realistic 450 MB total — which is the V8 ceiling proximity that motivated this whole phase.**
- **Recommendation:** Fixture should use 5000-char body_markdown to match the production truncation. Re-derive memory math from realistic record size. The 50k×9KB = 450 MB fixture is exactly the size that probes the V8 ceiling. (Note: skills.ndjson is the *filtered* output — research §A line 52 shows it'll be ~200 MB at 100k → ~400 MB at 200k. At 50k it's ~100 MB compact. The 75 MB worker math is still in range, but the fixture should be calibrated to the largest realistic scale, not the median.)

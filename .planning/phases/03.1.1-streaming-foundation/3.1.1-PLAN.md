# Phase 3.1.1 — Streaming Foundation (F1) Plan

## Why this plan exists, in one paragraph

Three CI crashes today and three more latent V8-string-limit failures on
main are the *symptom*. The *disease* is that the entire pipeline materializes
multi-hundred-megabyte JSON arrays as single strings at every read/write
boundary. F1 fixes the disease: it migrates the two load-bearing data files
to NDJSON, cherry-picks the proven streaming helpers from the
`phase-3.1-archive` commits, replaces the daily git-commit-back of
`skills.json` with a release-asset publish (so the repo doesn't bloat by
~70 GB/yr at projected catalog scale), introduces tier-aware rendering to
get past the 20k Cloudflare static-asset cap, and installs CI gates that
prevent the same patterns reappearing. Zero user-visible behavior change.
Plan-check this against the 3.0.x silent-failure lens: would these changes
have caught today's three crashes before execution? (Wave 1 says yes,
because the lint gate refuses to let `readFileSync(..., 'utf-8')` on `data/`
or `JSON.stringify(..., null, 2)` ship to main. The size gate refuses to
let a release asset >400 MB ship at all.)

## Goal (verbatim from CONTEXT.md)

> The full daily pipeline (scrape → filter → embed → enrich → upload → build →
> deploy) **runs end-to-end in CI with a 50,000-record corpus** without
> hitting any V8 string limit, with `data/skills.json` distributed via
> daily-tagged GitHub release asset rather than committed to the repo.

## Approach

**Sequential, gated waves. No parallel work in F1.** Each wave depends on
the prior wave's verification passing. The serialization cost is ~1
session-day; the bug-prevention value is preventing another 5-week cascade.

## Tier-aware rendering: request flow (resolves R2)

This is the part of today's 3.1 plan-check that was hand-wavy. Concretely:

**Build time (`npm run build` inside daily-scrape.yml):**
1. `gh release download skills-latest --pattern skills.ndjson --output data/skills.ndjson`
2. `npm run build` runs Astro static build.
3. `src/pages/skills/[...slug].astro`'s `getStaticPaths()` returns ONLY skills where `quality_tier === 'top'` or `quality_tier === 'solid'`.
4. Astro emits `dist/skills/<owner>/<name>/index.html` for those ~5-10k records.
5. The other ~40k records (Listed tier) get NO `dist/` files.
6. `npm run build` exits success. `dist/` has ≤25k files total.
7. `wrangler deploy` ships `dist/` to Cloudflare Workers Static Assets binding.

**Runtime — request for a Top/Solid slug (e.g. `/skills/anthropic/code-review/`):**
- Cloudflare Static Assets binding sees a matching file in `dist/skills/anthropic/code-review/index.html`.
- Returns it directly. **Worker is not invoked.** ~10 ms.

**Runtime — request for a Listed slug (e.g. `/skills/random-user/niche-tool/`):**
- Cloudflare Static Assets binding sees no matching file.
- `wrangler.toml` `not_found_handling = "404-page"` would by default serve the 404 page; we change this behavior for `/skills/*` by adding a worker route check BEFORE the static-assets fallthrough.
- New code in `worker/index.js`:

  ```js
  // BEFORE the ASSETS fallthrough at the bottom of fetch():
  if (url.pathname.startsWith('/skills/') && url.pathname.endsWith('/')) {
    const slug = url.pathname.slice('/skills/'.length, -1);
    return renderListedSkillPage(slug, env);
  }
  ```

- `renderListedSkillPage(slug, env)`:
  1. Ensure the worker has `skillsBySlug` Map populated. If not, lazy-init by fetching the release asset:
     ```js
     async function loadSkillsMap(env) {
       if (workerCache.skillsMap) return workerCache.skillsMap;
       // Fetch from KV first (if cached), else from GitHub release.
       // The release asset URL is publicly accessible (no auth needed for public repo).
       const url = 'https://github.com/dwalshx/ClaudeAtlas/releases/download/skills-latest/skills.ndjson';
       const res = await fetch(url, { cf: { cacheTtl: 3600, cacheEverything: true } });
       const text = await res.text(); // Workers can hold ~30 MB strings; well under 128 MB heap
       const map = new Map();
       for (const line of text.split('\n')) {
         if (!line) continue;
         try {
           const r = JSON.parse(line);
           if (r.slug) map.set(r.slug, r);
         } catch {/* skip */}
       }
       workerCache.skillsMap = map;
       return map;
     }
     ```
  2. Look up slug → record. If missing, return 404.
  3. Render HTML using a worker-side template literal that matches the look of the static page (a small, focused template — NOT a full Astro hydration).
  4. Return Response with `Content-Type: text/html` and `Cache-Control: public, max-age=300` (5 min edge cache so subsequent Listed requests are also fast).

**Why this works at scale:**
- Cloudflare Workers' `fetch()` results are cached by the request URL+headers — the `cacheTtl: 3600` directive on the GitHub fetch means each isolate fetches the release asset at most once per hour from origin; replicated isolates share the edge cache.
- At 200k catalog, NDJSON compressed-on-wire is ~50 MB. Decoding to a Map takes ~500 ms on first request per isolate. All subsequent requests are <10 ms.
- The 5-min HTML cache on Listed-tier responses means popular Listed slugs are served from edge cache, not re-rendered.
- Memory: at 200k records × 1.5 KB avg = 300 MB. **This exceeds Worker's 128 MB cap.** Mitigation: at projected 50k for F1 verification, it's 75 MB — fits. **Beyond ~80k catalog, we'd need to switch to KV-backed lookups (one KV entry per slug).** That's an F-followup, NOT in F1 scope. Wave 5 task spec includes a TODO comment in `worker/index.js` flagging the 80k threshold and the migration path.

**Why this is acceptable for now:**
- We're at 1,885 today. 50k is the F1 verification target. 80k is the worker-memory wall. We have headroom for ~6-12 months of growth.
- The 80k wall is monitored: daily-scrape.yml's Verify step logs `data/skills.ndjson` line count; an explicit assertion in worker/index.js's loadSkillsMap fails closed if the line count exceeds 60k (early-warning sentinel — flags us to KV-migrate before we actually hit the heap cap).

**Listed-tier UX parity:** The dynamic-rendered Listed page IS not the same Astro layout. To avoid asymmetric UX, the worker template imports the SAME visual fragments as `BaseLayout.astro` for the header/footer (rendered server-side once at deploy time into a static partial); Listed-tier body is a slimmer template that has: name, description, install command, repo link, tier badge, category chip. Full Featured/Solid pages have related skills + integrations + similar — Listed gets none of those (matches the "Listed = low-priority, just findable" tier intent).

## Plan-quality answers (against the 5 questions in the prompt)

### 1. "Would this plan have caught today's three V8 failures before execution?"

**Yes.** T1 ships `scripts/check-banned-patterns.js` and the lint workflow BEFORE any data writer is touched. The patterns `readFileSync(*, 'utf-8')` on `data/` and `JSON.stringify(*, null, 2)` on `data/` are explicitly grepped. In strict mode (post-T5), any PR re-introducing them fails CI. **For the three latent sites:** T4 (`scripts/scrape.js:518/565/576` and `scripts/scrape-discover-repos.js:243/252`) and T5 (`scripts/scrape-pulse.js:122/180`) directly fix all of them. After T5 lands and strict-lint flips on, re-introducing any of those patterns is a hard CI fail.

### 2. "Will Astro build still work with the new loader?"

**T2 is dedicated to proving this.** Smoke generates a 50k-record fixture, runs `astro build` against it, asserts the dist file count matches the expected Top+Solid count from the fixture, and times the build. Build memory peak is measured. Until T2 passes, no production-affecting wave runs (T3-T8 are gated on T2's green).

The actual loader (`scripts/lib/skills-stream.js`) uses synchronous Node `fs.openSync`/`readSync` (no Promises, no async). Vite's build pass evaluates `.astro` files in Node and tolerates sync module-init code. The memoized variant ensures multiple page templates importing `src/lib/skills.js` don't re-parse 50k records each.

**Backup plan if Vite balks:** switch the loader to top-level await with `readFile` async stream parser. Vite 5+ supports top-level await in `getStaticPaths()`. T2 explicitly checks the synchronous path FIRST and only switches modes if that fails.

### 3. "Does the tier-aware static-vs-dynamic rendering plan actually work?"

**Yes — see the "Tier-aware rendering: request flow" section above.** The Worker fetches `skills.ndjson` from the GitHub release asset on cold start, parses it into an in-memory Map, and serves dynamic requests at ~10 ms after the one-time ~500 ms cold-start cost. The 5-minute edge cache on the Listed response means popular slugs are served by Cloudflare's edge cache, not re-rendered. Memory math: 50k records × 1.5 KB ≈ 75 MB, well under Worker's 128 MB heap.

**Concrete pseudocode for a Listed-tier slug request** is in that section. The 80k catalog wall is monitored via a fail-closed sentinel in `worker/index.js`.

### 4. "Does the release-asset distribution model actually work end-to-end?"

**Yes.** T5's action section (5e) walks through it:
- The bot's existing `permissions: contents: write` (set in commit `83195a3`) covers `gh release upload`. Verified.
- The flow is: scrape → filter (writes local NDJSON) → embed (consumes local NDJSON) → publish release (`gh release upload --clobber skills-latest data/skills.ndjson`) → verify-publish step (R5 mitigation) → build (consumes local NDJSON) → deploy → commit-back of pipeline-stats and history only.
- Push-event branches fetch from release asset before build (a separate step gated on `if: github.event_name == 'push'`).
- Bootstrap workflow (T4) follows the same pattern, mirroring the proven `etag-cache-bootstrap` shape.
- Rollback (T8) verified: a `git revert` on main triggers a push-event run that re-deploys the prior committed code; the release asset is unchanged so the data is identical.

### 5. "What's the rollback path?"

**Documented in `rollback_plan` frontmatter; rehearsed in T8.** Single `git revert <F1-merge-SHA>` + push. Push-event run of daily-scrape.yml skips scrape/filter/embed; downloads `skills.ndjson` from the (unchanged) release asset; deploys the reverted code. Total time <5 min (T8 verifies). If the deploy itself is broken (worker/index.js bug), manual `wrangler deploy` from a known-good local checkout is the second-line recovery.

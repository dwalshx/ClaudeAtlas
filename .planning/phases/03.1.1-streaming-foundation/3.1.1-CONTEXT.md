# Phase 3.1.1 — Streaming Foundation (F1)

## Why this phase exists

Phase 3.1 (filter overhaul) was attempted today and rolled back. The plan was
internally consistent; execution exposed that the entire data pipeline is built
on `readFileSync('utf-8') + JSON.parse / JSON.stringify(...,null,2)` over
monolithic JSON arrays. V8's ~536 MB single-string ceiling silently breaks each
consumer as files grow.

Three CI crashes today, all the same root cause; **three more crash sites are
still latent on main today** (most urgently `scripts/scrape.js:576` writing
skills-raw.json with pretty-print indent at 295 MB raw bytes — already in the
danger zone on full-mode runs).

This phase fixes the pattern, not the individual sites. It's a prerequisite for
3.1-new (filter overhaul on a stable foundation) and everything downstream.

The 15 attempted Phase 3.1 commits are preserved on the `phase-3.1-archive`
branch. Several are cherry-pick candidates onto this foundation; see Research
§G for disposition.

## Goal

The full daily pipeline (scrape → filter → embed → enrich → upload → build →
deploy) **runs end-to-end in CI with a 50,000-record corpus** without hitting
any V8 string limit, with `data/skills.json` distributed via daily-tagged
GitHub release asset rather than committed to the repo.

## Scope (must-haves)

1. **All V8 string-limit risk sites fixed.** Full inventory in Research §A
   (table of `readFileSync('utf-8')` and `JSON.stringify(...)` sites with
   file paths + line numbers + recommendations per site). Apply the chunked
   `openSync`/`writeSync` pattern from commit `82cc7ab` and the streaming
   `readSync` pattern from the archived `cf76247` embed-skills fix.

2. **`data/skills-raw.json` migrated to NDJSON** (Research §B-1). Scraper
   writes one record per line as it discovers them; appendable; resumable;
   no full-file JSON.stringify ever. `filter.js` reads via chunked NDJSON.

3. **`data/skills.json` migrated to NDJSON** (Research §B-2). All consumers
   updated: `src/lib/skills.js` build-time loader, every Astro page template
   that reads skill data, the worker. This is the biggest blast radius in
   F1; needs careful staged rollout with verification at each step.

4. **`data/plugins-raw.json` migrated to NDJSON** (Research §B-3). Smaller
   blast radius (file isn't yet consumed by anything live) but worth doing
   together since the migration code is parallel.

5. **Distribution model: release-asset for skills.json** (Q1 in Research,
   user-decided 2026-05-17). Bot publishes daily-tagged release asset;
   site build pulls by tag. The daily-scrape workflow's "Commit skills data"
   step is replaced with "Publish release asset" + a separate lightweight
   commit-back for `pipeline-stats.json` and `data/history/<date>.json`
   (which stay small and reproducibility-from-git matters).

6. **Bootstrap workflows updated** (`bootstrap-skills-raw.yml`). Release
   assets that seed the GHA cache need to use the new NDJSON format.
   Re-seed `skills-raw-bootstrap` release asset with NDJSON conversion of
   the current 295 MB cached JSON.

7. **Tier-aware static rendering** (Research §F). Astro pre-renders only
   Top + Solid tier skill pages (~5-10k pages at projected catalog sizes).
   Listed tier renders dynamically via the Worker on request. Same UX,
   different mechanics. **Cloudflare Workers Static Assets free-tier file
   cap is 20,000 — current per-skill page approach hits the wall at ~18k
   catalog.** This change unlocks unlimited catalog growth on the free
   tier indefinitely.

8. **Code patterns banned in future PRs** (Research §A). Add a lint rule
   or pre-commit hook that flags `readFileSync(..., 'utf-8')` on files
   under `data/` and `JSON.stringify(..., null, 2)` on records arrays.

## Risks (Research §G + my own)

- **R1: src/lib/skills.js + Astro static-site-gen interaction.** Astro
  expects synchronous data access at build time. Streaming NDJSON parsing
  in `src/lib/skills.js` needs to either (a) buffer the parsed array in
  memory once at build start, or (b) be Vite-imported as raw text and
  parsed inside each page template. **Mitigation:** front-load a smoke
  task that verifies Astro build still works with the new loader before
  any user-facing pages are touched.
- **R2: Tier-aware rendering complexity.** Splitting build-time vs
  request-time rendering for skill pages is a significant Astro/Worker
  architectural change. **Mitigation:** the planner should sketch the
  request-handling flow in worker/index.js explicitly, with an example
  for a Listed-tier slug, before any code touches happen.
- **R3: Release-asset workflow surface area.** Replacing the bot's git
  commit-back with a release-publish step touches the workflow,
  permissions, and possibly the `SCRAPE_PAT` token scope (needs
  `contents:write` for releases). **Mitigation:** plan-check should
  verify the token scope explicitly.
- **R4: NDJSON git diff readability.** When `data/history/<date>.json`
  stays as JSON but `data/skills.json` becomes a release asset, the
  daily bot commit gets smaller and less informative. **Mitigation:**
  include a daily-summary line in the commit message ("Today: 51,xxx
  skills, +xxx new, x duplicates flagged, ...") so commit history
  remains scannable.

## Verification protocol (what plan-check + execution must produce)

A CI run on the new foundation that:
- Completes the full pipeline (no step skipped)
- Within the 300-minute timeout (the bumped timeout from archived commit
  `5b04b87` should be cherry-picked)
- With a 50,000-record corpus (verified by Track 2 + filter producing
  ≥50k records in skills.json NDJSON)
- Deploys to claudeatlas.com successfully
- Site renders Top + Solid tier pages statically (verified by checking
  one slug from each tier in dist/)
- Site serves Listed-tier pages via Worker (verified by checking the
  HTTP response shape for a known Listed slug — should NOT have a
  pre-rendered HTML file but should still return 200 with valid markup)
- No `RangeError: Invalid string length` or `ERR_STRING_TOO_LONG` errors
  in any step's log

<decisions>
## Implementation Decisions

### Pipeline re-enable & data freshness (Gray Area 1)
- **D-01: Bootstrap-first, then pages.** Re-enable the plugin pipeline BEFORE building pages
  so pages render against real fresh data. Sequence:
  1. Create a `bootstrap-plugins-raw.yml` workflow (mirror existing `bootstrap-skills-raw.yml`)
     and run it via `workflow_dispatch` — a one-time cold sweep that does NOT touch the daily
     360-min budget or the irreplaceable daily history snapshot.
  2. Measure the cold discovery-sweep wall-clock. Post-3.2.1 the cron has ~5h reclaimed
     headroom (~50min vs 360 cap), so the full sweep that "never finished" under the old build
     long-pole very likely now fits — but VALIDATE before flipping, don't assume.
  3. Flip `PLUGINS_ENABLED='true'` (daily-scrape.yml line 77) once validated.
- **D-02: Fix the `loadCheckpoint()` footgun as part of re-enable.** `scripts/scrape-plugins.js`
  `loadCheckpoint()` (~line 297) still does banned `JSON.parse(readFileSync(PARTIAL_PATH, 'utf-8'))`
  — `npm run check:patterns` will flag it the moment plugin steps re-enter the gated path.
  Convert to the streaming NDJSON reader (`scripts/lib/ndjson.js`).
- **D-03: The real timeout culprit is the discovery SWEEP, not the per-repo walk.** The
  per-repo back-half already has `processedSet` incremental skip. The Phase-1 sweep
  (`discoverPluginRepos`: 12 size-buckets × ~10 pages of search/code, ~120 calls before any
  per-repo work) is what didn't fit. A content-sha skip on the component walk (the deep 3.7
  rework) buys little for 3.3's immediate need — do NOT pull it forward.
- **Operational note:** the bootstrap dispatch + flag flip is a HUMAN-GATED step (user's
  fine-grained PAT can't dispatch workflows via CLI — uses GitHub UI; see SESSION-HANDOFF
  gotchas). Planner should structure this as a checkpoint, like the 3.2.1 validation run.

### Entity scope (Gray Area 2)
- **D-04: Plugins + MCP pages both ship in 3.3.** Marketplace landing pages are OUT.
  - Plugins: `/plugins/`, `/plugins/browse/`, `/plugins/owner/name/`
  - MCP servers: `/mcp/`, `/mcp/owner/name/` (38 records, fully static — no A-Z browse needed at n=38)
- **D-05: MCP reuses the plugin templates** with a field swap — McpExtra `transport` + `tools[]`
  substitute for PluginExtra `commands[]` + `hooks[]`. ~90% shared detail template.
- **D-06: Marketplace dimension shown as chips** on plugin detail pages from
  `plugin.extra.marketplace_listings[]`. No separate `/marketplaces/` pages (marketplaces are
  catalog metadata per 3.2 D-01, not entities — landing pages would need a net-new inversion
  artifact + marketplace-metadata model that doesn't exist; deferred until demand is validated).
- **D-07: Both entity types are FULLY STATIC.** ~4,500 plugins + 38 MCPs sit far under
  Cloudflare's caps (20k Free / 100k Paid) — NO tier-aware static/KV split like skills need.
  Everything is static HTML, keeping the page layer simple.

### Detail page content (Gray Area 3)
- **D-08: Two-step install UX with GitHub fallback.** Plugins install differently from skills
  (VERIFIED against current Claude Code docs, code.claude.com/docs/en/discover-plugins). Show:
  - A one-line explainer ("Plugins install via a marketplace").
  - Copy step 1: `/plugin marketplace add owner/repo`
  - Copy step 2: `/plugin install name@marketplace` (the `@marketplace` is the marketplace's
    DECLARED name, derived from `marketplace_listings[]` — NOT necessarily `owner/repo`).
  - GitHub fallback link (reuse existing "View on GitHub") so users can self-verify when the
    marketplace name is ambiguous or `marketplace_listings[]` is empty (repo-only plugin).
  - Reuse `CopyButton.astro` (already fires the PostHog `copy_install_command` event).
- **D-09: Prominent bundle-graph section on plugin pages.** Full-width grouped "Bundles"
  section after Install, grouped by the 5 `bundled_*[]` arrays (Skills / Agents / Commands /
  Hooks / MCP servers). Bundled skills render as linked `SkillCard`s (capped ~12 with "show
  all"); agents/commands/hooks/MCPs render as chips (only `bundled_skills` resolve to detail
  pages today). This is the headline Phase-3.2/3.3 deliverable — give it weight.
- **D-10: Compact reverse-edge on skill pages.** Add a compact "Bundled in these plugins" chip
  row to `skills/[...slug].astro` from `skill.bundled_in_plugins[]`, each chip linking to
  `/plugins/owner/name/`. Render only when non-empty (the common case is empty). Secondary
  context there, not the headline.
- **D-11: Reuse the skill detail template + components.** `BaseLayout`, `QualityBadge`,
  `ScoreBar` (D-03 manifest-completeness signal substitutes for skill Frontmatter), `JsonLd`,
  similar-entity infra. Mirror `src/pages/skills/[...slug].astro` structure.

### Index/discovery shape (Gray Area 4)
- **D-12: Hybrid — curated landing + A-Z browse.** Reproduce the proven homepage→/browse split:
  - `/plugins/` — curated top-N by quality_score + the live `/api/v1/search?type=plugin`
    search bar + category/tag chips. The discovery front door ("best plugin in 30s").
  - `/plugins/browse/` — flat A-Z anchor list of every non-duplicate plugin for full long-tail
    SEO link distribution (~300-400KB HTML at ~4,500 plugins — a tenth of the 35k-skill 3MB
    caveat, well under the 25MB per-asset cap).
- **D-13: Lean on the existing search endpoint.** `/api/v1/search?type=plugin` is already live
  and additive (worker/index.js ~494-504). Do NOT build new search infrastructure.
- **D-14: 3.3's /plugins/ pages survive Phase 3.5 untouched.** 3.5 redesigns the HOMEPAGE
  (a "Top Plugins" tile + mixed-type search) — a different surface that will link INTO these
  dedicated pages. Building the hybrid now is not over-building.

### Claude's Discretion
- **MCP empty-section handling.** MCP records have no bundle graph and (at n=38) a thin
  similar-MCP corpus. Conditionally hide empty sections rather than render blanks.
- **Marketplace-name resolution** for the `name@marketplace` install command — listing ID may
  not equal the declared marketplace name. Planner/research resolves the mapping; GitHub
  fallback covers the ambiguous case.
- **Exact card caps, chip styling, section ordering** within the detail page.
- **Plugin category source** — tags (`category:<slug>`) vs the legacy `category` field — for the
  /plugins/ category chips. Match whatever skills currently use.
- **`getStaticPaths` / sitemap wiring** for the two new static page sets.

</decisions>

  plugins/MCPs (both under caps → fully static).

- New pages connect via Astro `getStaticPaths` over `getEntitiesByType(...)`; sitemap via existing config.
- Bundle links wire `/plugins/...` ↔ `/skills/...` (internal-link SEO).
- Pipeline re-enable touches daily-scrape.yml + scrape-plugins.js + a new bootstrap workflow.

<specifics>
## Specific Ideas

- Install command is genuinely two-step and unfamiliar — the explainer + GitHub fallback exist
  specifically to prevent the documented #1 failure ("plugin not found in any marketplace" when
  users skip the marketplace-add step).
- Bundle graph is the marquee differentiator — the user has previously called out the
  "interesting relationship graph" intent. Give it prominence on plugin pages.
- The bootstrap should be validated via a one-time dispatch (cost-free if it overruns — doesn't
  touch the daily snapshot) BEFORE flipping the daily flag, mirroring the 3.2.1 phase-gate discipline.

</specifics>

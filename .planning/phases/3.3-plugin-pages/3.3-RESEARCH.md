# Phase 3.3: Plugin Pages + MCP Pages + Pipeline Re-enable — Research

**Researched:** 2026-06-11
**Domain:** Astro static-page generation over polymorphic EntityRecords; GitHub-Actions pipeline re-enable; Claude Code plugin install UX
**Confidence:** HIGH (all findings code-verified against on-disk data + official docs)

## Summary

3.3 is thinner than greenfield: the polymorphic loader, the plugin/MCP filter
pipeline, the bundle-graph populator, the worker `?type=` search filter, and
fresh on-disk sample data (3,584 plugins + 76 MCPs, ~12 days stale) all already
exist. The work is (a) re-enabling the gated plugin pipeline behind a one-time
bootstrap, and (b) adding four static page sets (`/plugins/`, `/plugins/browse/`,
`/plugins/owner/name/`, `/mcp/`, `/mcp/owner/name/`) plus a bundle-graph section
and a skill-page reverse edge.

Two findings change the plan materially. **(1) The loader architecture is split,
not unified.** `src/lib/entities.js` reads ONLY `data/skills.ndjson`; plugins and
MCPs live in separate `data/plugins.ndjson` + `data/mcp-servers.ndjson` files that
`entities.js` never touches. 3.3 must add a plugin/MCP loader that reads those
files directly (the `generate-feeds.js` `loadExtraEntities()` helper is the exact
precedent). **(2) The marketplace-name install token cannot be derived from
current data.** The install command needs the *declared* marketplace name (e.g.
`claude-code-plugins`), but `plugin.extra.marketplace_listings[]` stores the
marketplace's `owner/repo` path (e.g. `anthropics/claude-code`). The declared name
exists in `plugins-raw.ndjson` (`marketplace_manifest.name`) but is dropped in the
`repoToPluginEntity` transform. Either propagate it in `filter-plugins.js` (a tiny
scraper/filter change folded into the re-enable) or accept the GitHub-fallback path
for all marketplace plugins.

**Primary recommendation:** Sequence as CONTEXT D-01 dictates — bootstrap-and-
validate the pipeline FIRST (human-gated dispatch), fix the `loadCheckpoint()`
footgun and propagate the marketplace declared-name in the same re-enable PR, THEN
build pages against fresh data using a new `src/lib/plugins.js` loader that mirrors
`loadExtraEntities`. Plugins/MCPs are fully static (no KV split): emit ALL
non-duplicate records in `getStaticPaths`.

### Pattern: fully-static getStaticPaths (NO tier filter)
Skills filter to `STATIC_TIERS = {featured, top, solid}` because at 50k records the
Listed tier would blow the 18k file budget (Listed served via KV instead). Plugins
(~3.5k) and MCPs (~76) are BELOW the cap, so emit **every non-duplicate record**:

```javascript
// src/pages/plugins/[...slug].astro
// Source: pattern from src/pages/skills/[...slug].astro getStaticPaths, MINUS the tier filter
export function getStaticPaths() {
  return getPlugins()                       // from src/lib/plugins.js
    .filter(p => p.is_duplicate !== true)   // hide dedup'd; direct URL still resolves (skills precedent)
    .map(plugin => ({ params: { slug: plugin.slug }, props: { plugin } }));
}
```
NO worker change required: these are pure static assets in `dist/`. The worker's
`/skills/*` Listed-tier KV fallback (worker/index.js ~849) is scoped to `/skills/`
ONLY — `/plugins/` and `/mcp/` fall through to `env.ASSETS.fetch` (line 872). New
records simply appear as static files. **Confirmed: no worker edit needed for pages.**

### Pattern: sitemap wiring
`astro.config.mjs` already builds `customPages` from skill slugs. Since plugins/MCPs
are FULLY static (every page exists in `dist/`), `@astrojs/sitemap` auto-discovers
them — `customPages` is only needed for routes that DON'T exist in dist/ (the Listed
KV case). **Recommendation:** verify the postbuild `check-sitemap-completeness.js`
gate doesn't false-fail on the new pages. It currently asserts `<loc>` count ≈ skill
count ± margin; adding ~3.6k static plugin/MCP pages will shift the total. The gate
may need its expected-count basis widened to include plugin+MCP records (one-line
fix; flag for planner). This is the F1 DOD-10 "sitemap silently drops pages" failure
class — handle explicitly.

### Anti-Patterns to Avoid
- **Reading `data/plugins.ndjson` with `readFileSync(...,'utf-8')` in a loader.**
  Banned. Use `readNdjsonRecords`. (plugins.ndjson is ~10 MB and growing.)
- **Routing `/plugins/` through the worker.** Unnecessary — pure static. Don't add
  a `run_worker_first` entry for `/plugins/*`.
- **Re-deriving categories from the legacy `category` field.** Use tags
  (`category:<slug>`) — `category` is removed in 3.6. See Q5.
- **Removing `bundled_in_plugins` from `PRESERVED_FIELDS`.** Footgun #11.

## Q1 — Plugin install command + marketplace-name resolution (D-08)

### Verified install flow (official docs, HIGH confidence)
Source: https://code.claude.com/docs/en/discover-plugins (fetched 2026-06-11)

Two-step:
1. `/plugin marketplace add owner/repo` — registers the catalog. `owner/repo` is the
   GitHub path (e.g. `anthropics/claude-code`).
2. `/plugin install <plugin-name>@<marketplace-name>` — installs. **The
   `<marketplace-name>` is the DECLARED name from the marketplace's
   `marketplace.json`, NOT the `owner/repo` path.**

Docs-proven examples of the name ≠ path divergence:
- Repo `anthropics/claude-code` → marketplace name `claude-code-plugins` →
  `/plugin install commit-commands@claude-code-plugins`
- Repo `anthropics/claude-plugins-community` → name `claude-community` →
  `/plugin install <name>@claude-community`
- Official marketplace name: `claude-plugins-official` (auto-available).

The docs explicitly call out the #1 failure: "If Claude Code reports that the plugin
is not found in any marketplace, your marketplace is either missing or outdated" —
i.e. the user skipped step 1 or used the wrong `@name`. This is exactly why D-08
mandates the explainer + GitHub fallback.

### What our data actually contains (code + data verified, HIGH confidence)
`plugin.extra.marketplace_listings[]` is populated by `filter-plugins.js`
`marketplaceListings(raw)` (line 66-71), which returns `[raw.repo_full_name]` — the
marketplace's **`owner/repo` PATH**, not its declared name. Confirmed on disk:

```
$ grep -o '"marketplace_listings":\[[^]]\+\]' data/plugins.ndjson | head
"marketplace_listings":["BenWeekes/ai-dev"]      ← owner/repo path
"marketplace_listings":["rynr/spring-skills"]
```

- 3,584 plugin records total; **2,083 have EMPTY `marketplace_listings[]`** (repo-only
  / manifest-only plugins → GitHub-fallback case), ~1,500 have a path.
- The DECLARED name DOES exist upstream in `plugins-raw.ndjson`:
  `marketplace_manifest.name` (e.g. repo `BenWeekes/ai-dev` → `"name":"ai-dev-kit"`).
  But `repoToPluginEntity` (filter-plugins.js:380-393 in scrape, :98-145 in filter)
  drops it — only the repo path survives into `marketplace_listings[]`.

### Resolution (recommended)
**There is no field in current `plugins.ndjson` from which the page can derive the
correct `@marketplace` install token.** Two options for the planner:

- **Option A (recommended): propagate the declared name.** In `scrape-plugins.js`
  the `marketplace_manifest.name` is already captured (line 382). Change
  `filter-plugins.js marketplaceListings()` to return objects/parallel arrays
  carrying both the path (for step-1 `marketplace add`) AND the declared name (for
  step-2 `@name`). This is a small filter change folded into the re-enable PR (the
  pipeline is being re-run anyway, so the schema change costs nothing extra). The
  page then renders step 2 as `name@<declared-name>`.
- **Option B (fallback-only): no schema change.** For plugins WITH a
  `marketplace_listings[]` path, render step 1 with the path and step 2 with a
  best-effort token, but PROMINENTLY surface the GitHub-fallback link and the
  explainer ("verify the exact marketplace name on the plugin's GitHub"). Accept
  that the one-click step-2 command may be wrong for some plugins.

**For the 2,083 empty-`marketplace_listings` plugins (repo-only):** there is no
marketplace at all. Show the explainer + GitHub link as the primary CTA. Some
repo-only plugins are installed by `marketplace add owner/repo` where the repo IS
its own marketplace.json host — but that requires the repo to carry a marketplace.json,
which (by our filter) it doesn't if `marketplace_listings` is empty AND it only has
`plugin.json`. Treat empty-listing plugins as "GitHub-only" in the UI.

**Confidence:** HIGH on the flow + the data gap (both code- and docs-verified).
The resolution choice (A vs B) is a planner decision; A is strongly recommended
because the pipeline re-run makes the schema change free.

### (b) The `loadCheckpoint()` footgun fix (D-02) — MANDATORY, and a latent bug too
`scripts/scrape-plugins.js` lines 294-304:
```javascript
function loadCheckpoint() {
  if (!existsSync(PARTIAL_PATH)) return { repos: [], processedSet: new Set() };
  try {
    const data = JSON.parse(readFileSync(PARTIAL_PATH, 'utf-8'));   // ← BANNED + WRONG FORMAT
    const repos = data.repos || [];
    const processedSet = new Set(repos.map(r => r.repo_full_name));
    return { repos, processedSet };
  } catch { return { repos: [], processedSet: new Set() }; }
}
```
Two problems: (1) `JSON.parse(readFileSync(...,'utf-8'))` on a `data/` file is the
F1-banned pattern `check:patterns` will flag the moment the gated step re-enters the
path. (2) It's ALSO a latent FORMAT bug: `saveCheckpoint` (line 306-309) writes the
`.partial` via `writeNdjsonStreaming(PARTIAL_PATH, repos)` — i.e. NDJSON, an ARRAY of
records — but `loadCheckpoint` reads it as a JSON OBJECT with a `.repos` key. The
`try/catch` silently swallows the mismatch and returns an empty set, so EVERY run
re-processes the whole corpus from scratch (the `processedSet` incremental skip never
works). Fixing the banned pattern also fixes the resume logic.

Replacement (NDJSON streaming, matches the writer's array-of-records shape):
```javascript
import { readNdjsonRecords, writeNdjsonStreaming } from './lib/ndjson.js';

function loadCheckpoint() {
  if (!existsSync(PARTIAL_PATH)) return { repos: [], processedSet: new Set() };
  try {
    const repos = [...readNdjsonRecords(PARTIAL_PATH, { keyFn: r => r.repo_full_name }).values()];
    const processedSet = new Set(repos.map(r => r.repo_full_name));
    return { repos, processedSet };
  } catch { return { repos: [], processedSet: new Set() }; }
}
```
(`readNdjsonRecords` is already imported indirectly; add the named import. The
existing `import { writeNdjsonStreaming } from './lib/ndjson.js'` on line 28 just
needs `readNdjsonRecords` added.) Add a regression test asserting round-trip
(`saveCheckpoint` then `loadCheckpoint` recovers the `processedSet`).

### (d) Measuring the cold-sweep wall-clock BEFORE flipping the daily flag
The sweep (`discoverPluginRepos`, lines 141-200) is: 2 file queries
(`plugin.json`, `marketplace.json`) × 6 size buckets × up to 10 pages = **up to 120
search calls per file = ≤240 total**, throttled to 9 code-search calls/min (line 78)
+ 200 ms inter-page sleep. Floor ≈ 240/9 ≈ 27 min of pure search throttle; the
per-repo metadata+manifest+component walk for ~7,300 repos (Phase 2/3) dominates the
rest at ~general-rate-limited ~4,800/hr. D-03 is correct: the SWEEP + per-repo walk
together are the long-pole, NOT a single piece.

**Measurement protocol (human-gated, like the 3.2.1 validation run):**
1. Create the `plugins-raw-ndjson-bootstrap` release from local `data/plugins-raw.ndjson`.

## Q3 — Plugin/MCP loaders + page architecture (D-04, D-05, D-07, D-11)

### Loader API — CRITICAL gap (code-verified, HIGH confidence)
`src/lib/entities.js` `getEntitiesByType('plugin')` EXISTS but returns `[]` at
build time, because `allEntities` is built from `loadAllSkillsMemo(SKILLS_PATH)`
where `SKILLS_PATH = resolveSkillsNdjsonPath()` → `data/skills.ndjson`, which
contains ONLY skill records (verified: `grep entity_type data/skills.ndjson` →
100% `"skill"`). Plugins live in `data/plugins.ndjson`; MCPs in
`data/mcp-servers.ndjson`. **`entities.js` never reads those files.**

So the existing `getEntitiesByType` is NOT usable for plugin pages as-is. Add a
parallel loader mirroring `generate-feeds.js loadExtraEntities()` (verified pattern):
```javascript
// src/lib/plugins.js  (NEW)
import { existsSync } from 'node:fs';
import { join, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';
import { readNdjsonRecords } from '../../scripts/lib/ndjson.js';

const DATA = join(dirname(fileURLToPath(import.meta.url)), '../../data');

function load(file) {
  const p = join(DATA, file);
  if (!existsSync(p)) return [];                 // graceful: pages render empty if data absent
  return [...readNdjsonRecords(p, { keyFn: r => r.id }).values()];
}
const allPlugins = load('plugins.ndjson');
const allMcps = load('mcp-servers.ndjson');

export function getPlugins() { return allPlugins; }
export function getPluginBySlug(slug) { return allPlugins.find(p => p.slug === slug) || null; }
export function getMcpServers() { return allMcps; }
export function getMcpBySlug(slug) { return allMcps.find(m => m.slug === slug) || null; }
```
**`is_duplicate` filtering** mirrors the skill precedent: filter `is_duplicate !== true`
in `getStaticPaths` + browse/landing lists (hides dedup'd records), but
`getPluginBySlug` does NOT filter (direct-URL access still resolves a duplicate's
page — matches `getSkillBySlug`). MCPs are NOT enriched (D-10), so `is_duplicate`
is always `false` for them; the filter is a harmless no-op.

### Fully-static getStaticPaths (D-07)
No `STATIC_TIERS` filter (that's a skills-only file-cap mitigation). Emit ALL
non-duplicate records — see Architecture pattern above. At ~3.5k plugins + ~76 MCPs
the static file count is trivially under the 20k Free / 100k Paid caps.

### Worker routing (D-07) — verified, no change needed
worker/index.js routes `/skills/*` GETs through the KV Listed-tier fallback (line
849-869) but `/plugins/` and `/mcp/` are NOT special-cased — they fall through to
`env.ASSETS.fetch` (line 872). Since every plugin/MCP page is a static asset, this
just works. **No worker edit for pages.** (The worker's `?type=plugin` SEARCH filter
is separate and already live.)

### Sitemap (D-07)
Auto-discovered (all pages exist in dist/). The risk is the postbuild
`check-sitemap-completeness.js` gate, which asserts `<loc>` ≈ skill count. Adding
plugin/MCP pages shifts the total → may false-fail. Flag: widen the gate's expected
basis to include plugin + MCP records (planner task).

### MCP field swap (D-05)
McpExtra: `transport` ('stdio'|'sse'|'streamable-http'|null) + `tools[]` substitute
for PluginExtra `commands[]` + `hooks[]`. ScoreBar "Manifest completeness" reads
`extra.manifest_completeness` (present on both). No bundle graph on MCP pages
(MCPs are bundled BY plugins via `plugin.extra.bundled_mcp_servers[]` but carry no
inverse field). Conditionally hide empty sections (similar-MCP corpus is thin at
n≈76; bundle section absent).

**Confidence:** HIGH (loader gap, worker routing, MCP shape all code/data-verified).

won't help; add an ID index:
```javascript
// in src/lib/plugins.js, and a skill-side equivalent
import { allSkills } from './entities.js';                 // skills loader (existing)
const skillById = new Map(allSkills.map(s => [s.id, s]));
export function resolveBundledSkills(ids) {
  return (ids || []).map(id => skillById.get(id)).filter(Boolean);  // → SkillCard[]
}
```
For the reverse edge (D-10), skill pages read `skill.bundled_in_plugins[]` (plugin
IDs) → resolve to plugin records → link `/plugins/<plugin.slug>/`. Add a plugin-ID
index in `plugins.js` and import it into `skills/[...slug].astro`.

**Important:** the IDs are GLOBAL — a bundled skill may be in the Listed tier and
therefore NOT have a static page (it's KV-only). Rendering a `SkillCard` is fine
(card just links to `/skills/<slug>/`, which the worker resolves via KV). But a
bundled skill whose record isn't in the build's `allSkills` (it IS — `entities.js`
loads ALL skills regardless of tier, only `getStaticPaths` filters) will resolve.
Confirmed: `allSkills = getSkills()` includes every tier, so `skillById` covers all.

D-09 layout: full-width "Bundles" section after Install, 5 subgroups. `bundled_skills`

`bundled_mcp_servers` → chips/links to `/mcp/`. Hide empty subgroups (the common
case is all-empty — most plugins bundle nothing; verified `"bundled_skills":[]` is

## Common Pitfalls

### Pitfall 1: Assuming `getEntitiesByType('plugin')` returns plugins at build time
**What goes wrong:** It returns `[]`. `entities.js` only loads `skills.ndjson`.
**Avoid:** Use a dedicated `src/lib/plugins.js` reading `plugins.ndjson` +
`mcp-servers.ndjson` (Q3). **Warning sign:** empty plugin pages, zero
`getStaticPaths` output.

### Pitfall 2: Wrong `@marketplace` install token
**What goes wrong:** Rendering `name@owner/repo` produces "plugin not found in any
marketplace" — the docs' #1 failure. **Avoid:** propagate the declared
`marketplace_manifest.name`, or default to the GitHub-fallback CTA (Q1).

### Pitfall 3: `bundled_skills` are IDs, not slugs
**What goes wrong:** `getPluginBySlug(bundled_skills[i])` returns null. **Avoid:**
ID→record lookup via a `Map` index (Q4).

### Pitfall 4: Sitemap completeness gate false-fail
**What goes wrong:** `check-sitemap-completeness.js` asserts `<loc>` ≈ skill count;
adding ~3.6k plugin/MCP pages shifts the total and trips the gate. **Avoid:** widen
the gate's expected basis (Q3). **Warning sign:** postbuild FATAL after pages land.

### Pitfall 5: Flipping `PLUGINS_ENABLED` before measuring the sweep
**What goes wrong:** The plugin sweep pushes the warm 4.5–5.5h run past the 360-min
cap → the run dies BEFORE the daily history snapshot commit (unreplayable data loss
— the exact reason it was gated off). **Avoid:** D-01's measure-on-a-branch-first
protocol (Q2d).

### Pitfall 6: `loadCheckpoint()` silently resetting `processedSet`
**What goes wrong:** Even after the banned-pattern fix, if the NDJSON read shape
doesn't match the writer, the resume logic silently no-ops and every run re-scrapes
the full corpus. **Avoid:** the round-trip regression test (Q2b).

## Root cause — rate-limit-bound discovery walk

The sweep is **throughput-bound by GitHub's 5,000 REST/hr limit**, not hung:

- Processed only **~1,700 of ~7,300 repos (~23%)** in 5.5 h.
- Steady burst ~50 repos / ~1.7 min, then a **403 rate-limit wall every ~800–1,100
  repos**, each forcing a **~44-min hard wait** for the REST limit to reset
  (observed waits: 2648 s, 2599 s, 2587 s, 3006 s).
- Extrapolated full-sweep time: **~24 h** — infeasible in one 6h job, let alone
  the daily cron alongside skills + build + deploy.

The Task 1 bootstrap cache only avoids re-**fetching** known repo *content*; the
**per-repo discovery walk** (enumerate + inspect each of ~7,300 repos for
`.claude-plugin/` / `mcp` components) is what burns the budget. A cache seed
cannot fix that.

## Implication

This is exactly the failure the `PLUGINS_ENABLED='false'` gate documents
(daily-scrape.yml lines 61–75, Pitfall 5): the sweep "never finishes inside the
timeout, so the run dies at Run plugin discovery BEFORE the commit/deploy/
history-snapshot steps — losing the daily history snapshot and skipping the
deploy." Flipping the flag on main would break the daily cron.

## The real fix (future phase)

Make plugin discovery **incremental**, mirroring skills' Track 2 skip-known-IDs
pattern, and/or batch repo inspection via a single GraphQL query instead of N
REST calls per repo. Candidate levers:

1. **Incremental discovery:** persist the set of known plugin repos; each daily
   run only walks NEW/changed repos (recency-filtered `search/repositories`),
   not the whole ecosystem. Steady-state daily delta is small.
2. **GraphQL batch walk:** replace per-repo REST tree/manifest GETs with batched
   `repository(...){ object(expression:"HEAD:.claude-plugin/") }` queries to cut
   the per-repo call count (and thus rate-limit pressure) dramatically.
3. **Day-sharding fallback:** if neither lands quickly, shard the full sweep
   across N days (process repos[i] where i % N == day_of_week), accepting an
   N-day freshness lag.

Until one of these lands, `PLUGINS_ENABLED` stays `'false'`; plugin/MCP pages
ship live-but-empty (page code + bootstrap release/cache are already in place,
so re-enable is a one-line flag flip once the sweep fits).

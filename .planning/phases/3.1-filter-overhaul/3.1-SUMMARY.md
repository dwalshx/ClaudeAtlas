## What we shipped beyond the plan

The dry-run cascade surfaced infrastructure work that wasn't in the original plan but is now load-bearing:

1. **Branch-safe CI gating** — `daily-scrape.yml` publish/deploy steps gated on `github.ref == 'refs/heads/main'`. Future risky phases can dry-run on a branch without touching production. Documented in commit `7a3ed48`.
2. **Percentile-based tier assignment** — `filter.js` tier logic moved from absolute thresholds (≥90/≥70) to percentile rank (top 10% / next 30% / rest). The original "Featured ballooning to 56%" calibration debt (RECALIBRATION.md Deviation 2) was promoted from "Phase 3.6 follow-up" to "load-bearing for Cloudflare's 20k static-asset cap." Commit `d30f186`.
3. **Postbuild defense-in-depth guards** — `scripts/check-asset-sizes.js` (NEW) enforces both per-asset size (24 MiB margin under 25 MiB cap) and total file count (95k margin under 100k Workers Paid cap). Catches the "single-file-pattern doesn't scale" class of bugs at BUILD time, not at DEPLOY time. Commits `e4f2e4b` + `e2939ae`.
4. **Cost ceiling upgrade** — $12/yr → ~$102/yr (Cloudflare Workers Paid $60 + Vectorize stored-dim overage $30) to support 1M KV writes/day (needed for one-shot ~21k Listed-tier publish). Commit `46db97b`.
5. **Wrangler 4.x pin in CI** — fixes silent `run_worker_first` ignore from wrangler 3.90.0. Commit `46db97b`.
6. **`run_worker_first` extended to `/api/*`** — fixes silent F1 regression where `/api/v1/search` and `/api/log-search` were intercepted by `not_found_handling = "404-page"` before the worker could run. Bug was live for ~2 days but not user-visible until Phase 3.1.x wired the homepage to the search API. Commit `a23a1d0`.
7. **Architectural rework of homepage + /browse** — homepage no longer inlines 35k hidden SkillCards (74 MB → 149 KB). Semantic search via `/api/v1/search` replaces client-side substring filter. New `/browse` page is the SEO-link-distribution surface. Commits `590cf6d` + `2212afe` + `6d9ff55`.

## Operational debt / follow-ups (tracked but not blocking)

1. **HNSW migration for enrich + compute-similar** — current O(n²) cosine at 35k = ~25 min each. Cron-only impact; daily site updates take ~3h end-to-end. Migration trigger: catalog grows past ~50k OR daily runtime exceeds 4h.
2. **Truncated embeddings (1536 → 512 dims)** — saves ~$30/yr on Vectorize storage overage. Quality loss ~5% per OpenAI docs. Phase 3.x optimization.
3. **Tier rename Featured → Top** — Phase 3.6 work. Percentile model already in place; just a labeling change.
4. **Catalog growth past 100k** — File count guard fails at 95k, currently at ~67k after badge tier-filter. Headroom estimate: ~150% catalog growth before next file-count mitigation needed.

## Lessons learned (worth carrying into Phase 3.2)

1. **Single-file-pattern is the systemic risk at scale.** Four separate occurrences in this phase (homepage HTML, registry JSON, category page HTML, badge file count). All shared the same shape: "thing that worked at 1k records becomes a cap-buster at 35k." Phase 3.2 (plugins) should audit its inputs against this pattern before implementation.

2. **Build-time guards >> deploy-time errors.** The asset-size + file-count guards added in PR #4 and #5 would have caught the cascade in minutes instead of 5–10 min CI cycles per occurrence. New phases should add guards proactively.

3. **`run_worker_first` semantics need broader coverage.** Any new worker route added after F1 needs to be in `run_worker_first` or it'll be silently intercepted by `not_found_handling = "404-page"`. Phase 3.2's plugin API routes will need this from day one.

4. **The polymorphic envelope (Phase 3.1.2) is now genuinely necessary.** Phase 3.1.x's `/api/v1/search` already serves a unified search primitive; adding plugins/APIs/MCPs as additional entity types embedded into the same Vectorize index is the architectural shape that's already half-built.

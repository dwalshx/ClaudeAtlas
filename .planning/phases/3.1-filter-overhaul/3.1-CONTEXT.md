# Phase 3.1 — Filter Overhaul

**Status:** Planning (research complete; decisions locked)
**Authored:** 2026-05-17
**Precursor to:** Phase 3.2 (plugin scoring), 3.4 (novelty UI)
**Unblocked by:** Phase 3.0.0-3.0.2 (infrastructure trilogy complete, daily pipeline reliable)

---

## Why this phase exists

`docs/PHASE-3.0-SPEC.md` Phase 3.1 is the first user-visible product change in milestone v3.0: drop editorial gatekeeping, replace with embedding-based intelligence. The previous filter gates (`MAX_PER_REPO=2`, `MIN_STARS=10`) were calibrated for the "curated 1,078 skills" era. Phase 3.1 transforms the catalog from "curated gallery" to "comprehensive index, surface via quality scoring" — the Wirecutter model from the spec.

Research surfaced multiple corrections to the spec's algorithmic constants. See [`./RESEARCH.md`](./RESEARCH.md) — 951 lines, 8 questions, empirical evidence.

## Decisions LOCKED (from research findings)

### Decision A — Cosine duplicate threshold at 0.92 ✓ (spec validated)

Direct measurement of pair-similarity distribution in `data/skill-vectors.ndjson` shows a perfectly clean natural valley between 0.88 and 0.92 (zero pairs in the 0.89/0.90/0.91 buckets) with a dense cliff above 0.92. The spec value is empirically optimal — keep it.

### Decision B — Novelty threshold is PERCENTILE, not absolute 0.45 ✗ (spec wrong)

Random skill pairs cluster at 0.20–0.40 cosine; p95 of random pairs is 0.45 itself. The spec's "novelty > 0.45" is sitting at the noise floor — would mark virtually everything as noteworthy. Replace with **top 5% by novelty score** (percentile slice). When 3.4 ships the "New & Noteworthy" UI, the gate becomes "top 5% novelty AND Top tier quality."

### Decision C — Drop active-fork detection (DEAD CODE)

`scripts/scrape.js:462` (now in scrape-discover-repos.js too) skips git forks at discovery. Zero forks ever enter `skills-raw.json`. The active-fork logic from spec would never trigger.

**Replacement:** semantic-clone detection using existing first-commit-timestamp data:
- If two skills have cosine similarity > 0.92 AND `skill_first_commit_at` exists for both, the older one is canonical
- If the newer one has more stars (10x ratio), flag for "newer-but-popular successor" review (manual eyeball, not auto-promotion)
- Don't call GitHub's `/compare` endpoint at all — saves rate budget

### Decision D — Slug collisions are 13, not 6

The audit's "6 collisions" number was stale. Empirical re-grep of current `data/skills.json` (now 1,885 skills) shows 13 colliding slug pairs. Fix design must scale to N collisions, not hardcode 6.

**Slug rule:** `owner/skill-name` when unique; `owner/path-component-name` (use parent dir of SKILL.md) when collision. Backward compat via Worker-side 301 redirect for old colliding URLs to the canonical resolved slug.

### Decision E — Compute novelty LOCALLY, not via Vectorize ANN

Vectorize free-tier breaks the $12/yr ceiling at daily novelty-query volume across 1,885+ corpus. We already have `data/skill-vectors.ndjson` on disk (~32 MB), already loaded in memory by `compute-similar.js`. Compute novelty during that same pass:

```js
// In compute-similar.js (or new sibling script):
for each vector v:
  novelty_score = 1 - max(cosineSim(v, w) for all w != v in the index)
```

Brute-force O(n²) at n=1,885 → ~3.5M comparisons. Trivial — completes in <30 sec in Node. For corpus growth to 20k+, switch to a tiled cosine matrix or k-d tree (defer to a future phase if/when needed).

Vectorize stays in production for live `/api/v1/search` queries (the user-facing path) and for `compute-similar.js`'s top-5 nearest neighbors. Novelty just doesn't need to call it.

### Decision F — Dedup becomes the load-bearing gate

`MAX_PER_REPO=2` currently suppresses **~29,343 records (88% of raw 33k)** from reaching `skills.json`. Dropping it without dedup would explode the catalog into a mostly-duplicate mess. The 0.92 cosine dedup IS the new line of defense:

- Old chain: scrape → filter (MAX_PER_REPO + MIN_STARS + slop + body length + lang variants) → 1,078
- New chain: scrape → filter (slop + body length + lang variants) → embed → dedup (0.92 cosine) → ~5-10k canonical skills

This means **dedup MUST run before the catalog ships to users.** Pipeline ordering becomes critical (see Decision G).

### Decision G — Pipeline ordering: multi-pass

Filter and dedup can't be a single pass because dedup needs embeddings. Two passes:

1. **Filter (pass 1)** — slop blacklist, body length, lang variants, R3 merge, score, categorize. Produces `skills.json` with `is_duplicate: null`, `canonical_slug: null`, `novelty_score: null` (placeholder fields).
2. **Embed** — generates vectors for new/changed skills.
3. **Enrich (new script, pass 2)** — reads skill-vectors.ndjson, computes:
   - Pairwise similarity for dedup (sets `is_duplicate` + `canonical_slug`)
   - Novelty score per skill
   - Writes back to `skills.json` (in-place field update)
4. **Compute-similar / Upload-vectors / Mine-apis / Build / Deploy / Commit** — downstream as today.

Estimated added time: ~2-3 min for enrich step at current corpus. Well under the 10-min budget.

### Decision H — Tier thresholds stay absolute (90 / 70)

Spec uses absolute thresholds. Research found this is fine — "Top" is meant to be rare; as catalog grows from 1,885 to 5-10k, Top tier % naturally shrinks but absolute count stays meaningful. Percentile-based tiers were considered but rejected because they'd make "Top" a moving target that confuses returning users.

## Risks (must be addressed in PLAN.md)

### R1 — Recalibration explosion

Dropping MAX_PER_REPO surfaces 29k+ previously-suppressed records. If dedup undercounts (e.g., misses near-duplicates with 0.85-0.92 similarity), the catalog inflates and tier distribution skews. Mitigation: post-recalibration manual eyeball; if Featured count balloons >2x current 305, investigate.

### R2 — Local novelty O(n²) at scale

Brute-force fine at 1,885 (~3.5M comparisons). At 20k → 400M comparisons. May need to migrate to LSH or tiled matrix in Phase 3.x. Document as a known scaling cliff.

### R3 — Slug redirect map maintenance

Worker-side 301 redirect needs a map of old→new slugs. The map grows over time as collisions are discovered. Storage option: hardcoded in worker (simple, requires deploy to update), or KV/D1 (flexible but adds infra). Recommendation: hardcoded for now, revisit if redirect list grows past ~50.

### R4 — `skill_first_commit_at` coverage

Decision C's semantic-clone detection relies on `skill_first_commit_at` for tie-breaking. From earlier audit, this field was one-shot backfilled for 305 Featured skills. Need to verify coverage on the expanded catalog. If <100% coverage, fall back to `repo_created_at` for older-tie-break.

### R5 — Existing similar-skills data

`data/similar-skills.json` already has top-5 nearest neighbors per skill. If we change slug computation, the JSON's keys/values may need migration. Mitigation: regenerate similar-skills.json in same run as enrich.

### R6 — Phase 3.0 spec drift

Research found the spec's 0.45 novelty threshold and active-fork detection are both wrong. Other parts of Phase 3.0 (3.2-3.9 sub-phases) may reference these incorrect constants. Mitigation: update `docs/PHASE-3.0-SPEC.md` with corrections so 3.2+ planning doesn't repeat the errors.

## Recovery if 3.1 breaks the site

The new fields (`is_duplicate`, `canonical_slug`, `novelty_score`) are additive — existing site rendering doesn't reference them. If the dedup logic produces garbage results, the site still loads with all skills visible (just with possibly-stale tier assignments). To revert:

1. Revert the filter.js + enrich.js commits
2. Re-trigger daily-scrape (will regenerate skills.json from skills-raw.json under old rules)
3. Worker redirect map can stay (idempotent — only fires for old colliding slugs)

The 13 slug collisions are pre-existing; redirect map fixes them and is safe to ship independently.

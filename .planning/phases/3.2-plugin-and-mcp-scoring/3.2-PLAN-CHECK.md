# Phase 3.2 Plan Check — Iteration 1

## Verdict

**NEEDS_REVISION** — 3 blockers, 7 flags. The plan is structurally sound, mirrors prior-phase precedents well, and honors all 11 user decisions in spirit. ## Blockers (must fix before execution)

### B-1. Task 7 MCP small-N carve-out contradicts D-04

**Dimension:** decision_fidelity
**Plan location:** Task 7 behavior, filter-mcps.js section: "if N<10 ... assign top 10% Featured (rounded up so N=38 -> 4 Featured), next 30% Solid (~11), rest Listed".

**Issue:** D-04 explicitly says "No special-case logic for small entity_type populations. The 10/30/60 split holds even at small N." The plan introduces a small-N branch anyway. Additionally, at N=38 the guard `if N<10` never fires — so the carve-out is unreachable dead code. The stated arithmetic is also wrong: Math.ceil(0.30 * 38) = 12, not "~11".

**Fix:** Drop the N<10 branch in filter-mcps.js entirely. Apply the same percentile assignment as skills/plugins. Confirm rounding convention by reading filter.js Step 3 (likely Math.floor) and match it byte-for-byte before factoring into the shared scripts/lib/tier-assignment.js helper.

### B-2. Task 4 skill embedding-input snapshot is circular; risks re-embedding 35k catalog

**Dimension:** F1/F2 invariants + cost ceiling
**Plan locations:** Task 4 — "Skill: against committed fixture, output string MUST match snapshot of today inline logic"; Task 9 — "content_sha delta-detection unchanged: per-record sha based on buildEmbeddingInput(record) output".

**Issue:** Task 4 snapshot is the only guard against embedding-input drift, but the snapshot is written by the planner from current inline logic — circular. If today inline emits `name + " " + description` (single space) and the extracted builder emits `name + " | " + description` (pipe-spaced, mirroring plugin/mcp shape), every skill content_sha changes and the next embed-skills.js run re-embeds the entire 35k catalog. The plan asserts this will not happen but provides no enforcement beyond a self-written snapshot.

**Fix:** Task 4 verify must additionally run buildSkillEmbeddingInput against the first 10 records of live data/skills.ndjson and compare against a one-shot buildSkillEmbeddingInputLegacy helper that inlines the pre-refactor logic (kept in __tests__/ only). Any divergence fails the task. Task 9 done must add: "Re-running embed-skills.js against unchanged skills.ndjson produces ZERO new vectors (cache hit rate = 100%)." This is the only operationally meaningful guard.

### B-3. Task 13 cron mitigation lacks projection math; chosen mitigation may not fit 330-min budget

**Dimension:** requirement_coverage (DOD-12) + decision_fidelity (D-11)
**Plan location:** Task 13 Step 1 says "Compute the post-3.2 projected runtime"; Step 2 picks "Combine D + C"; Step 3 implements. No verify checks the projected runtime under D+C is < 330 min.

**Issue:** Today scheduled run hit 5h0m18s and died IN compute-similar (per CONTEXT). Adding plugin scrape (~30 min) + filter (~5 min) + embed (~3 min) + enrich (~2 min at N=4500) is ~40 min new work. 5h0m + 40min = 340 min, exceeding the bumped 330 min. The K reduction (5 -> 3) must reclaim at least 10 min to fit; the plan does not state whether 5 -> 3 actually saves that much, nor what the audit doc must contain to validate this before merge.

**Fix:** Task 13 done must include: "3.2-CRON-AUDIT.md asserts projected post-3.2 runtime <= 320 min (10-min margin) under chosen mitigation; if projection > 320 min, escalate to Option B (split workflow) before merging." Audit doc must contain a table with columns: step, pre-3.2 mean, post-3.2 projected, mitigation delta. Without this, Task 14 smoke could pass on a lucky run while production timeouts continue.

### F-2. Task 7 assumes MCPs in plugins-raw.ndjson carry entity_type=mcp_server — unverified

**Issue:** CONTEXT line 195 reports "38 MCPs" in plugins-meta.json stats but does not confirm those records are tagged entity_type=mcp_server in plugins-raw.ndjson. If tagged entity_type=plugin with a server_path field, filter-mcps.js dispatch silently matches zero.

**Action:** Task 7 done should add: "Confirmed via grep: data/plugins-raw.ndjson contains >= 30 records with entity_type=mcp_server before filter-mcps.js is exercised."

### F-3. Task 8 link-bundles.js rewrites skills.ndjson — needs atomic-write + PRESERVED_FIELDS guarantee

**Issue:** filter.js PRESERVED_FIELDS pattern assumes one writer per output file. link-bundles.js rewriting skills.ndjson after filter.js means: (a) any failure leaves skills.ndjson in undefined state if writes are non-atomic, (b) re-running filter.js alone blows away bundled_in_plugins from link-bundles.

**Action:** Task 8 should require: "link-bundles.js MUST use writeNdjsonStreaming with tmp+rename. filter.js PRESERVED_FIELDS list MUST include bundled_in_plugins so a subsequent filter.js re-run preserves link-bundles output."

### F-4. Plan does not enforce postbuild guards (24 MiB + 95k files) in any task verify

**Issue:** success_criteria mentions asset-size + file-count guards but no task runs scripts/check-asset-sizes.js. /browse.astro is already ~3MB at 35k records; mixed-type feeds may grow further.

**Action:** Add to Task 14 round-trip verifier: `npm run build && node scripts/check-asset-sizes.js` as a post-build assertion.

### F-5. Task 12 CLAUDE.md update misses the Data model section

**Issue:** CLAUDE.md Data model section currently describes PluginExtra/McpExtra as "ready for 3.2+". Task 12 updates Project structure but not Data model. Post-3.2 readers will see stale "ready for 3.2+" notes against shipped extras.

**Action:** Task 12 must also update CLAUDE.md Data model section to mark Plugin/MCP extras as "shipped 3.2" with the final expanded field lists from Task 1.

### F-6. Task 12 banned-patterns allowlist additions are conditional and vague

**Issue:** Task 12 says "Add allowlist entries for any new sidecar JSON writes... e.g., data/plugin-stats.json if filter-plugins.js writes one; data/bundle-graph.json if link-bundles produces one." But Task 7 writes to existing pipeline-stats.json (no new file) and Task 8 says link-bundles.js rewrites NDJSON only. Allowlist delta is likely zero.

**Action:** Task 12 done should assert: "Allowlist delta documented (likely zero new entries); banned-patterns lint clean against full diff."

### F-7. Task 5 mcpRecipe stub status should be explicit per D-10

**Issue:** D-10 lists McpRecipe as one of the ~50% more work components. Task 5 delivers it but as a stub shape with empty discover() generator. The plan should state explicitly that recipes are SHAPE-CONFORMANT STUBS — production discovery still lives in scrape-plugins.js — so D-10 coverage is not mis-read as functional discovery.

**Action:** Task 5 done should clarify: "Recipes are shape-conformant stubs — discover() is empty generator; real discovery lives in scrape-plugins.js. Registry registration enables future tooling that introspects recipes[plugin] without changing the production pipeline."

## Phase Boundary

This phase adds **plugin** and **mcp_server** entity types to the ClaudeAtlas catalog pipeline. After this phase ships:

- `data/skills-latest` release asset becomes the unified entity asset (skills + plugins + mcp_servers).
- `/api/v1/search` returns mixed-type results; the existing `?type=` filter on the worker triad starts producing real plugin and MCP results.
- Existing feeds (`whats-new.json`, `trending.json`, `notable.json`) carry plugin and MCP entries alongside skills, distinguished by `_claudeatlas.type_chip`.
- The daily-scrape cron produces fresh plugin + MCP data alongside skill data.
- Skill records gain a `bundled_in_plugins: string[]` field; plugin records gain `bundled_skills: string[]`, `bundled_agents: string[]`, etc.

**Out of scope (deferred to later phases):**

- Plugin detail pages at `/plugins/[slug]/` — Phase 3.3.
- MCP detail pages at `/mcp/[slug]/` — Phase 3.3 (or later).
- Plugin browse page at `/plugins/` — Phase 3.3.
- Homepage redesign with separate Top Skills / Top Plugins sections — Phase 3.5.
- Recalibrating skill `quality_score` to include `bundled_in_featured_plugins` signal — Phase 3.4 or later.
- `Featured → Top` rename throughout — Phase 3.6.
- /trends page surfacing daily snapshot deltas across types — Phase 3.9.

**Why this phase, why now:**

Phase 3.1.2 shipped the polymorphic envelope specifically to make this phase a "add files, don't refactor" exercise. Phase 3.1.3 wired the feed infrastructure with type-chip support already designed in. Phase 3.1.4 (just shipped) ensures filter.js writes v2 EntityRecord shape so plugins/MCPs can join the same data stream cleanly. All prior infrastructure built toward this.

<decisions>
## Implementation Decisions

### Entity Definition

- **D-01: What IS `entity_type: 'plugin'`?**
  A plugin is anything discovered via plugin.json OR listed in a marketplace.json. Marketplaces are catalog metadata (not separate entity_type); a single plugin appearing in multiple marketplaces deduplicates via cosine ≥ 0.92 (same as skill dedup). The 11 "neither plugin.json nor marketplace" false-positive repos in the April scrape get filtered out by the `HAS_MANIFEST_OR_LISTING` gate.

- **D-10: MCP servers as separate `entity_type: 'mcp_server'`**
  Per the typedef stub (`src/lib/types.d.ts` lines 117-124), MCP servers are conceptually distinct from plugins. Phase 3.2 ships them as a third entity type alongside skills and plugins. 38 known MCP-server repos in current data (today's scrape). McpExtra fields: `server_path`, `manifest`, `readme_markdown`, `tools[]`, `transport` ("stdio" | "sse" | "streamable-http" | null).

  Implication: ~50% more Phase 3.2 work (separate McpRules pack, McpScorer, McpRecipe, MCP-specific embedding-input builder, McpExtra typedef expanded from stub). Accepted deliberately.

### Bidirectional Plugin↔Skill Graph

- **D-02: Skill records know what plugins bundle them; plugins know what they bundle.**
  Add to `SkillExtra` (and `EntityCommon` where it makes sense for cross-type):
  - `bundled_in_plugins: string[]` (array of plugin slugs)

  Add to `PluginExtra`:
  - `bundled_skills: string[]`
  - `bundled_agents: string[]`
  - `bundled_commands: string[]`
  - `bundled_hooks: string[]`
  - `bundled_mcp_servers: string[]`

  Data shape only in Phase 3.2. Display rendering deferred to Phase 3.3 (plugin detail pages). Scoring-signal use (e.g., "bundled in N Featured plugins" boosts skill quality_score) deferred to Phase 3.4 or its own mini-phase — needs separate calibration to avoid recalibrating the existing skill tier composition.

### Scoring

- **D-03: Plugin & MCP scoring formula = same 7-signal as skills, with 1 swap.**
  Replace skill-specific "Frontmatter" (20%) with type-specific "Manifest completeness" (20%):
  - **Plugin manifest completeness:** has description (≥ 50 chars) + version + author + license + ≥ 1 keyword
  - **MCP manifest completeness:** has description + transport declared + ≥ 1 tool listed

  All other 6 signals (Stars 20%, Recency 20%, Documentation 15%, Issue health 10%, License 10%, Description 5%) match skill formula. Keeps tier semantics consistent across entity types — a user sees "Featured" and it means the same kind of curation rank.

  Plugin & MCP scorers live in `scripts/lib/scorers/plugin.scorer.js` and `scripts/lib/scorers/mcp.scorer.js`. Filter dispatch via existing scorer registry (`scripts/lib/scorers/index.js`).

- **D-04: Same percentile tiers as skills.**
  Top 10% → Featured. Next 30% → Solid. Remainder → Listed. At projected ~4,500 admitted plugins → ~450 Featured plugins; at ~38 admitted MCP servers → ~4 Featured MCPs.

  No special-case logic for small entity_type populations. The 10/30/60 split holds even at small N. If it starts producing weird outcomes at small N (e.g., 4 Featured MCPs feels like too few), revisit in Phase 3.4 recalibration.

### Filter Gates

- **D-05: Plugin + MCP filter gates**
  Per `scripts/lib/filter-rules/` registries, dispatching on entity_type:
  - `MIN_DESCRIPTION_LENGTH: 50` chars (manifest description)
  - `HAS_MANIFEST_OR_LISTING` — must have plugin.json OR be in a marketplace.json
  - `COMPONENT_FLOOR: ≥ 1 component` for plugins (filters ~33% empty scaffolds → reduces ~7k discovered to ~4.5k admitted)
  - For MCPs: `HAS_TRANSPORT_DECLARED` + `≥ 1 tool listed` (loose; only 38 records total)
  - Slop name blacklist (shared `common.rules.js`)
  - Language-variant dedup (shared)
  - **No MIN_STARS** (Phase 3.1 precedent: star gate is anti-curation)

### Slug Strategy

- **D-08: Slug = `owner/plugin-name` (mirror skill convention).**
  Same `assignSlugs()` path-aware logic from Phase 3.1. When a plugin and skill share a slug pattern (e.g., owner has both `claude-skills/SKILL.md` and a plugin.json named the same), `assignSlugs()` resolves collisions automatically — plugin wins the short form, skill falls back to `owner/repo/skill-name`. The collision logic is entity-type-agnostic by design; this just exercises an existing path.

  URL pattern: `/skills/owner/name/` and (deferred to 3.3) `/plugins/owner/name/`. Worker route lookup uses entity_type metadata from KV to disambiguate at request time.

### Embedding Input

- **D-09: Plugin embedding input = name + description + manifest keywords (~200 chars).**
  Lean, matches skill embedding-input shape (which is name + description + frontmatter snippet). README explicitly NOT included — adds ~5x token cost for marginal signal gain given README quality variance.

  MCP embedding input shape: name + description + transport + comma-joined tool names. Capture the "what does this MCP do" essence.

  Implementation lives in `scripts/lib/embedding-input/plugin.js` and `mcp.js` (new files, registered in existing `scripts/lib/embedding-input/index.js` registry stub).

  Cost projection: ~4,500 plugins + ~38 MCPs ≈ 4,540 new embeds at ~200 chars each ≈ ~$0.01 one-time. Negligible.

### Feeds

- **D-06: Feeds are mixed across entity types.**
  Existing `/feed/whats-new.json`, `/feed/trending.json`, `/feed/notable.json` carry skill, plugin, and MCP entries together. Distinguished by:
  - `_claudeatlas.type_chip: "skill" | "plugin" | "mcp_server"`
  - Worker filter passthrough: `?type=plugin` already supported (Phase 3.1.3)

  Defer separate `/feed/plugins.json` / `/feed/mcps.json` to Phase 3.x if subscriber demand emerges. Don't speculate.

### Site Surfacing (Scope Anchor)

- **D-07: Phase 3.2 ships data infrastructure only — no new pages.**
  - Plugins exist as EntityRecord entries
  - `/api/v1/search?type=plugin` returns plugin results with `source` field
  - `/api/v1/whats-new?type=mcp_server` returns MCP-only feed
  - `/skills-registry.json` envelope unchanged (renderable subset stays Featured + Solid skills only — plugins/MCPs not added to the registry endpoint in this phase; deferred to 3.3 or 3.5)
  - Schema-org `DataCatalog` markup on the homepage doesn't change in this phase
  - No `/plugins/` or `/mcp/` pages

### Daily-Scrape Integration

- **D-11: Wire plugin + MCP discovery into daily-scrape.yml.**
  Add steps after Track 2:
  - **Scrape plugins** (`scrape-plugins.js`) — ~30 min at current GitHub API quota
  - **Filter plugins** (`filter.js` dispatching by entity_type, OR new `filter-plugins.js` — defer to planner) → writes plugin records to skills-latest via the same `writeNdjsonStreaming` + `_header` path Phase 3.1.4 added.
  - **Embed plugins** (delta-only via content_sha, same pattern as embed-skills.js)
  - **Enrich plugins** (skip dedup for MCPs — population too small; do dedup for plugins)
  - Publish step uses the same `skills-latest` release asset (which becomes a heterogeneous file once plugins land — F2 explicitly designed `_header.entity_type = null` for mixed-type files per `scripts/lib/entity-version.js#buildHeader`).

  Cron timeout concern: today's scheduled cron hit the 5h workflow timeout. Adding plugin discovery + filter could push runtime past 5h. **Mitigation: planner must include a cron-runtime audit task.** Options: HNSW migration for compute-similar (skill-side optimization that frees budget); split plugin discovery to a separate workflow; reduce K in compute-similar; etc.

### Claude's Discretion

- Whether plugin filter logic lives in `scripts/filter.js` (dispatched by entity_type) or a separate `scripts/filter-plugins.js` and `scripts/filter-mcps.js` — planner decides based on which keeps filter.js maintainable.
- Whether MCP-specific enrich (dedup) is skipped entirely at this population (n=38, dedup overhead > benefit) — planner decides.
- Exact field shape of `PluginExtra` and `McpExtra` beyond the stubbed fields — planner may extend per scraper data.
- Order of recipe-engine wiring vs writing the plugin scorer — planner decides; both required this phase.

### Folded Todos

None — no pending backlog items relevant to this scope.

## Existing Code Insights

### Reusable Assets

- **`upcastRecord` + `buildHeader`** (`scripts/lib/legacy-skill-reader.js`, `scripts/lib/entity-version.js`) — Established v2 write pattern from Phase 3.1.4. Plugin and MCP filters write via identical mechanism (`writeNdjsonStreaming(path, records, { header: buildHeader('plugin') })`).
- **`assignSlugs` path-aware** (`scripts/lib/slug.js`) — Already handles cross-type collisions when slug shape matches.
- **`scorer/filter-rule/recipe registries`** (`scripts/lib/{scorers,filter-rules,recipes}/index.js`) — Phase 3.1.2 stubs ready for plugin + mcp module registration; "add files, don't refactor" promise.
- **`serveFeed` worker handler** (`worker/index.js`) — Filter passthrough already supports `?type`; no worker changes needed for type filtering.
- **`generate-feeds.js`** — Already groups by date/score, adds `_claudeatlas` extension. Need to: load entities (not skills), set `type_chip` per-entity_type, ensure all 3 feeds include all 3 types.
- **`embedding-input/` directory** — Phase 3.1.3 left this directory not extracted; plugin work is the natural moment to formalize the registry (one file per entity_type, registered in `index.js`).
- **`PRESERVED_FIELDS` array in filter.js** — Carries enrichments across daily runs. Plugin filter needs its own preserved-fields list (probably `is_duplicate`, `canonical_id`, `novelty_score` — same as skills).

### Established Patterns

- **Percentile tier assignment** (`scripts/filter.js` Step 3, lines ~280-310): top 10% / next 30% / rest. Apply same logic to plugin and MCP scorer outputs, dispatched per entity_type.
- **Content_sha for embed delta-detection** (`scripts/embed-skills.js`): hash of embedding-input string. Identical pattern for plugins/MCPs — `computeContentSha(buildEmbeddingInput(entity))`.
- **Filter PRESERVED_FIELDS pattern**: enrichments survive failed enrich runs. Plugin/MCP filters need same defensive copy.
- **Tier-filter badge generation** (Phase 3.1's PR #5): only Featured + Solid get embeddable badges. Plugins/MCPs follow same pattern in `scripts/generate-badges.js` (extended for entity_type).
- **Branch-safe CI dispatching** (Phase 3.1 PR #5 + 3.1.4): plugin filter PR can dry-run safely via `gh workflow run daily-scrape.yml --ref <branch>` because publish/deploy steps are gated to `main`.

### Integration Points

- **`writeNdjsonStreaming(OUTPUT_PATH, records, { header: buildHeader(...) })`** — Plugin + MCP filters write to same `data/skills.ndjson` OR separate files (planner decides; if separate, the cutover/publish step changes).
- **Vectorize metadata** — `entity_type` already in the embed-skills.js metadata payload. Plugin/MCP upload-vectors.js extends naturally.
- **`worker/index.js`** filter triad — `?type=plugin` parsing already in place (Phase 3.1.2 T8). No worker changes needed for filtering; new entity_type values just start returning results.
- **`scripts/embed-skills.js`** — Per-skill embed loop. Plugin + MCP equivalents either: (a) extend this script with type dispatch, or (b) create `embed-plugins.js` + `embed-mcps.js`. Recommend (a) for consistency; planner decides.
- **`scripts/enrich.js`** — Currently skills-only. Plugin enrich (dedup + novelty) likely reuses same brute-force O(n²) cosine logic at smaller N (~4,500). MCP enrich probably skipped (n=38 too small for meaningful dedup).
- **`daily-scrape.yml`** — New steps land between existing "Track 2 (Discovery)" and "Filter" steps OR as parallel jobs. Planner decides ordering vs runtime budget impact.

### Constraints from Operational Reality

- **5h cron timeout was hit on 2026-05-30.** Today's scheduled run was cancelled at exactly 300 min. Adding plugin discovery + filter could push past this. Mitigation options for planner: (a) HNSW migration for compute-similar (frees ~70 min of cron time), (b) split plugin scrape to separate workflow, (c) reduce K, (d) defer some compute-intensive steps to weekly.
- **Workers Paid cost ceiling ~$102/yr** — Plugin adds: ~4,500 new Vectorize stored dims × 1536 = ~7M dims × $0.05/M = ~$0.35/mo. Negligible.
- **Cloudflare Static Assets file count cap 95k** — Plugin badges (if generated for Featured+Solid plugins) = ~1,800 SVG files. Combined with existing 49,841 → ~52k. Well under cap.

# Phase 3.1.2 — Polymorphic Entity Envelope (F2)

## Why this phase exists

The current data model assumes every record is a "skill" with a flat field
layout. The project's stated direction includes at least three more entity
types (plugins, MCPs, frameworks-as-tags) plus an open-ended "whatever weird
artifacts emerge." The current schema doesn't accommodate them without
either (a) field accretion (skill records grow plugin-specific null fields
and vice versa, getting messier over time) or (b) repeated refactor passes
for each new entity type.

This phase reshapes the data model ONCE so all future entity types are
mechanical add-ons.

## Goal

Every record on disk and in memory conforms to a discriminated `EntityRecord`
shape with:
- A top-level common-fields band shared by all entity types
- An `entity_type` discriminator field
- A typed `extra` blob for per-entity-type fields

After this phase lands:
- Adding a new entity type means: new scraper recipe + new filter rules +
  new `extra` typedef + new page template. No core schema or pipeline
  changes required.
- Search, browse, novelty scoring, and dedup all work across entity types
  uniformly.

## Scope (must-haves)

1. **`EntityRecord<extra>` TypeScript type** with discriminated union over
   `entity_type`. Common fields: `id`, `slug`, `name`, `description`,
   `entity_type`, `tags[]`, `quality_score`, `quality_tier`,
   `repo_full_name`, `repo_stars`, `repo_url`, `repo_pushed_at`,
   `repo_owner_type`, `repo_owner_avatar`, `body_length`, `content_sha`,
   `scraped_at`, `is_duplicate`, `canonical_slug`, `novelty_score`. Plus
   `extra: SkillExtra | PluginExtra | MCPExtra | ...`. See Research §E
   "Proposed entity envelope" for the detailed shape.

2. **`tags[]` replaces `category` as the discovery axis.** Skills can carry
   tags derived from frontmatter, README inference, and embedding clusters.
   Categories become an emergent property of tag clustering, not a hardcoded
   field. **This is the change that enables frameworks-as-tags**
   (Q3 decision: frameworks like Hermes/GSD/Org OS become `framework:gsd`
   tags attachable to any entity, not a separate entity type).

3. **Migration of existing skill records** to `EntityRecord<SkillExtra>`
   shape. Every `body_markdown`, `has_name`, `has_description`, etc. moves
   into `extra`. `category` field becomes a tag `category:ai-automation`
   for backward compatibility during transition; can be dropped in 3.6.

4. **All consumers updated to the new shape:** `src/lib/skills.js` (now
   `src/lib/entities.js`?), every Astro page template, the worker, the
   build helpers, `scripts/filter.js`, `scripts/enrich.js`, the embed
   pipeline metadata. Plan-check focus: did we miss any consumer?

5. **Scraper recipe abstraction.** Refactor `scripts/scrape.js` into a
   generic engine + per-entity-type recipe files. Skill recipe is the
   first implementation; plugin recipe lands in 3.2. Recipe interface:
   `{ entity_type, discovery_query, parse_fn, extract_extra_fn,
   id_strategy }`. The engine handles HTTP, ETag caching, rate limiting,
   checkpointing.

6. **Filter rule packs per entity type.** Refactor `scripts/filter.js`
   similarly. Common gates (min-stars, slop blacklist, language variants,
   placeholder-name rejection) live in a shared module; entity-type-specific
   gates live in rule packs. Skill rule pack is the first implementation.

7. **Search rank normalization across entity types.** Per-type
   `quality_score` is calibrated separately (a "Top tier" skill and a
   "Top tier" plugin are quality-equivalent within their type). Search
   results across types need a comparable score. Recommendation in
   Research §E "Search ranking" — recommend the planner reads that section
   carefully and produces a concrete formula in the plan.

8. **Backwards-compatible reader for old JSON-array `skills.json`.** During
   migration, the loader must handle both old shape and new shape. Once F2
   is verified, the old-shape support is removed in a follow-up cleanup
   commit.

## Out of scope (explicit non-goals)

- Implementing plugin/MCP/framework scrapers — F2 only delivers the
  framework; entity-specific scrapers are 3.2 and beyond
- Site-side rendering of plugin/MCP pages — Phase 3.3
- Categorization redesign beyond the category-to-tag migration —
  Phase 3.4+ can refine tagging heuristics
- ANN enrich — Phase 3.1.3 (F3)
- Filter gate changes — Phase 3.1-new

## Locked decisions

- **Q2 (envelope aggressiveness):** FULL discriminated union shape.
  User-decided 2026-05-17. Pay it once now, save 3.2/3.3/future-MCP
  the schema-churn tax.
- **Q3 (frameworks):** TAG-BASED. Frameworks like Hermes, GSD, Org OS,
  BMAD become `framework:gsd` style tags attachable to any entity.
  No `entity_type: "framework"` — frameworks are methodologies, not
  artifacts. User-decided 2026-05-17.
- **Q5 (plan-check):** mandatory plan-check pass before execution starts.
  Plan-check focus: "did F2 miss any consumer of the old skill shape?
  does the new shape break any Astro page template? does the search
  rank formula make sense across types?"

## Risks

- **R1: Astro static-site-gen with discriminated union types.** Astro's
  TypeScript inference may struggle with discriminated unions in page
  templates. **Mitigation:** smoke task verifies a sample Astro page
  reads `entity.entity_type === 'skill' && entity.extra.body_markdown`
  with full type inference before the migration spreads.
- **R2: Tag explosion.** Free-form tags can produce thousands of tags
  with low individual signal. **Mitigation:** in this phase, only the
  category-to-tag migration is mechanical (8 categories → 8 tags). New
  tag sources (frontmatter, README inference, clustering) are deferred
  to 3.4+. The schema supports them; this phase doesn't populate them.
- **R3: Search ranking is genuinely hard cross-type.** Recommend the
  plan ships a simple formula (e.g., `quality_tier_rank * tier_weight +
  log(stars) * star_weight + embedding_similarity * sim_weight`) as a
  v1 and accepts that calibration is an empirical exercise across the
  first month of real query logs.
- **R4: Backward-compat reader complexity.** Reading both old-shape and
  new-shape during migration risks silently mishandling edge cases.
  **Mitigation:** version-stamp the data file (`schema_version: 2` at
  the top), and refuse to load unrecognized versions explicitly.

## Verification protocol

- All Astro pages render correctly against new-shape data (sample check:
  at least 1 page per entity_type, at least 5 skill pages)
- Search across mixed-type data returns ranked results (only skills in
  F2; plugins/etc. land later)
- `tags[]` array populated correctly on every record (at minimum,
  `category:*` tag derived from old category field)
- Existing 3.0.x pipeline still runs end-to-end on the new shape
- Site loads under 2s on home + a sample skill page + a sample tag page
  (assuming tag pages exist; they may be 3.4+)
- No regression in semantic search quality (compare query results
  before/after F2 on a fixed test query set)

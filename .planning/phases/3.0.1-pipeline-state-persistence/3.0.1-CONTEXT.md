# Phase 3.0.1 — Daily Pipeline State-Persistence Architecture

**Status:** Planning (research complete, decisions locked)
**Authored:** 2026-04-27
**Precursor to:** Phase 3.0 sub-phases (3.1–3.9)
**Replaces:** the broken Track 2 + filter steps disabled in 3.0.0 stopgap commit `7ae2756`

---

## Why this phase exists

Phase 3.0.0 shipped a sound architecture (Track 1 / Track 2 split) but the implementation hit four interaction bugs the planner didn't catch:

1. **The big one — `pushed:>` doesn't filter on code search.** Verified via [GitHub's searching-code docs](https://github.com/github/docs/blob/main/content/search-github/searching-on-github/searching-code.md): code search supports `language`, `repo`, `path`, `extension`, `filename`, `org`, `user`, `size`, `in`, `boolean operators`. It does **NOT** support `pushed:`, `created:`, `updated:`, or `sort:`. Our 3.0.0 incremental "filter" was either silently ignored or treated as text content. That's why narrowing was only ~5%.
2. V8's 512 MiB string limit on `JSON.stringify` (caches grow past it; saveETagCache crashed in CI — fixed `82cc7ab`).
3. `skills-raw.json` (~295 MB) is gitignored but the incremental skip-known-IDs logic NEEDS it on the runner.
4. ETag cache hit rate is low across multi-day windows because GitHub's repo-metadata etag changes whenever any displayed field changes (stars/forks/issues tick up daily on active repos).

We're currently in stopgap (Track 1 only on daily; Track 2 + filter + weekly disabled per `7ae2756`).

Research surfaced two platform changes Claude's training missed:
- **GHA cache 10 GB cap removed Nov 20, 2025.** No per-repo size ceiling; LRU + 7-day inactive eviction only. ([changelog](https://github.blog/changelog/2025-11-20-github-actions-cache-size-can-now-exceed-10-gb-per-repository/))
- **304 conditional responses don't count against the primary REST rate limit.** ETag cache is more leverage-positive than 3.0.0 modeled. ([best-practices docs](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api))

Full research: [`./RESEARCH.md`](./RESEARCH.md) (1,154 lines, 10 questions answered with citations).

## Architecture decisions (LOCKED)

These three decisions were the load-bearing open questions from research. Locked here; planner builds against them.

### Decision A — Discovery via repository search (NOT code search)

**The change:** Track 2 discovery moves from `/search/code?q=filename:SKILL.md` to `/search/repositories?q=topic:claude-skills+pushed:>{cutoff}` (and other relevant topics).

For each candidate repo from the topic search, enumerate SKILL.md files via the trees endpoint (`GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1`). The trees endpoint supports conditional GET (304 free), so warm runs are cheap.

This is the same pattern used by pkg.go.dev and similar large-corpus indexers (per RESEARCH.md Q2).

**Why not the alternatives:**
- ❌ `sort:updated` on code search + early termination — `sort:` not supported on code search either (RESEARCH.md Q3)
- ❌ Stay with code search + skip-known-IDs only — ignores the underlying "filter doesn't filter" bug; parse step still fetches every candidate

**Topics to seed the search with** (initial set; planner refines):
- `topic:claude-skills`
- `topic:claude-code`
- `topic:claude-skill`
- `topic:agent-skills`
- `topic:claude-plugin`
- Any topic ClaudeAtlas's Phase 1.5 topic-search currently uses (planner reads `scripts/scrape.js` `searchByTopics` for the existing list)

**Long-tail safety net:** weekly Sunday full sweep continues to use `/search/code` (no recency filter; full corpus enumeration) as the safety check that catches any SKILL.md file that isn't in a topic-tagged repo. Accepts that this hits the 6h platform cap; the bootstrap cache pattern means partial progress isn't lost across weekly runs.

### Decision E — skills-raw.json: GHA cache + release-asset bootstrap

**Storage tier:** GHA cache, with a one-shot bootstrap workflow that seeds it from a release asset.

**Pattern:**
1. **Release asset:** `skills-raw-bootstrap` release containing `data/skills-raw.json` (~295 MB). Persistent fallback. Refreshed manually after major schema migrations.
2. **GHA cache:** key `skills-raw-${{ github.run_number }}`, restore-keys `skills-raw-`. Daily/weekly workflows restore at start, save at end with `if: always()` (where the platform-cap caveat doesn't apply because Track 2 incremental fits well under 6h with the new design).
3. **Bootstrap workflow:** `bootstrap-skills-raw.yml` (mirrors `bootstrap-etag-cache.yml`). One-shot via `workflow_dispatch`. Downloads the release asset, calls `actions/cache/save@v4` with the right key prefix.

**Why not alternatives:**
- ❌ Don't persist (rebuild each weekly run from scratch) — daily filter step needs it; can't be regenerated cheaply on demand
- ❌ Commit to git — exceeds 100 MB single-file push limit
- ❌ Cloudflare R2 — would work but adds a new infra surface; GHA cache is in-band and free

GHA cache 10 GB cap is gone (per RESEARCH.md Q4); 295 MB is comfortable. 7-day inactive eviction is mitigated by the daily access pattern (every daily run touches the cache).

### Decision G — Track 1 stays REST (no GraphQL migration this phase)

REST Track 1 already works, finishes in <5 min cold and <1 min warm. GraphQL batched 100-alias queries would reduce ~826 requests to ~9 — but Track 1 is already well within budget.

**Defer GraphQL Track 1 to a Phase 3.0.x optimization** when the corpus grows to 20k+ during Phase 3.0 itself. Keeps 3.0.1 scope tight and risk low.

## Risks (must be addressed in PLAN.md)

### R1: Topic-search recall is incomplete

`/search/repositories?q=topic:X` only finds repos that have explicitly tagged the topic. SKILL.md files in repos without these topics are missed. The current code search catches them.

**Mitigation:** weekly Sunday `/search/code` full sweep IS the safety net. Anything missed by topic search on Monday gets discovered Sunday at the latest. RESEARCH.md Q8 documents this trade-off.

### R2: Topic list maintenance

If a new community standard topic emerges (e.g., `claude-cookbook`), our discovery silently misses it until we add it. Need a process for topic-list expansion.

**Mitigation:** weekly Sunday code search catches anything topic search misses; if we see weekly discovering many "new" skills the daily missed, that's a signal to add a topic. Document in CLAUDE.md.

### R3: Trees endpoint per-repo cost

For each topic-search candidate, we fetch its tree to find SKILL.md files. ~100-500 candidates/day × 1 tree fetch each = 500 max. Well under 5000/hr. ETag-supported (304 if unchanged) so warm runs are nearly free.

**Mitigation:** verify trees-endpoint ETag behavior in research-spike; if not reliably 304, bound the number of trees-fetches per run.

### R4: skills-raw.json grows unbounded

Track 2 discovery keeps adding entries. Currently 295 MB / 33k entries ≈ ~9 KB per entry (mostly the truncated body_markdown). Growth: ~100-500 new entries/day × ~9 KB = ~5 MB/day. Steady state: file grows linearly forever.

**Mitigation:** acceptable for Phase 3.0.1. Phase 3.x can add archive/eviction if needed (e.g., drop entries that haven't been seen in any scrape for 90 days). Document in CLAUDE.md as known growth.

### R5: Bootstrap-from-release-asset failure

If the release asset is deleted accidentally, the cache can't be re-bootstrapped without re-uploading from a local copy.

**Mitigation:** keep the release named `skills-raw-bootstrap` permanent (don't delete after first use). Document the recovery procedure in MORNING-CHECKLIST + CLAUDE.md.

### R6: Smoke seed false confidence

A 10-repo seed validates code paths but not scale. Bugs that only appear at 30k candidates (e.g., V8 string limit, rate-limit math) won't be caught locally.

**Mitigation:** smoke seed catches what it can. CI integration test on production corpus is the real validator. Don't pretend smoke covers scale issues.

If a new bug surfaces during 3.0.1 execution:
1. Stopgap is already deployed (`7ae2756`). Daily Track 1 still works.

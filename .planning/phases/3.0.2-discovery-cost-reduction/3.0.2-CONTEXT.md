# Phase 3.0.2 — Discovery cost reduction

**Status:** Planning (gap closure for 3.0.1)
**Authored:** 2026-05-06
**Precursor to:** Phase 3.1 (still blocked by daily pipeline reliability)

---

## Why this phase exists

Phase 3.0.1 shipped the architecturally correct discovery (repo search via `topic:X pushed:>{cutoff}` + skills-raw cache + bootstrap pattern). Six daily runs since (4/30 → 5/5) have all been **cancelled at the 90-min job timeout**. Site data hasn't moved since 2026-04-29.

Diagnosed via direct CI log inspection of run `25366158712`:

| Window | Repos | Time | Inferred cost |
|---|---|---|---|
| 0–450 (warm) | 450 | ~7 min | ~64 repos/min, mostly tree-only |
| 450–500 (mega-repo zone) | 50 | **58 min** | 5,099 "updated" content fetches → ~100 fetches/repo + 1-hour rate-limit reset |
| 500–550 | 50 | ~1 min | back to fast post-reset |

The 58-min stall is the smoking gun.

## Bugs (locked, in priority order)

### Bug 1 — Wasteful re-fetch of unchanged content (LOAD-BEARING)

`scripts/scrape-discover-repos.js:317-321` skip logic uses a 24h age check on `existing.scraped_at`:

```js
if (existing && existing.scraped_at) {
  const ageHr = (Date.now() - Date.parse(existing.scraped_at)) / 3600_000;
  if (ageHr < 24) continue;
}
```

After the first run, every `scraped_at` is >24h old, so every subsequent daily run re-fetches every SKILL.md content body — even if the file hasn't changed. Combined with mega-repos (hundreds of SKILL.md files each), this exhausts the 5000/hr GitHub API budget before the run finishes.

**Fix:** GitHub's trees endpoint (`GET /repos/{owner}/{repo}/git/trees/{branch}?recursive=1`) returns a `sha` for every blob. That sha is content-derived and stable across pushes when the file body hasn't changed. We already fetch the tree once per repo (ETag-friendly). Use the per-blob sha to detect actually-unchanged content WITHOUT a content fetch.

In `listSkillPaths`, change return shape from `Array<string>` to `Array<{path: string, sha: string}>`. Then in the per-skill loop, compare `blobSha === existing.content_sha`. If equal, skip the fetch entirely.

Expected impact: ~95% reduction in content-fetch volume after first run. Mega-repo 58-min stalls disappear.

### Bug 2 — No per-repo SKILL.md file cap

When a mega-repo (e.g., awesome-list aggregator) contains hundreds of SKILL.md files, all are fetched. But `scripts/filter.js:CONFIG.MAX_PER_REPO=2` caps each repo to 2 skills in the final `skills.json`. Over-fetching is wasted work that monopolizes rate budget.

**Fix:** Add `CONFIG.MAX_FILES_PER_REPO = 50` to `scripts/scrape-discover-repos.js`. After `listSkillPaths` returns paths for a repo, sort by path (deterministic), slice to first 50, log warning when truncating.

50 cap leaves headroom for the filter to pick its 2; mega-repos stop monopolizing budget.

### Bug 3 — Track 1 etag invalidation (DOCUMENTED, NOT FIXED)

Track 1's per-repo `GET /repos/{owner}/{repo}` etags invalidate daily because stars/forks/issues tick up. Track 1 burns ~500-800 fresh requests every day before Track 2 starts. Acceptable when Bug 1 is fixed (Track 2 leaves plenty of budget). Document in CLAUDE.md as known cost. Future GraphQL migration (research finding from 3.0.1) addresses if it ever becomes binding.

## Risks

### R1 — Smoke harness compatibility

`scripts/scrape-smoke.js` imports `listSkillPaths` (3.0.1 Task 4). The new return shape may break it. Mitigation: Task 1 audits scrape-smoke.js usage and updates as needed in the same commit (or surfaces if a separate fix is required).

### R2 — content_sha validity

`content_sha` for existing entries was set during their initial fetch from the contents API (`data.sha`). The trees endpoint returns blob sha for the same blob. **Are these the same value?** GitHub docs and standard git behavior: yes, both are git's blob SHA-1 of the file content. Verified by spot-checking an existing skill record's content_sha vs the corresponding tree blob sha if needed.

If they happen to differ in some edge case, the comparison falls through to a fetch (false negative — we re-fetch unnecessarily). No incorrectness risk; only wasted work. Not fatal.

### R3 — Large-tree truncation handling

Existing code already warns on `data.truncated`. Preserve that. Apply MAX_FILES_PER_REPO cap AFTER truncation handling so we get a deterministic top-50 from whatever the tree returned (truncated or not).

### R4 — content_sha missing on legacy records

Some early skills-raw.json entries may lack `content_sha` (if scrape.js didn't always set it). Skip-known logic must handle `existing.content_sha === undefined` gracefully — fall through to fetch.

### Locked Decisions

#### D-01: Two entity types, `api` and `dataset`
Not one `data_feed` type. Extra shapes, scorers, sources and pages differ as much as skill vs plugin. Shared pieces are the `access` block and the nav section (4.3). Add both to the `EntityType` union, the `EntityRecord` discriminated union, `scorers`, `builders`, `rulePacks`, and the recipe registry.

#### D-02: `origin` on EVERY record; `repo_*` nullable only for non-GitHub origins
```ts
origin: {
  kind: 'github' | 'registry' | 'portal' | 'manual';
  source: string;        // 'github' | 'apis.guru' | 'data.gouv.fr' | 'huggingface' | 'data.gov' | ...
  source_id: string;     // native id in that source (repo_full_name for github)
  source_url: string;    // where the record was read (repo_url for github)
  also_listed_in: string[];
};
home_url: string;        // repo_url for github-origin records
docs_url: string | null;
```
The upcaster fills `origin = { kind: 'github', source: 'github', source_id: repo_full_name, source_url: repo_url, also_listed_in: [] }`, `home_url = repo_url`, `docs_url = null` for skill/plugin/mcp_server so the shape stays uniform and no existing consumer has to branch. For `api`/`dataset`, `repo_*` fields are `null` (not `''`/`0`) when no GitHub repo is known; when one is known (e.g. an APIs.guru `x-origin` pointing at GitHub) they populate normally. Types: `repo_*` become `T | null` on `EntityCommon` with a doc comment that they are non-null for github-origin records; a test asserts the upcaster never emits null `repo_*` for skill/plugin/mcp_server.

#### D-03: Shared `access` block, top-level on `api`/`dataset` records only
Shape exactly as in `docs/PHASE-4.0-SPEC.md` § "Shared access block": `cost`, `rate_limit`, `auth`, `license`, `formats`, `transport`, `provenance` (keyed by field path, each `{ method: 'declared'|'spec'|'probed'|'heuristic'|'extracted'|'manual', source_url, confidence, checked_at }`). `unknown` is a first-class value; the upcaster defaults every enum to `'unknown'`, numbers to `null`, arrays to `[]`, provenance to `{}`. Helper module `scripts/lib/access.js`: `emptyAccess()`, `setAccessField(access, path, value, prov)`, `accessClarity(access)` → 0-1 (auth known ⅓ + cost model known ⅓ + rate limit known ⅓, each × provenance confidence; `unknown` counts 0).

## Summary

Phase 4.1 is pure scaffolding inside a codebase that already has every seam it needs: Phase 3.1.2/3.2 built dispatch registries for scorers (`scripts/lib/scorers/index.js`), embedding inputs (`scripts/lib/embedding-input/index.js`), filter rule packs (`scripts/lib/filter-rules/index.js`) and recipes (`scripts/lib/recipes/index.js`), plus a central upcaster (`scripts/lib/legacy-skill-reader.js`) whose `buildCommonFields()` is the single place where `repo_*` defaults are coerced. The work is: add two keys to four registries, add two upcast paths, make one shared builder nullable-aware, generalize `assignSlugs`' owner derivation, and prove it all with a round-trip test. Most of the D-07 blast radius turns out to be already null-tolerant (`|| ''`, `|| 0`, `?? null`, `if (!x) continue`); the real code changes are confined to five files (upcaster, `slug.js`, `tier-assignment.js`, `common.rules.js` dedup key, and a defensive guard in `SkillCard.astro`).

Three findings materially shape the plan. (1) **The upcaster returns `schema_version === 2` records unchanged** (`if (rec.schema_version === CURRENT_SCHEMA_VERSION) return rec;`), so every v2 record already on disk or in the `skills-latest` release asset will *not* gain `origin`/`home_url`/`docs_url` unless the passthrough branch back-fills them in place — D-02's "no existing consumer has to branch" depends on this. (2) **Slugs are scoped per entity type** (`types.d.ts`: "URL-safe slug, scoped per type"; `filter-mcps.js` calls `assignSlugs(records)` on its own array only), so the D-05 test should assert that an `api` and a `skill` with the same `owner/name` *both keep* `owner/name` (they live in different files/routes) and that two apis with the same `provider/name` get the `owner/<disambiguator>/name` collision form. (3) **D-09's literal fixture path `scripts/test/fixtures/` does not exist**; the committed precedent for pipeline-level NDJSON fixtures is `data/__fixtures__/plugins-mini.ndjson` / `mcp-mini.ndjson` (used by `embed-skills.test.js` and `upload-vectors.test.js`), and module-local fixtures live in `scripts/lib/<module>/__tests__/fixtures/`. D-09's own parenthetical ("match existing fixture location/naming") authorizes using `data/__fixtures__/apis-mini.ndjson` + `datasets-mini.ndjson`.

Baseline measured in this worktree (Node v22.18.0, 2026-11-02): `npm test` → 449 tests, **441 pass, 2 fail, 6 skipped** (the 2 fails are `scripts/__tests__/embed-skills.test.js` "Task 9: B-2 cache-hit pre-check" and "B-2 drift assertion" — subprocess-driven, pre-existing, listed in STATE.md; the 6 skips are HNSW-engine tests that only run with `ANN_REQUIRE_HNSW=1` in CI). `npm run check:patterns` → `lint mode: clean (0 baselined, 0 new)`. `node scripts/lint-no-legacy-skill-shape.js` → 5 warnings, exit 0. Vectorize pricing verified live: Workers Paid includes **10M stored dims**, then **$0.05 per 100M**; 50M queried dims included, then $0.01 per 1M — CLAUDE.md's "$0.05/M after the 5M included" is wrong on both numbers.

**Primary recommendation:** Extend `buildCommonFields(rec, { nullableRepo })` rather than writing a parallel builder; back-fill `origin`/`home_url`/`docs_url` in place on the v2 passthrough branch; keep `CURRENT_SCHEMA_VERSION = 2` (additive nullable fields; a bump would make `assertKnownSchemaVersion` reject every file in production); put fixtures in `data/__fixtures__/`; write the round-trip test at `scripts/lib/__tests__/data-feeds-roundtrip.test.js` and only import side-effect-free helpers into it (`generate-registry.js`, `publish-kv.js` and `src/lib/entities.js` all execute on import).

### Pattern 1: The upcaster (`scripts/lib/legacy-skill-reader.js`) — exact current behaviour

**Dispatch (top of `upcastRecord`):**
```js
if (isHeaderRecord(rec)) return rec;
if (rec.schema_version === CURRENT_SCHEMA_VERSION) return rec;          // ← v2 passthrough, IDENTITY
if (typeof rec.schema_version === 'number' && rec.schema_version !== CURRENT_SCHEMA_VERSION) assertKnownSchemaVersion(...);
if (rec.entity_type === 'plugin') return upcastPluginRecord(rec);
if (rec.entity_type === 'mcp_server') return upcastMcpRecord(rec);
return upcastSkillRecord(rec);                                           // v1 skills carry no entity_type
```
Add `if (rec.entity_type === 'api') return upcastApiRecord(rec);` and the dataset line before the skill fallthrough. The existing test `'Task 6: v2 record passes through unchanged'` asserts **identity** (`assert.equal(upcastRecord(v2in), v2in)`), so any origin back-fill on the passthrough branch must mutate in place and return the same object (see Pitfall 1).

**`buildCommonFields(rec)` — the shared defaults (used by plugin + mcp paths; the skill path inlines an identical list):**

| Field | Current default | Nullable-mode default for api/dataset (D-02) |
|-------|-----------------|------------------------------------------------|
| `slug`, `name`, `description` | `rec.x \|\| ''` | same |
| `repo_full_name`, `repo_url` | `\|\| ''` | `rec.x ?? null` |
| `repo_stars`, `repo_forks`, `repo_open_issues` | `typeof === 'number' ? x : 0` | `typeof === 'number' ? x : null` |
| `repo_topics` | `Array.isArray ? x : []` | `Array.isArray ? x : null` |
| `repo_license`, `repo_language`, `repo_description` | `?? null` | same (already nullable) |
| `repo_created_at`, `repo_updated_at`, `repo_pushed_at` | `\|\| ''` | `?? null` |
| `repo_owner_type` | `\|\| 'User'` | `?? null` |
| `repo_owner_avatar` | `\|\| ''` | `?? null` |
| `repo_archived`, `repo_is_fork` | `Boolean(x)` | `typeof === 'boolean' ? x : null` |
| `body_length` | `typeof === 'number' ? x : 0` | keep a number: `(rec.body_length ?? (rec.extra?.readme_markdown ?? rec.description ?? '').length)` |

### Pattern 4: Scorer design for `api.scorer.js` / `dataset.scorer.js` (D-06, uncalibrated)

Mirror `mcp.scorer.js` exactly: a `WEIGHTS` object, a `scores` object of 0-100 sub-signals, weighted sum, `Math.round(Math.min(100, Math.max(0, total)))`.

### Pattern 8: Slugs (`scripts/lib/slug.js`) — generalize owner/repo derivation

Today `assignSlugs` derives `owner = repo_full_name.split('/')[0]`, `repoName = split('/')[1]`, and **skips any record whose owner or `name` is empty** (`if (!owner || !s.name) continue;` at three sites) — so an api with `repo_full_name: null` leaves the loop with whatever `slug` the upcaster set (`''`). Canonical form `owner/name`; collision form `owner/repoName/name`; winner = highest `quality_score`, tie → shorter `repo_full_name`.

Minimal change: introduce one resolver and use it at all four sites (three loops + the tie-break):
```js
function slugParts(s) {
  if (s.entity_type === 'api')     return { owner: s.extra?.provider || '', repo: hostOf(s.extra?.base_urls?.[0]) || s.origin?.source || '' };
  if (s.entity_type === 'dataset') return { owner: s.extra?.publisher || s.origin?.source || '', repo: s.origin?.source || '' };
  const [owner = '', repo = ''] = (s.repo_full_name || '').split('/');
  return { owner, repo };
}
```
Dispatch on `entity_type` **before** `repo_full_name` so an api with a known GitHub repo still slugs as `provider/name` (D-05). Tie-break: replace `(a.repo_full_name || '').length` with `(a.repo_full_name ?? a.id ?? '').length` — behaviour for skills unchanged. Do **not** slugify `name` inside `assignSlugs` (it would silently rewrite every skill slug); harvesters must supply slug-safe `name` and `provider` — fixtures should too (`stripe`, `insee`, `nvidia`, `noaa`, `zenodo`...). Existing slugs already contain dots (GitHub repo names), so `api.stripe.com` as a collision disambiguator is route-safe.

Cross-type behaviour to assert in the D-05 test: `assignSlugs([skillOwnerFoo, apiOwnerFoo])` where both have owner `acme` and name `foo` — today this *would* count as a collision (same `owner/name` key) and emit `acme/<repo>/foo` for both. But production never mixes types in one `assignSlugs` call (`filter.js`, `filter-plugins.js`, `filter-mcps.js` each pass their own array), and routes are type-prefixed. So the test that matches "the way skill/plugin collisions already do" is: two separate per-type calls each yield `acme/foo`; and a within-type collision (two apis, same provider+name, different hosts) yields `acme/<host>/foo` with a redirect entry to the higher-scored one.

### Pattern 9: Tiers (`scripts/lib/tier-assignment.js`)

Line 34: `.map((s, i) => ({ i, score: s.quality_score, stars: s.repo_stars, id: s.id }))` → `stars: s.repo_stars ?? 0`. With nulls the comparator `b.stars - a.stars` coerces to 0 but `b.stars !== a.stars` (null vs 0) is `true`, so the id tie-break is skipped and ordering falls back to input order — a determinism bug, not a crash. ### Pattern 11: NDJSON round trip (`scripts/lib/ndjson.js`)

- `writeNdjsonStreaming(path, records, { header })` — per-record `JSON.stringify(r)`; records with `_header: true` are skipped; tmp+rename with Windows EPERM retry.
- `readNdjsonRecords(path, { keyFn = r => r.id, onHeader })` → `Map`; **records whose key is `undefined/null/''` are dropped** — fixtures that are "raw-ish" and lack `id` must be read with a `keyFn` (e.g. `r => r.origin?.source_id`), or the test should read them via the `openSync/readSync` loop that `embedding-input/__tests__/index.test.js` uses.
- `JSON.stringify` drops `undefined` but keeps `null` → every upcaster default must be `null`, never `undefined`, or `assert.deepEqual(before, after)` across the disk hop fails (Pitfall 6).

### Anti-Patterns to Avoid
- **Parallel NDJSON reader in a test** — allowed in tests, but prefer `readNdjsonRecords` with a `keyFn` so the test also exercises the production reader.
- **Importing `scripts/generate-registry.js`, `scripts/lib/publish-kv.js`, or `src/lib/entities.js` from a unit test** — all three execute `main()` / load `data/skills.ndjson` at import (registry ends with a bare `main();`; publish-kv ends with `main().catch(...)`; entities.js calls `resolveSkillsNdjsonPath()` + `loadAllSkillsMemo` at module top). Importable helpers: `generate-feeds.js` (`buildWhatsNew, buildNotable, buildItem, loadAllEntities`), `snapshot-catalog.js` (`aggregateSnapshot, loadCatalogRecords, main` — guarded), `enrich.js` (`compareForCanonical`, `enrichSkills`), `scripts/lib/bundled-links.js` (`linkBundles`).
- **Bumping `schema_version` to 3** — see State of the Art.
- **Adding `'api'`/`'dataset'` to `CANONICAL_ENTITY_TYPES` in `snapshot-catalog.js`** — `snapshot-catalog.test.js` asserts `Object.keys(snap.by_entity_type).sort()` equals exactly `['mcp_server','plugin','skill']` on an empty catalog; unknown types auto-bucket anyway (`if (!byType[et]) byType[et] = emptyTypeBucket();`). Leave it for 4.2/4.5 when data exists.
- **Widening `EntityCommon.source`** — `'registry'` and `'manual'` already exist; use them. `origin.source` is the *provenance catalog name* (`'apis.guru'`), `source` is the *discovery channel* — keep the two distinct and comment it (Pitfall 7).

## Common Pitfalls

### Pitfall 1: v2 passthrough never gains `origin`
**What goes wrong:** `upcastRecord` returns any `schema_version === 2` record by identity. Every record in `data/skills.ndjson` (and the `skills-latest` asset, `plugins.ndjson`, `mcp-servers.ndjson`) is already v2, so `origin`/`home_url`/`docs_url` would be `undefined` on all production records until the next full filter run — and `src/lib/entities.js` / page code reading `entity.origin.kind` would throw.
**Why it happens:** D-02 assumes the upcaster is the universal choke point; it is, but only for v1 input.
**How to avoid:** In the passthrough branch, call `backfillOriginInPlace(rec)` that sets the three fields only when `rec.origin === undefined`, then `return rec` (same object → the identity test still passes). Add a test: v2 skill without `origin` → after upcast has github origin, `===` identity preserved.
**Warning signs:** round-trip test passes but `generate-feeds`/`llms.txt` runs on real data show `undefined` origins.

### Pitfall 2: `assignSlugs` silently skips null-repo records
**What goes wrong:** api/dataset records exit `assignSlugs` with `slug: ''`; downstream `detail_url` = `/apis//`.
**How to avoid:** `slugParts()` resolver (Pattern 8); assert in the round-trip test that every record has a non-empty slug containing exactly one `/` (or two for collisions).

### Pitfall 3: `dedupLanguageVariants` merges unrelated feeds
**What goes wrong:** key `"null/<name>"` → `weather` from provider A and `weather` from provider B dedup to one.
**How to avoid:** key on `repo_full_name ?? origin.source_id ?? id`. Note `filter.js` is the only caller today, and only for skills — the fix is defensive for 4.2's `filter-apis.js`.

### Pitfall 4: tie-break nondeterminism with null stars
See Pattern 9 — `?? 0` + test.

### Pitfall 5: `generate-registry.js`, `publish-kv.js`, `src/lib/entities.js` execute on import
**What goes wrong:** importing them in the round-trip test runs the generator/publisher or throws `pre-F1 JSON-array … / skills.ndjson absent` (there is no `data/skills.ndjson` in this worktree — `ls data` shows only `skills.json` + sidecars).
**How to avoid:** import only the pure helpers listed under Anti-Patterns. If the planner wants registry coverage, first extract `buildRegistryEntry(s)` behind the `invokedAsScript` guard pattern used by `generate-feeds.js:387-395` (small, safe refactor) — otherwise document "registry: no pure helper; covered in 4.3".

### Pitfall 6: `undefined` vs `null` across the disk hop
**What goes wrong:** `JSON.stringify` drops `undefined` keys; `assert.deepEqual(upcasted, readBack)` fails on any field the upcaster left `undefined` (e.g. `transport === undefined ? null : transport` exists in the mcp path for exactly this reason).
**How to avoid:** every default in the new paths is an explicit `null`/`[]`/`{}`/`'unknown'`; round-trip assertion compares against `JSON.parse(JSON.stringify(upcasted))` *and* flags any `undefined` via a recursive walk.

### Pitfall 7: `source` vs `origin.source`
**What goes wrong:** a future reader confuses `EntityCommon.source` (discovery channel enum: `'code-search'|'topics'|'seed'|'discover'|'registry'|'manual'`) with `origin.source` (catalog name `'apis.guru'`).
**How to avoid:** api/dataset use `source: 'registry'`; add a one-line JSDoc on both fields in `types.d.ts`; name the fixture field `origin.source` explicitly.

### Pitfall 8: Common slop gates eat realistic fixture names
`BIZ_SLOP_PATTERNS` rejects `^energy-`, `^inventory-`, `-management$`, `-optimization$`; `TEMPLATE_NAMES` rejects `test`, `sample`, `default`, …; `PLACEHOLDER_DESC_PATTERNS` rejects descriptions starting with `[`. Pick fixture names like `stripe`, `melodi`, `simready-assets`, `electric-vehicle-population`, `ghcn-daily`, `archi-v2`. Record the data-domain false-positive risk (`energy-*`, `climate-*` datasets) as a 4.5 calibration note.

### Pitfall 9: Lint scope for new files
`check-banned-patterns` Banned-A matches **any** `readFileSync(x, 'utf-8')` in `scripts/`, `src/`, `worker/` outside `__tests__/`/`*.test.js` (e.g. a fixture loader at `scripts/test/fixtures/load.js` would fail CI). `lint-no-legacy-skill-shape` flags object keys `body_markdown:`, `frontmatter:`, `has_name:`, `has_description:`, `skill_path:`, `skill_first_commit_at:` at line start in non-excluded files — the new scorers/rules/access modules must not declare such keys (they have no reason to). Expected lint output stays at exactly 5 warnings.

### Pitfall 10: `types.test.js` is a substring test
`dts.includes('consumed_by')` passes if the word appears anywhere — fine for presence, blind to shape. Pair it with the runtime round-trip test for real coverage; don't rely on it alone.

### Pitfall 11: The two known-failing tests are subprocess tests
`embed-skills.test.js` "B-2 cache-hit" and "B-2 drift" spawn `node scripts/embed-skills.js` and grep stdout (`cache hit rate: 100.000%`); they fail in this Windows worktree today and are the STATE.md baseline. Do not try to fix them in 4.1; assert the fail count is exactly 2 and both names are unchanged.

### 2. `scripts/lib/access.js` (D-03)
```js
export const UNKNOWN = 'unknown';
export function emptyAccess() {
  return {
    cost: { model: UNKNOWN, free_tier: null, price_notes: null },
    rate_limit: { requests: null, per: null, notes: null, headers_observed: [] },
    auth: { type: UNKNOWN, signup_url: null },
    license: { spdx: null, name: null, url: null },
    formats: [],
    transport: null,
    provenance: {},
  };
}
/** path like 'auth.type' or 'rate_limit.requests'; prov = { method, source_url, confidence, checked_at } */
export function setAccessField(access, path, value, prov) {
  const [group, key] = path.split('.');
  if (!access[group] || !(key in access[group])) throw new Error(`setAccessField: unknown path ${path}`);
  access[group][key] = value;
  access.provenance[path] = {
    method: prov?.method ?? 'manual',
    source_url: prov?.source_url ?? null,
    confidence: clamp01(prov?.confidence ?? 1),
    checked_at: prov?.checked_at ?? new Date().toISOString(),
  };
  return access;
}
/** 0-1: auth known ⅓ + cost model known ⅓ + rate limit known ⅓, each × provenance confidence; 'unknown' = 0 */
export function accessClarity(access) {
  if (!access) return 0;
  const conf = (p) => access.provenance?.[p]?.confidence ?? 1;
  const authKnown = access.auth?.type && access.auth.type !== UNKNOWN ? conf('auth.type') : 0;
  const costKnown = access.cost?.model && access.cost.model !== UNKNOWN ? conf('cost.model') : 0;
  const rlKnown = (typeof access.rate_limit?.requests === 'number' && access.rate_limit.per)
    ? conf('rate_limit.requests') : (access.rate_limit?.notes ? 0.5 * conf('rate_limit.notes') : 0);
  return (authKnown + costKnown + rlKnown) / 3;
}
```
(The `notes`-only half-credit for rate limits is a judgement call — data.gouv.fr's declared limits are free text; document it in the JSDoc and in the test.)

### 3. `api.scorer.js` skeleton (mirrors `mcp.scorer.js`)
```js
import { scoreRecency, scoreLicense, scoreStars, scoreDescription } from '../../score.js';
import { accessClarity } from '../access.js';
const WEIGHTS = { access: 0.20, reachability: 0.15, docs: 0.15, license: 0.15, freshness: 0.15, popularity: 0.15, adoption: 0.05 };
const NEUTRAL_REACHABILITY = 70, NEUTRAL_POPULARITY = 50;
export function scoreApi(record) {
  const clarity = accessClarity(record?.access);
  if (record?.extra) record.extra.access_clarity = clarity;          // side-effect, same convention as manifest_completeness
  const cb = record?.extra?.consumed_by || {};
  const adoption = (cb.skills?.length || 0) + (cb.plugins?.length || 0) + (cb.mcp_servers?.length || 0);
  const scores = {
    access: clarity * 100,
    reachability: NEUTRAL_REACHABILITY,
    docs: scoreFeedDocs(record),
    license: scoreLicense(record?.access?.license?.spdx ?? record?.access?.license?.name ?? null),
    freshness: scoreRecency(record?.extra?.source_modified_at ?? record?.repo_pushed_at ?? null),
    popularity: typeof record?.repo_stars === 'number' ? scoreStars(record.repo_stars) : NEUTRAL_POPULARITY,
    adoption: Math.min(100, adoption * 20),
  };
  let total = 0;
  for (const [k, w] of Object.entries(WEIGHTS)) total += scores[k] * w;
  return Math.round(Math.min(100, Math.max(0, total)));
}
```

   - What we know: spec says "days since spec/dataset `modified`"; neither `ApiExtra` nor `DatasetExtra` in the spec has a modified field; `repo_pushed_at` is null.
   - What's unclear: whether to add `source_modified_at` to both Extras (recommended) or put it on `origin`.
   - Recommendation: add `source_modified_at: string | null` to `ApiExtra` and `DatasetExtra` (D-04 "as in the spec" plus one field, justified by the spec's own Freshness row); fall back to `repo_pushed_at` when a repo is known.

2. **`access` top-level (spec) vs `extra.access`** (Claude's discretion).
   - Recommendation: top-level, as a member of the api/dataset union types only. Reasons: 4.3's access card and the MCP `find_data_source` filters read one path for both types; `PRESERVED_FIELDS` logic in future `filter-apis.js` operates on top-level keys; keeps `extra` purely type-specific. No pushback.

3. **Fixture directory** — D-09 names `scripts/test/fixtures/` (non-existent) with the qualifier "match existing".
   - Recommendation: `data/__fixtures__/apis-mini.ndjson` + `datasets-mini.ndjson` (existing pipeline-fixture precedent, committed, lint-safe). The planner should state this deviation explicitly in the plan so the verifier doesn't flag it.

4. **Lint rule banning non-null-safe `repo_*` reads** (discretion).
   - Recommendation: skip in 4.1. A regex can't distinguish `s.repo_stars` in a skill-only page from a shared helper; the round-trip test plus the audit table above is the durable guard. Revisit when 4.3 adds mixed-type pages.

5. **Freshness when `source_modified_at` is missing: 0 or neutral?**
   - D-06 reserves neutral defaults for signals "whose inputs do not exist yet" (probe history, consumer graph). Modified dates exist at harvest time for every verified source, so missing = unknown → `scoreRecency(null) === 0`. Keep 0; calibrate in 4.2/4.5.

6. **Should `generate-registry.js` get an `invokedAsScript` guard + exported entry builder now?**
   - Cheap and consistent with `generate-feeds.js`/`snapshot-catalog.js`; makes the "registry helper" leg of D-07 testable. Optional task; if skipped, note "registry covered in 4.3".

7. **Embedding input for api lacks "first 10 endpoint summaries"** (spec) because no field holds them in 4.1. Decide in 4.2 whether `ApiExtra.endpoint_summaries: string[]` is worth the storage; the builder should read it if present (`arr(e.endpoint_summaries).slice(0,10)`) so 4.2 is additive.

### What a failing signal looks like
- `npm test`: `# fail 3` (or more) — the third name identifies the regression; `not ok … failureType: 'testCodeFailure'` with `location:` path.
- `check:patterns`: `[check-banned-patterns] lint mode: N new hit(s)` + `file:line  <pattern letter>` lines, exit 1.
- legacy-shape lint: `WARN legacy-read: <file>:<line>` count > 5 (still exit 0 in warning mode — the verifier must compare the count, not the exit code).
- Round-trip: `AssertionError … Expected values to be strictly deep-equal` with a diff showing a missing key → an `undefined` default (Pitfall 6); `TypeError: Cannot read properties of null (reading 'split')` → a consumer missed in the sweep.

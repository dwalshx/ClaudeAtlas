<domain>
## Phase Boundary

This phase makes `api` and `dataset` valid `entity_type`s that round-trip through every shared pipeline helper **without a GitHub repo**. It is scaffolding: types, defaults, registries, a feature flag, fixtures and tests. After this phase ships:

- `EntityType` includes `'api' | 'dataset'`; `ApiExtra` and `DatasetExtra` exist in `src/lib/types.d.ts` + `src/lib/types.js`.
- `EntityCommon` gains `origin`, `home_url`, `docs_url`; `api`/`dataset` records gain a top-level `access` block with per-field provenance.
- `repo_*` fields are nullable for `api`/`dataset` records; every shared consumer is null-safe.
- Scorer, embedding-input, filter-rule and recipe registries have `api` and `dataset` entries (test-driven on fixtures; calibration happens in 4.2/4.5 with real data).
- `scripts/lib/access.js` exists (empty-access constructor, field setter with provenance, access-clarity 0-1).
- `daily-scrape.yml` carries `DATA_FEEDS_ENABLED: 'false'` in its env block, with a comment; **no new steps yet**.
- CLAUDE.md: data-model section documents the two new types + the `origin`/`access` additions, and the Vectorize cost line is corrected (verified 2026-11-02: $0.05 per **100M** stored dims/month, 10M included on Workers Paid; the old "$0.05/M" was 100× too high).

**Out of scope (later phases):** harvesters (4.2, 4.5), pages and nav (4.3, 4.5), probe (4.4), consumer graph (4.6), extraction ladder (4.7), GitHub spec discovery (4.8). No workflow steps, no data files, no UI.

**Why this phase, why now:** Phase 3.1.2's polymorphic envelope assumed every entity lives in a GitHub repo (`repo_full_name`, `repo_stars`, `repo_pushed_at` are required and feed slugs, tiers, scoring, feeds, registry, KV publish, creators). Data feeds are the first entities that mostly do not. Doing the generalization alone, test-first, keeps 4.2's harvester a pure "add files" exercise exactly as 3.1.2 did for 3.2.

</domain>

<decisions>
## Implementation Decisions

### D-01: Two entity types, `api` and `dataset`
Not one `data_feed` type. Extra shapes, scorers, sources and pages differ as much as skill vs plugin. Shared pieces are the `access` block and the nav section (4.3). Add both to the `EntityType` union, the `EntityRecord` discriminated union, `scorers`, `builders`, `rulePacks`, and the recipe registry.

### D-02: `origin` on EVERY record; `repo_*` nullable only for non-GitHub origins
```ts
origin: {
  kind: 'github' | 'registry' | 'portal' | 'manual';
  source: string;        // 'github' | 'apis.guru' | 'data.gouv.fr' | 'huggingface' | 'data.gov' | ...
  source_id: string;     // native id in that source (repo_full_name for github)
  source_url: string;    // where the record was read (repo_url for github)
  also_listed_in: string[];
};
home_url: string;        // repo_url for github-origin records
docs_url: string | null;
```
The upcaster fills `origin = { kind: 'github', source: 'github', source_id: repo_full_name, source_url: repo_url, also_listed_in: [] }`, `home_url = repo_url`, `docs_url = null` for skill/plugin/mcp_server so the shape stays uniform and no existing consumer has to branch. For `api`/`dataset`, `repo_*` fields are `null` (not `''`/`0`) when no GitHub repo is known; when one is known (e.g. an APIs.guru `x-origin` pointing at GitHub) they populate normally. Types: `repo_*` become `T | null` on `EntityCommon` with a doc comment that they are non-null for github-origin records; a test asserts the upcaster never emits null `repo_*` for skill/plugin/mcp_server.

### D-03: Shared `access` block, top-level on `api`/`dataset` records only
Shape exactly as in `docs/PHASE-4.0-SPEC.md` § "Shared access block": `cost`, `rate_limit`, `auth`, `license`, `formats`, `transport`, `provenance` (keyed by field path, each `{ method: 'declared'|'spec'|'probed'|'heuristic'|'extracted'|'manual', source_url, confidence, checked_at }`). `unknown` is a first-class value; the upcaster defaults every enum to `'unknown'`, numbers to `null`, arrays to `[]`, provenance to `{}`. Helper module `scripts/lib/access.js`: `emptyAccess()`, `setAccessField(access, path, value, prov)`, `accessClarity(access)` → 0-1 (auth known ⅓ + cost model known ⅓ + rate limit known ⅓, each × provenance confidence; `unknown` counts 0).

### D-04: `ApiExtra` / `DatasetExtra` as in the spec
Fields per spec § "ApiExtra / DatasetExtra" (`base_urls`, `spec_url`, `endpoint_count`, `provider`, `consumed_by`, … / `download_urls`, `size_bytes`, `size_bucket`, `update_frequency`, `publisher`, `popularity`, `schema_url`, `consumed_by`). `consumed_by` defaults to `{ skills: [], plugins: [], mcp_servers: [] }` and goes into filter `PRESERVED_FIELDS` thinking later (4.6) — 4.1 only defines it.

### D-05: ID + slug scheme
`id = 'api:<primary_host>/<service_key>'` (e.g. `api:api.stripe.com/stripe`), `id = 'dataset:<source>/<native_id>'` (e.g. `dataset:huggingface/squad`). `slug = '<provider>/<name>'` through the existing `assignSlugs()` so collision handling is reused unchanged; a test proves an `api` and a `skill` with the same `owner/name` resolve the way skill/plugin collisions already do.

### D-06: Scorers in 4.1 implement the spec's 7 data-feed signals, uncalibrated
`scripts/lib/scorers/api.scorer.js` and `dataset.scorer.js`: Access clarity 20, Reachability 15, Documentation 15, License 15, Freshness 15, Popularity 15, Ecosystem adoption 5 (weights from spec § "Scoring"). Signals whose inputs do not exist yet read neutral defaults (reachability 0.7 when no history; popularity 0.5 when no source metric; adoption 0 when `consumed_by` empty) so the scorer is total on day one. Calibration against real harvests is 4.2 (api) and 4.5 (dataset); **do not tune weights here**. Embedding inputs per spec § "Embedding input". Rule packs: `api.rules.js` / `dataset.rules.js` reuse `common.rules.js` (template names, placeholder descriptions, min description 50 chars) and add `HAS_HOME_URL` and, for api, `HAS_BASE_URL_OR_SPEC`; for dataset, `HAS_DOWNLOAD_OR_LANDING`. No star gate (Phase 3.1 precedent).

### D-07: Null-safety sweep of shared consumers, test-first
Blast radius measured 2026-11-02 (files referencing `repo_stars|repo_full_name|repo_pushed_at|repo_url`, excluding tests): `scripts/lib/legacy-skill-reader.js`, `scripts/lib/slug.js`, `scripts/lib/tier-assignment.js` (stars tie-break → `?? 0`), `scripts/lib/filter-rules/common.rules.js` (`isFixtureRepo`, `dedupLanguageVariants` key), `scripts/generate-feeds.js`, `scripts/generate-registry.js`, `scripts/snapshot-catalog.js`, `scripts/lib/publish-kv.js`, `scripts/enrich.js`, `scripts/embed-skills.js`, `scripts/filter.js`, `scripts/lib/bundled-links.js`, `scripts/lib/skill-fields.js`, `src/lib/entities.js` (`getCreators` must skip records with null `repo_full_name`), `src/lib/charts.js`, `src/components/SkillCard.astro`, `src/pages/index.astro`, `worker/index.js`, `worker/markdown.js`, `worker/mcp.js`. Pages under `src/pages/{skills,plugins,mcp}` only ever receive their own type and need no change. Write the round-trip test FIRST (fixture api + dataset records through upcast → score → embedding input → isSlop → tiers → slugs → `writeNdjsonStreaming` → `readNdjsonRecords` → feeds/registry/snapshot helpers), watch it fail, then fix each consumer.

### D-08: Feature flag only
Add `DATA_FEEDS_ENABLED: 'false'` next to `PLUGINS_ENABLED` in `daily-scrape.yml` env with a comment pointing at the spec. No steps gated on it yet (4.2 adds them). `scripts/check-banned-patterns.js` rules apply to any new script.

### D-09: Fixtures
`scripts/test/fixtures/` (match existing fixture location/naming) gets 4 api records (APIs.guru-shaped with OpenAPI `securitySchemes`-derived auth; data.gouv.fr-shaped with declared `rate_limiting`; public-apis-shaped minimal; one with a known GitHub repo so `repo_*` populate) and 4 dataset records (Hugging Face-shaped with downloads + size bucket; data.gov DCAT-US-shaped with `accrualPeriodicity`; AWS ODR-shaped with `UpdateFrequency`; Zenodo-shaped with bytes + citations). Fixtures are raw-ish inputs to the upcaster, not finished records, so 4.2/4.5 harvesters can target the same shape.

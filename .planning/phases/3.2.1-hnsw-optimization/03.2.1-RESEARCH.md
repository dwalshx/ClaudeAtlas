## Summary

Both O(N²) targets were measured and the bottleneck decomposed empirically. `compute-similar.js` (~162 min at 51k, inside the Build step) is the **naive worst case**: full n² scan, per-pair norm recomputation (3 ops/dim instead of 1), per-row allocation of 51k score objects, and a full O(n log n) sort per row, over plain float64 JS arrays. `enrich.js` (~59 min) is already the **optimized exact form** (pre-normalized Float32Array, dot-only, symmetric i<j loop) — local benchmark confirms it runs at the JS single-thread ceiling (~0.93 GMAC/s on the dev box; calibrates to the measured GHA times within ~10%). Conclusion for Q1e: compute-similar has ~3× of pure implementation waste, but even a perfectly optimized exact pass totals ~45–65 min single-thread on GHA and grows quadratically — not durable. ANN is the right fix; the constant-factor option survives only as the fallback engine.

The option space resolves decisively. **Cloudflare Vectorize as the ANN engine is dead on two independent grounds**: (1) cost — 51k queries/day × 1536 dims = 78.3M queried dims/day ≈ 2.38B/month ≈ **$23.3/month ≈ $280/yr**, 2.7× the entire current annual budget; (2) latency — there is **no batch query API** (verified), and the global Cloudflare REST API limit of **1,200 requests/5 min** means 51k daily queries from a GHA runner take ≥212 min on rate limits alone. **voy (WASM)** is a k-d tree — algorithmically useless at 1536 dims — plus unmaintained (Sep 2023) and not loadable in plain Node (bundler-target package; verified locally). **faiss-node** and **hnswlib-wasm** are stale. **usearch** is actively maintained (May 2026) but its npm install **fell back to node-gyp and failed on the win32-arm64 dev box** (no prebuilt for that platform) — same dev-box story as hnswlib-node, with a less battle-tested Node binding. Empirical install test: **no native addon builds on the dev box today** (no VS C++ toolchain), so whatever native lib is chosen MUST ship with a pure-JS fallback path.

**Primary recommendation:** `hnswlib-node` (127k downloads/week, the LangChain-ecosystem standard, exposes deterministic `randomSeed`, cosine/IP spaces, `searchKnn` with filter, index serialization) behind a new `scripts/lib/ann.js` helper that **falls back to the existing exact Float32 brute-force when the native module fails to load** (dev box) — with a CI gate asserting the native engine actually loaded in cron so the fallback can never silently regress production to O(N²). Build the index twice (once in enrich, once in compute-similar) rather than serializing — rebuild is ~2–4 min and eliminates a 350 MB artifact + staleness contract. Projected effect: enrich 59 → ~6–10 min, Build step 162+ → ~25–40 min; full cron ~75–120 min, restoring ~200+ min of headroom under the 360 cap and unblocking Phase 3.3 (+48 min). Audit B lands as a **flag-don't-block** content scanner in `filter-rules/content.rules.js` — the empirical scan over the real 33k-record raw corpus shows hard-blocking is not viable (236 records legitimately contain `curl|sh`), and surfaced **4 new scanner-fixture repos** that should instead extend `FIXTURE_REPO_DENYLIST`.

### Pattern 1: `ann.js` — engine detection with loud fallback

**What:** One module owning vector prep + neighbor search. Tries native HNSW; falls back to exact Float32 brute-force (optionally worker_threads-parallel) when the native module can't load.

**When to use:** Both consumers. Never import hnswlib-node directly elsewhere.

```javascript
// scripts/lib/ann.js (shape — Source: yoshoku.github.io/hnswlib-node typedoc, verified 2026-06-10)
import { createRequire } from 'node:module';

let HierarchicalNSW = null;
let engine = 'exact';
try {
  const require = createRequire(import.meta.url);
  ({ HierarchicalNSW } = require('hnswlib-node'));
  engine = 'hnsw';
} catch (err) {
  console.warn(`[ann] hnswlib-node unavailable (${err.message}) — falling back to exact brute-force`);
}

export function annEngine() { return engine; }   // CI gate asserts 'hnsw' in cron

/**
 * items: Array<{ id, vec: Float32Array }> — vecs MUST be pre-normalized
 * (dot == cosine). Returns per-item top-K neighbors [{ idx, sim }].
 * Determinism: items are sorted by id by the CALLER before this runs;
 * randomSeed is fixed (default 100) → identical output for identical input.
 */
export function topKNeighbors(items, k, { efSearch = Math.max(2 * k, 100) } = {}) {
  if (engine === 'hnsw') {
    const dim = items[0].vec.length;
    const index = new HierarchicalNSW('ip', dim);          // pre-normalized → inner product == cosine
    index.initIndex(items.length, 16, 200, 100);            // M=16, efConstruction=200, randomSeed=100
    for (let i = 0; i < items.length; i++) index.addPoint(Array.from(items[i].vec), i);
    index.setEf(efSearch);
    return items.map((it, i) => {
      const { neighbors, distances } = index.searchKnn(Array.from(it.vec), Math.min(k + 1, items.length));
      const out = [];
      for (let j = 0; j < neighbors.length; j++) {
        if (neighbors[j] === i) continue;
        out.push({ idx: neighbors[j], sim: 1 - distances[j] });  // ip space: distance = 1 - dot
      }
      return out.slice(0, k);
    });
  }
  return exactTopK(items, k);   // existing Float32 dot loop, factored out of enrich.js
}
```

Verified API facts (HIGH confidence, typedoc): `initIndex(maxElements, m=16, efConstruction=200, randomSeed=100, allowReplaceDeleted=false)`; `searchKnn(queryPoint, numNeighbors, filter?)`; `setEf(ef)`; `writeIndexSync/readIndexSync`. Space `'ip'` returns distance `1 − innerProduct` (hnswlib convention) — convert back to similarity; alternatively space `'cosine'` skips manual normalization, but pre-normalizing keeps the exact-fallback and HNSW paths numerically identical.

### Pattern 2: enrich dedup via top-K + threshold filter (range query emulation)

**What:** HNSW has no native range/radius query. Emulate: query `K_DUP` neighbors (recommend **K_DUP = 64, efSearch = 150**), keep only `sim > 0.92`, symmetrize edges (add edge if EITHER endpoint found the other), then run the existing BFS clustering + `compareForCanonical` unchanged.

**Why this is safe:** the approximation can only MISS pairs, never invent them — every returned neighbor's similarity is exactly computed before thresholding. False dedup merges are impossible; the only failure mode is a cluster split (a missed borderline edge). For dense duplicate clusters (the common case — template copies at sim ≈ 0.99), every member's top-64 is dominated by cluster siblings, so BFS connectivity survives easily even for clusters far larger than 64.

**Novelty from the same query:** `novelty_score = 1 − sim(top-1 neighbor)` — top-1 comes free from the same `searchKnn` call. A recall miss can only UNDERESTIMATE max-sim → slightly OVERESTIMATE novelty; the percentile gate (top 5%, rank-based) is robust to small uniform noise. Quantified in the validation harness.

### Pattern 3: compute-similar rewrite

**What:** Replace the naive loop with: load vectors via `readNdjsonRecords` (unchanged), slug-dedupe (unchanged), normalize to Float32Array, call `topKNeighbors(items, TOP_K)`, emit the same `similar-skills.json` shape. Per CONTEXT, `TOP_K` can return to 5 — with ANN the runtime cost of K is negligible (planner's choice; output-size is the only consideration, was ~40% of 728 KB).

**Stays inside prebuild:** post-HNSW compute-similar is ~3–5 min, so no workflow-step restructuring is needed. Note (pre-existing behavior to preserve deliberately): on push-event builds, `data/skill-vectors.ndjson` is the committed stale 1,078-vector Phase-1 seed (the GHA cache restore step is cron-only), so push-deploy `similar-skills.json` reflects only those 1,078 records. Not in scope to fix — but do not accidentally "fix" or break it.

### Pattern 4: Audit B — annotate pass in filterRaw, flags not gates

**What:** `content.rules.js` exports `scanContentFlags(record) → string[]` (rule names). Called from a new annotation step inside `filterRaw()` **after Step 1 (isSlop) and BEFORE Step 4b body truncation** — at that point `body_markdown` is the raw scraper output (5000-char truncation), which is what the scan must see. Writes `record.content_flags = [...]` (additive field; recomputed every run from raw body → does NOT go in `PRESERVED_FIELDS`). Summary counts appended to `pipeline-stats.json` (bounded sidecar, allowlisted).

**Posture: FLAG, don't block** — empirically mandated, see Pitfall 4. The only hard-block change is extending `FIXTURE_REPO_DENYLIST`.

**Performance:** empirical scan of all 13 candidate rules over the real 33,000-record raw corpus (5000-char bodies): **5.1 s on the dev box without any prefilter** — with a cheap `indexOf` keyword prefilter and on GHA, expect <10 s added to the ~6 s filter step. Well within budget.

### Anti-Patterns to Avoid

- **Querying Vectorize from the GHA runner for bulk neighbor retrieval:** $280/yr + 1,200 req/5 min global API cap = 212+ min. Never.
- **Serializing the HNSW index as a cross-run cache with incremental inserts:** rebuild is ~2–4 min; incremental insert requires delete/replace bookkeeping (`allowReplaceDeleted`), capacity resizing, and staleness invalidation against the vectors file. CONTEXT already leaned simplicity; confirmed.
- **Putting hnswlib-node in `dependencies`:** bricks `npm ci` on the dev box (verified: node-gyp fails — no VS toolchain). Use `optionalDependencies` + runtime detection.
- **Silent fallback in CI:** if the native build ever breaks on ubuntu (Node major bump, image change), the exact fallback would quietly restore the 221-min cron. The cron/CI MUST assert `annEngine() === 'hnsw'` (log line + a workflow grep gate, mirroring the 3.2 runtime-gate pattern).
- **Hard-blocking on `curl ... | sh` content match:** 236 real records (0.72%) match — overwhelmingly legit install instructions. Blanket blocking would nuke legitimate skills (the user constraint about the 95 example-path skills generalizes here).
- **Feeding the 1500-char truncated body to the scanner:** truncation happens in filterRaw Step 4b; scan before it or payloads at offsets 1500–5000 are invisible.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| ANN graph index | Custom HNSW/LSH in JS | hnswlib-node | Graph construction subtleties (level assignment, neighbor selection heuristic, pruning) take months to get right; hnswlib is the reference implementation with a decade of hardening |
| SIMD distance kernels | Hand-written WASM GEMM/tiling | hnswlib-node's native AVX2 kernels (or the plain JS fallback) | A tiled WASM SGEMM could make exact search ~2–4 min, but it's a hand-rolled numerical kernel with its own correctness/testing burden; HNSW achieves the same wall-clock with a maintained library |
| Range query on HNSW | Custom radius-search graph traversal | top-K=64 + `sim > 0.92` post-filter | Standard practice; the BFS clustering already tolerates the top-K formulation (misses only split clusters, never merge them) |
| Regex scanning engine | Custom string-matching automaton for Audit B | Plain JS RegExp + `indexOf` prefilter | Measured 5.1 s / 33k records with zero optimization — performance is a non-problem |

**Key insight:** the domain's hard part is not the math (cosine = dot on normalized vectors) — it's the graph-index construction quality and the years of edge-case hardening in hnswlib. Buy that; keep everything else (clustering, canonical selection, NDJSON I/O) as the existing proven code.

## Common Pitfalls

### Pitfall 1: Native module assumed available everywhere
**What goes wrong:** `npm ci` or `import` fails on win32-arm64 (verified: node-gyp cannot find VS 2017+; neither hnswlib-node nor usearch ships a win32-arm64 prebuilt).
**Why it happens:** Both libs build from source via node-gyp; dev box has no MSVC toolchain.
**How to avoid:** `optionalDependencies` + runtime engine detection in `ann.js` + exact fallback. Document the optional local remediation (install "VS 2022 Build Tools → Desktop development with C++ (ARM64)") but do not depend on it.
**Warning signs:** `gyp ERR! find VS` in npm output; tests passing locally only via fallback (fine — fixtures are small).

### Pitfall 2: Silent O(N²) regression via the fallback
**What goes wrong:** A future Node version bump or runner-image change breaks the native compile in CI; `ann.js` falls back silently; cron creeps back toward 221 min and eventually times out.
**How to avoid:** cron logs `[ann] engine=hnsw`; a workflow gate (or the enrich timing hard-warn, retargeted from 600 s to ~600 s post-HNSW it should never trip) fails loudly if engine ≠ hnsw on scheduled runs. Also keep the `elapsed > 600s` warn in enrich.js — post-HNSW it doubles as the regression tripwire.
**Warning signs:** enrich step duration jumping from ~7 min back to ~30+ min.

### Pitfall 3: Non-deterministic dedup churn
**What goes wrong:** `is_duplicate`/`canonical_slug` flap day-to-day, churning KV publishes and the catalog.
**Why it happens:** HNSW build depends on insertion order + RNG. Vectors themselves are stable (embed is incremental; `_content_sha` keyed).
**How to avoid:** sort items by vector `id` before insertion; `randomSeed` fixed at 100 (the default — pass it explicitly anyway). Given identical inputs, the build and queries are then fully deterministic. Day-to-day variation comes only from genuinely new/changed records — same as today.
**Warning signs:** validation harness flap-count > 0 on identical input replay.

### Pitfall 4: Blocking on content patterns (Audit B)
**What goes wrong:** Legit skills vanish from the catalog.
**Empirical evidence (scan of 33,000 real raw records, 2026-06-10):** `curl|sh` matches **236 records (0.72%)** — mostly legitimate install one-liners (e.g. `eddmann/whatsapp-cli`, `ZackKorman/skills :: pdf-helper`); jailbreak markers (`ignore previous instructions` etc.) match ~50 records — mostly scanner test fixtures and security-education skills (`mukul975/Anthropic-Cybersecurity-Skills`, `Orchestra-Research/AI-Research-SKILLs :: prompt-guard`, `alirezarezvani/claude-skills :: ai-security`). Records matching ≥2 distinct rules: only **28** — a reviewable set, still dominated by fixtures/education.
**How to avoid:** flag-don't-block (`content_flags[]` + pipeline-stats summary). Promotion to blocking is manual, via the existing `FIXTURE_REPO_DENYLIST` mechanism.
**Bonus finding:** the scan surfaced 4 scanner-fixture repos NOT in the current denylist, each hosting `prompt-injection-test` fixture skills: `majiayu000/claude-skill-registry`, `majiayu000/claude-skill-registry-data`, `liminal-ai/skill-scanner-ts`, `RekitRex21/Dino_Scan`. The plan should include a manual-verify-then-extend-denylist task for these (same class as the two already listed).

### Pitfall 5: `'ip'` distance sign confusion
**What goes wrong:** hnswlib `'ip'` space returns `1 − dot` as "distance"; treating it as similarity inverts rankings.
**How to avoid:** convert in `ann.js` (`sim = 1 − distance`) and unit-test against the exact engine on a fixture (both engines must return identical neighbor sets + sims within 1e-5 on small N).

### Pitfall 6: EMBED_DRY_RUN fake vectors through the new path
**What goes wrong:** Fake vectors repeat a 32-byte SHA pattern across 1536 dims (effectively a 32-dim subspace) — pairwise similarities are unusually high, so dry-run fixtures may produce many "duplicates."
**How to avoid:** this is already true of the exact path today; tests must assert determinism/shape, not specific dup counts, on dry-run data. HNSW handles the vectors fine (non-zero norm).

### Pitfall 7: compute-similar memory shape
**What goes wrong:** holding 51k × 1536 float64 JS arrays (~630 MB+ heap) AND Float32 copies risks pressure on the 16 GB runner alongside the Astro build.
**How to avoid:** after normalization to Float32Array (~313 MB), drop references to the parsed `values` arrays before querying (replace in-place); the metadata map is small. The native index holds its own copy (~330 MB off-heap). Total well under runner RAM.

## Open Questions

1. **hnswlib-node compile + build/query wall-clock on ubuntu-latest at 51k×1536**
   - What we know: gcc is preinstalled on the runner image; node-gyp compiles of single-addon packages typically run 30–90 s; hnswlib C++ distance kernels run 5–15 GMAC/s/thread with AVX2 → build ~2–4 min, 51k queries ~1–3 min (estimates).
   - What's unclear: exact figures on the 4-vCPU runner.
   - Recommendation: make the first CI task a benchmark gate (build index from the real cached skill-vectors.ndjson, log timings, assert < 15 min total) before wiring consumers. LOW risk, cheap to verify.
2. **Real-vector recall at 0.92 threshold (vs synthetic)**
   - What we know: published HNSW recall at M=16/efC=200/efS≥100 is typically >0.95–0.99; our error mode is misses-only; real embedding clusters are dense near 0.92+.
   - What's unclear: exact pair-recall on OUR vectors. Local measurement impossible (local skill-vectors.ndjson is the stale 1,078-vector Phase-1 seed; the real ~51k-vector file lives only in the GHA cache).
   - Recommendation: validation harness runs in CI where the warm cache exists (see Validation Architecture). Gate thresholds tunable at plan time (suggested: pair-recall ≥ 0.995, is_duplicate flap < 0.5%).
3. **Stored-dims pricing footnote (does not affect this phase)**
   - The official pricing page reads "$0.05 per 100 million" stored dims with 10M included, while CLAUDE.md's budget assumes $0.05/M with 5M included (~$30/yr at 55M dims). If the docs reading is right, the actual stored-dims overage is ~$0.30/yr, not $30 — the budget may be overstated. No action this phase; flag for the next budget review.

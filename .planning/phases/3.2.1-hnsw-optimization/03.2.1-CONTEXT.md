<decisions>
## Implementation Decisions

### Approach selection (user-locked)
- User has confirmed OK with approximate-NN trade-offs (handoff line: "User has confirmed
  OK with approximate-NN trade-offs").
- Research MUST thoroughly evaluate BOTH primary candidates plus any other viable options:
  1. **hnswlib-node** — local HNSW index, O(N²) → ~O(N log N), minutes instead of hours.
  2. **Cloudflare Vectorize queries** — embeddings are ALREADY uploaded there (it's an ANN
     index); fetch top-K neighbors at build time, possibly avoiding a local lib entirely.
     Check Vectorize query limits + cost at 50k+ records.
  3. **Other options** — other ANN libs (e.g. faiss-node, usearch, voy), GPU-free exact
     methods (matrix blocking / BLAS), LSH/blocking approaches. User explicitly wants to
     "thoroughly understand it and any other potential options."
- The final approach choice is presented with a cost/limits comparison; user decides at
  plan review if research surfaces a genuine toss-up. If one option clearly dominates,
  recommend it.

### Cost posture (user-locked, this session)
- Added cost is acceptable but NOT ideal — not a deal breaker. Surface the actual numbers.
- Current ceiling context: ~$102/yr (CLAUDE.md Constraints). Anything that breaks it
  requires explicit approval — so the comparison table must show projected annual cost
  per option (Vectorize query pricing at ~51k records × daily runs; hnswlib = $0 marginal).

### Quality/correctness constraints
- Dedup threshold 0.92 cosine stays (empirically validated; do not re-litigate).
- Novelty remains percentile-based (top 5%) — do not reintroduce absolute 0.45 gate.
- Enrichment-preservation contract must survive: `PRESERVED_FIELDS` semantics in filter.js
  (including `bundled_in_plugins`), graceful degradation when enrich fails.
- Approximate-NN recall trade-off is accepted, but research should quantify expected recall
  (HNSW typical >0.95 recall@K with sane ef/M params) so the decision is informed.

### Operational constraints
- Daily cron must keep completing under 360 min with the catalog continuing to grow
  (~50,959 skills now, growing daily). Target: enough headroom to re-enable the plugin
  pipeline steps (~48 min projected in 3.2 audit) and keep growing.
- Pipeline footguns apply (CLAUDE.md): NDJSON streaming I/O only, no giant string
  materialization, banned-pattern lint (`npm run check:patterns`) must stay green.
- Windows ARM64 dev box: wrangler cannot run locally; Vectorize interactions must be
  testable via REST API or in CI only. Local dev of an hnswlib path must work on
  win32-arm64 (check native build support!) — or be CI-only with a documented dev story.
- `EMBED_DRY_RUN` deterministic fake vectors must keep working for CI/smoke paths.

### Audit B content-scanner (folded in)
- Repo-level denylist (`FIXTURE_REPO_DENYLIST`) already exists; Audit B adds CONTENT
  scanning: curl|bash exfil + jailbreak/injection markers.
- Tuned against false positives: 95 legit example-path skills + legit security-education
  skills must survive. NOT a blanket path filter.

### Claude's Discretion
- Where the ANN index build lives in the pipeline (enrich step, separate step, or shared
  helper consumed by both compute-similar and enrich).
- HNSW parameters (M, efConstruction, efSearch) — benchmark-driven.
- Whether compute-similar and enrich share one index build or build twice.
- Exact content-scanner rule set and where it slots in filter-rules/.
- Test strategy details (fixture sizes, recall measurement methodology).

<specifics>
## Specific Ideas

- Warm-run timing breakdown for sizing (handoff): Track1+2 ~25m · filter ~0 · embed
  (incremental, warm cache) ~5m · enrich ~59m · build >162m. Build dominates; enrich is #2.
- Vectorize already holds the embeddings (uploaded daily via upload-vectors); metadata
  carries `entity_type`. The worker queries it for `/api/v1/search`.
- Vectorize pricing dimension to check: queried dims + stored dims; the ~$30/yr overage
  line in the current budget is STORED-dim overage at 55M dims. 51k top-K queries/day is
  the new cost driver to size.
- If "related skills" UI feels sparse post-HNSW, TOP_K can go back to 5 — with ANN the
  runtime cost of K is no longer the issue.
- HNSW index could potentially be GHA-cached across runs (like skill-vectors.ndjson) with
  incremental inserts — worth evaluating vs. rebuild-each-run (rebuild at 51k is likely
  only ~1-2 min, so simplicity may win).

</specifics>

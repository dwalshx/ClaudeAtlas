<domain>
## Phase Boundary

Make `scripts/scrape-plugins.js` plugin/MCP discovery **incremental** so the
plugin pipeline fits the daily-scrape CI budget (whole daily run — skills +
plugins + build + deploy — under the 360-min GH Actions platform cap, with
margin), then **re-enable** the pipeline by flipping `PLUGINS_ENABLED='true'` on
main. This is the one remaining step from Phase 3.3 (all plugin/MCP page code +
the bootstrap release/cache already shipped).

**In scope:** the discovery/walk rework (A+B+C below), the cache-wiring fix, a
mandatory branch measurement before the main flip, the flag flip + first-warm-run
observation.

**Out of scope:** any change to plugin/MCP scoring, filtering, page rendering, or
the data model. No new paid services (≤$102/yr ceiling). Skills Track 1/Track 2
behavior is untouched (the plugin path AND-combines with its existing gates).
</domain>

<decisions>
## Implementation Decisions

### Scope — LOCKED: Full A+B+C (research-recommended)
The user selected the full scope. All three coordinated changes ship in 3.4:

- **A — Fix the cache-wiring bug (the budget fix, MUST-HAVE).** `loadCheckpoint()`
  reads `data/plugins-raw.ndjson.partial` but the GHA cache + bootstrap only
  persist the OUTPUT `data/plugins-raw.ndjson`, so `processedSet` starts empty
  every run and all ~7,300 repos are re-walked. Seed `processedSet` from the
  cached OUTPUT file so a warm run skips known repos and only walks the NEW-repo
  delta. This alone makes the daily run fit. (See RESEARCH §Recommended Approach,
  §Common Pitfalls — the `.partial`-vs-OUTPUT mismatch.)
- **B — GraphQL batch engagement-refresh of known repos.** Mirror
  `scripts/scrape-pulse.js`'s `fetchRepoBatchGraphql` (the proven Track-1 GraphQL
  batch from quick-260603-e96) to refresh stars/forks/issues/pushed_at for known
  plugin repos on GraphQL's SEPARATE 5,000-pts/hr budget (~1 point/batch), so
  skipping their REST walk doesn't freeze engagement data.
- **C — `pushed_at` re-walk gate (completeness).** A known repo that ADDS a
  component (new skill/command/agent) has no new repo ID, so the skip would miss
  it. Gate a component re-walk on the repo's `pushed_at` advancing since last
  capture, ideally via a single recursive `GET /repos/{o}/{r}/git/trees/{sha}?
  recursive=1` call instead of N contents-API calls. (Mirrors Track 2's
  content_sha/blob-sha change-detection precedent in scrape-discover-repos.js.)

### Measure-before-flip — LOCKED (non-negotiable, Pitfall 5)
The `PLUGINS_ENABLED='true'` flag is flipped on main ONLY AFTER a feature-branch
dispatch of `daily-scrape.yml` (branch runs are publish/deploy/KV/commit-gated to
main — safe) measures the warm plugin-discovery wall-clock AND the TOTAL job
duration, and confirms it fits under 360 min with margin. A plugin-step overrun
would kill the run before the unreplayable `data/history/<today>.json` snapshot
commits. This mirrors the Phase 3.3 Plan 07 discipline.

### Staleness / periodic full re-walk — Claude's discretion (recommend)
Recommend a periodic FULL re-walk safety net (e.g. weekly, or an N-day shard) so
drift can't accumulate indefinitely even with A+B+C — but keep it cheap and
within budget. Planner picks the cadence + mechanism; document it.

### Engineering constraints — LOCKED
- **Streaming NDJSON only** on `data/` files (V8 ~536 MB ceiling): use
  `scripts/lib/ndjson.js` helpers; NEVER `readFileSync(...,'utf-8')` on data/
  files. `npm run check:patterns` must stay green.
- **Reuse, don't hand-roll:** the GraphQL client/batcher from `scrape-pulse.js`,
  the skip/checkpoint + change-detection patterns from `scrape-discover-repos.js`,
  `scripts/lib/ndjson.js` writers. (RESEARCH §Don't Hand-Roll.)
- **Daily history snapshot contract** must hold (the gate's whole purpose).
- The bootstrap release/cache + plugin/MCP page code from 3.3 stay as-is; 3.4
  must work WITH the warm `plugins-raw.ndjson` cache.

### Claude's Discretion
Function decomposition, exact GraphQL query shape + batch size (aliased nodes),
the tree-sha change-detection data structure, where the periodic full re-walk is
triggered, test fixtures. Follow RESEARCH §Code Examples patterns.
</decisions>

<specifics>
## Specific Ideas

- Quantify in a plan task: how much of the 24h the wiring bug (A) explains vs the
  genuine new-repo walk — the measurement showed ~1,700 repos in 5.5h from an
  empty processedSet.
- GraphQL point cost = ceil(connection-requests / 100) → an aliased multi-repo
  batch ≈ 1 point; size batches accordingly (RESEARCH §Code Examples).
- `search/code` discovery can NOT be recency-filtered (no `pushed:`); keep the
  cheap full search/code discovery for the repo SET, do the incremental work in
  the per-repo walk stage.
- Budget projection target (RESEARCH §Budget Projection): plugin subtotal
  ~21-46 min → combined ~290-330 min vs 360 cap. The branch measurement validates
  the real number against the now-~50k skills baseline.
</specifics>

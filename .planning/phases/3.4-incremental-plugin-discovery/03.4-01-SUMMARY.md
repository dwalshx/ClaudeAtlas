# Phase 3.4 Plan 01: Cross-run skip-wiring fix (Change A) Summary

**`loadCheckpoint()` now seeds `processedSet` from the cached OUTPUT `data/plugins-raw.ndjson` (merged with the same-job `.partial`, `.partial` winning per-repo), so a warm plugin run skips the ~7,300 known repos and walks only the daily new-repo delta — collapsing the ~24h cold sweep that caused the 3.3 re-enable NO-GO.**

## Accomplishments

- **Change A (the mandatory budget fix) landed.** `processedSet` is now seeded from the cached, bootstrapped OUTPUT corpus instead of the never-cached `.partial`. This is the single biggest win identified by RESEARCH §A — a warm run skips the entire known corpus at zero REST cost.
- **`buildProcessedSeedFrom(outputPath, partialPath)`** added as an exported, path-injectable pure helper: unions OUTPUT + `.partial` keyed by `repo_full_name`, `.partial` winning per-repo (fresher), `processedSet` = union of both files' names.
- **R-2 regression test (3 cases)** pins the contract that would have caught the original bug: OUTPUT seeds `processedSet` (size === N — the bug-catching case), OUTPUT+`.partial` merge with `.partial` winning on conflict, and the warm-run case (OUTPUT present, `.partial` absent).
- **Pitfall-1 instrument:** a `resume: N known repos seeded from OUTPUT+partial` log line in `main()` lets Plan 04's branch measurement confirm the counter starts near ~7,300 rather than 0.

## Decisions Made

- **Seed from OUTPUT, merge `.partial`** (RESEARCH Q1 option a) rather than adding a `.partial` cache step (option b): the OUTPUT is already cached + bootstrapped and is the authoritative completed corpus; `.partial` is a within-run artifact.

- **Left the `main()` skip loop (`if (processedSet.has(repoName)) continue`, line 363) untouched** — it was already correct; the bug was purely the read path feeding an empty `processedSet`.

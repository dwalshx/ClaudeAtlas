# Phase 3.4: Incremental Plugin Discovery — Research

**Researched:** 2026-06-14
**Domain:** GitHub REST/GraphQL rate-limit economics; incremental discovery wiring; in-repo Track-1/Track-2 precedents
**Confidence:** HIGH (all recon seeds code-verified with line numbers; GraphQL economics + negative claims verified against official GitHub docs)

## Summary

The plugin sweep died at ~24h because **every daily run re-walks all ~7,300 repos from scratch** — and the dominant reason is a **cache-wiring bug, not an algorithmic limit.** `loadCheckpoint()` (scrape-plugins.js:318) reads `PARTIAL_PATH` = `data/plugins-raw.ndjson.partial`, but the GHA cache and the bootstrap release only ever save/restore the OUTPUT file `data/plugins-raw.ndjson`. The `.partial` never survives between runs, so `processedSet` starts empty every time and the `if (processedSet.has(repoName)) continue` skip (line 363) never fires. The output file — which already contains all ~7,300 walked repos — sits in the cache, restored, and is simply never read by the resume path.

Fixing that one wire makes a warm run skip ~7,300 known repos and walk only the **daily delta of NEW plugin repos** (a few dozen, found via `search/code`). That alone is expected to bring plugin discovery from ~24h to **single-digit minutes warm.** But skip-only freezes the stars/components/manifests of known repos forever, and it never re-detects a known repo that ADDS a component. So the prescriptive design is three coordinated changes, in order: **(1) wire the skip correctly (seed `processedSet` from the cached OUTPUT), (2) add a Track-1-style GraphQL batch refresh of known plugin repos' engagement signals (mirror `scrape-pulse.js`), and (3) add a cheap repo-level `pushed_at` change-gate that re-walks only the small set of known repos that changed since last scrape.** GraphQL is needed for the refresh (separate 5,000-pts/hr budget, ~1 pt/batch), but is NOT needed to make the daily walk fit — the skip fix does that.

**Primary recommendation:** Ship skip-fix + GraphQL engagement-refresh + pushed_at re-walk gate, mirroring the exact split already proven for skills (Track 1 GraphQL pulse + Track 2 incremental discovery). Projected warm plugin step: **~8-15 min**; total daily run **~300-310 min**, comfortably under the 360-min cap.

## Recommended Approach

Ship these in order. A and the ordering are mandatory; B and C are both recommended (B is cheap and high-value; C closes the completeness gap).

### A. Fix the cross-run skip wiring (MANDATORY, the single biggest win)

**Root cause (verified):** `loadCheckpoint()` (scrape-plugins.js:318-320) reads only `PARTIAL_PATH` (`data/plugins-raw.ndjson.partial`). The daily workflow's "Restore plugins-raw cache" step (daily-scrape.yml:202-210) and the bootstrap release (`bootstrap-plugins-raw.yml`) cache/seed only the OUTPUT `data/plugins-raw.ndjson`. The `.partial` is a within-run checkpoint that is NEVER cached across runs (no cache step references it — verified: `grep partial .github/workflows/` finds only comments). So on every CI run `existsSync(PARTIAL_PATH)` is false, `loadCheckpoint()` returns `{ repos: [], processedSet: new Set() }`, and the line-363 skip never fires. **The output file with all ~7,300 walked repos is restored and ignored.**

> Note: the *format* bug recon seed #2 hypothesized was already fixed in 3.3-01 (commit 3b62b96) — `loadCheckpointFrom` now correctly reads NDJSON via `readNdjsonRecords`. The REMAINING bug is purely the path mismatch: it reads the wrong file (the un-cached `.partial`), not the cached OUTPUT.

**Fix (prescriptive):** Make the resume path seed `processedSet` from the cached **OUTPUT** file, falling back to `.partial` only for mid-run resume within the same job. Concretely: in `main()` build `processedSet` from a union of OUTPUT (`OUTPUT_PATH`) and PARTIAL (`PARTIAL_PATH`), preferring OUTPUT records (they are the completed corpus). `loadCheckpointFrom` is already path-injectable and exported — call it on both paths and merge. See Code Examples §1.

**Why this is the win:** A warm run then skips ~7,300 known repos at zero REST cost (they're already in `processedSet`) and only walks the daily delta of genuinely-new plugin repos surfaced by `discoverPluginRepos()`. The discovery `search/code` pass is cheap (≤240 search calls, ~27 min floor worst-case — see Q4) and the new-repo walk is a few dozen × ~6 REST calls. Quantified: of the ~24h extrapolation, the skip fix removes essentially all of the per-repo walk on warm runs — the ~35k-70k REST calls collapse to the discovery search + a small new-repo tail.

### B. GraphQL engagement refresh of known plugin repos (RECOMMENDED — mirror scrape-pulse.js)

Skip-only freezes known repos' `stars`/`forks`/`open_issues`/`pushed_at`/`topics`/etc. at last-walk values. The scorer (stars 20%, recency 20%) drifts stale. Mirror Track 1 **exactly**: a batched GraphQL `repository(...)` query, 50 repos/alias-batch, ~1 point/batch, on GraphQL's SEPARATE 5,000-pts/hr budget. At ~7,300 plugin repos that is ~146 batches ≈ ~146 points/hr-equivalent and ~2-4 min wall-clock — trivial. Reuse `scripts/lib/github-graphql.js` `fetchRepoBatchGraphql` (already returns the 11 freshness fields) and `SCRAPE_PAT_CLASSIC` (classic PAT required — fine-grained is 403'd by GraphQL; verified in github-graphql.js header). Write the refreshed fields back into the existing `plugins-raw.ndjson` records in-place before filter-plugins runs.

This also supplies the `pushed_at` signal that powers C.

### C. pushed_at re-walk gate for known repos (RECOMMENDED — closes the completeness gap)

Skip + refresh still won't catch a KNOWN repo that ADDS a new skill/command/agent to its plugin (no new repo, changed components). Use the **same change-detection idea as Track 2's blob-sha skip** (scrape-discover-repos.js:366), but at repo granularity: store the `pushed_at` captured at last component-walk on each record. On the daily run, for each known repo whose FRESH `pushed_at` (from the GraphQL refresh in B) is newer than the stored walk-time `pushed_at`, **re-walk just that repo's component dirs** (remove it from the skip set). Repos that haven't been pushed since the last walk keep their cached components for free. This bounds the daily component-walk to (new repos) + (repos pushed since yesterday) — a small set. The vast majority of the corpus is skipped at zero cost.

> D-03 from Phase 3.3 said "don't pull forward the content-sha component-walk skip (that's 3.7)." That referred to per-COMPONENT blob-sha diffing (skip individual unchanged skill files within a repo). C here is coarser and cheaper — a repo-level pushed_at gate that decides whether to re-walk a repo AT ALL. It is the minimum needed for correctness and does not require the per-file content-sha machinery. If the planner wants to honor D-03 strictly, C can ship as a periodic full re-walk instead (see Q2 option b) — but the pushed_at gate is strictly better and low-risk.

### D. Optional: GraphQL batch component-walk (NOT needed for budget; consider only if the new-repo tail is large)

The per-repo walk could itself move to GraphQL (`object(expression:"HEAD:.claude-plugin/plugin.json"){ ... on Blob { text } }` + aliased component-dir `Tree.entries`), collapsing ~6 REST calls/repo into ~1 GraphQL point for a batch. This is the documented CLAUDE.md note-#7 lever. **But it is unnecessary once A is in place** — the warm walk only touches the small daily delta, which fits REST easily. Recommend deferring D unless the new-plugin-repo daily delta turns out large (>~500/day), which is implausible. If implemented later, it also moves the walk off the REST budget entirely. (See Q4 for the economics and the one-directory-level caveat.)

### E. Re-enable

After a branch-measured warm run confirms the budget fit AND that `filter-mcps.js` still gets its `mcp-servers/` entries, flip `env.PLUGINS_ENABLED: 'false' → 'true'` (daily-scrape.yml:77). No structural workflow change needed — the 9 gated steps already exist and AND-combine the flag (verified daily-scrape.yml:204-378). This is a CHECKPOINT/human-gated step, exactly like the 3.2.1 validation run.

| `scripts/lib/github-fetch.js` (`rateLimitedFetch`, `fetchWithETag`) | discovery search + new-repo walk (A/D) | REST with 403/retry-after handling + ETag 304-free caching | Track 2 uses it; ETag makes warm tree-fetches free |
| `scripts/lib/ndjson.js` (`readNdjsonRecords`, `writeNdjsonStreaming`) | all data/ I/O | V8-string-limit-safe streaming NDJSON | MANDATORY — banned-pattern lint (`npm run check:patterns`) |

**GitHub API budgets (verified against official docs):**
- REST: **5,000 requests/hr** per PAT. 304 conditional responses do NOT count (CLAUDE.md fact #2).
- GraphQL: **5,000 points/hr** per PAT, **separate budget** from REST. Secondary cap: 2,000 points/min. Point cost = (requests to fulfill connections) / 100, rounded — so an aliased multi-repo `repository()` query with shallow connections costs **~1 point regardless of repo count in the batch** (verified: https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api).

**No `npm install` needed.** Zero new dependencies.

## Architecture Patterns

### Mirror the skills two-track split (the proven model)

```
SKILLS (working today):
  Track 1 (scrape-pulse.js)     → GraphQL batch refresh of KNOWN repos' engagement → in-place update + history snapshot
  Track 2 (scrape-discover.js)  → REST repo-search for NEW/changed, skip-known-IDs, blob-sha change-detect

PLUGINS (this phase — same shape):
  Refresh pass (NEW, mirror Track 1) → GraphQL batch refresh of KNOWN plugin repos' engagement (B)
  Discovery pass (existing, FIXED)   → search/code for repos, seed processedSet from cached OUTPUT (A),
                                        re-walk only repos with pushed_at newer than stored walk-time (C),
                                        walk NEW repos via REST (or GraphQL batch, D)
```

### Recommended structure of the change

Keep it in `scripts/scrape-plugins.js` (do NOT split into a separate file unless the planner prefers a `scrape-plugins-pulse.js` mirror of scrape-pulse.js). Minimal-blast-radius edits:

1. **Resume seed (A):** rewrite `loadCheckpoint()` to merge OUTPUT + PARTIAL (Code Examples §1).
2. **Engagement refresh (B):** add a pre-walk pass that loads the cached corpus, batches all known `repo_full_name`s through `fetchRepoBatchGraphql`, and writes fresh fields back. Gate its env to `SCRAPE_PAT_CLASSIC` in the workflow step (mirror the Track 1 step's `GITHUB_TOKEN: ${{ secrets.SCRAPE_PAT_CLASSIC }}`).
3. **Re-walk gate (C):** add `walked_pushed_at` to each record at walk time; in the main loop, a known repo is skipped UNLESS `freshPushedAt > record.walked_pushed_at`.
4. **MCP preservation:** the walk MUST keep populating `components["mcp-servers"].entries[]` and `component_summary.mcp_servers` — `filter-mcps.js` derives every MCP record from those (verified filter-mcps.js:60-69, 143-148). Don't drop them in any refactor.

### Workflow wiring

The daily-scrape plugin steps already exist and are gated. If B is a new step (recommended for clean `SCRAPE_PAT_CLASSIC` auth), add ONE step before "Run plugin discovery", gated identically (`env.PLUGINS_ENABLED == 'true' && github.event_name != 'push'`). Alternatively fold B into scrape-plugins.js and set `GITHUB_TOKEN: SCRAPE_PAT_CLASSIC` on the existing discovery step — but then the REST walk in the same process would use the classic PAT for REST too (works, but mixes budgets). **Recommend a separate refresh step** with the classic PAT, matching the Track1/Track2 separation exactly.

### Anti-patterns to avoid

- **Caching `.partial` instead of fixing the read.** You could add a cache step for `plugins-raw.ndjson.partial`, but the OUTPUT is already cached and is the authoritative completed corpus. Seed from OUTPUT; treat `.partial` as a same-job resume only. (See Pitfall #1.)
- **Recency-filtering `search/code`.** Impossible — code search has no `pushed:`/`created:`/`updated:`/`sort:` (verified). Recency filtering must happen at the repo level (GraphQL `pushed_at` of known repos, or `search/repositories?q=...pushed:>` for a discovery variant). See Pitfall #2.
- **Dropping `components["mcp-servers"]` in a GraphQL walk rewrite.** Breaks filter-mcps.js silently (Pitfall #6).

## Common Pitfalls

### Pitfall 1: The `.partial`-vs-OUTPUT wiring bug (THE root cause)
**What goes wrong:** `loadCheckpoint()` reads `data/plugins-raw.ndjson.partial`; only `data/plugins-raw.ndjson` is cached/bootstrapped. The `.partial` never exists at run start → `processedSet` is empty → all ~7,300 repos re-walked → ~24h → timeout. The restored OUTPUT corpus is silently ignored by the resume path.
**Why it happens:** The checkpoint writes `.partial` mid-run, but the workflow's `if: always()` save step (daily-scrape.yml:225-231) saves only `plugins-raw.ndjson`, and the bootstrap seeds only `plugins-raw.ndjson`. The read path and the persistence path point at different files.
**How to avoid:** Seed `processedSet` from `loadCheckpointFrom(OUTPUT_PATH)` (merge with `.partial` for same-job resume). See Code Examples §1.
**Warning sign:** Log line "Processing [N/?]" counter climbing from a low number toward 7,300 instead of starting near 7,300 with a tiny "new this run" delta. (The measurement saw exactly this.)
**Quantified:** This bug explains essentially ALL of the warm-run cost. With it fixed, a warm run skips the entire known corpus; without it, the run is a cold full sweep every single day.

### Pitfall 2: Trying to recency-filter `search/code`
**What goes wrong:** `filename:plugin.json path:.claude-plugin pushed:>2026-06-01` is treated as literal text or ignored — code search has NO date/sort qualifiers (verified vs official docs). You'd get a silent wrong result set, exactly like the 3.0.0 skills bug (CLAUDE.md fact #3).
**How to avoid:** Discovery of NEW repos stays on the full `search/code` sweep (it's cheap, ≤240 calls). Recency is applied at the REPO level: GraphQL `pushed_at` of known repos (C), or a `search/repositories?q=topic:claude-plugin pushed:>` variant (repo search DOES support the full qualifier set — verified, and Track 2 already relies on this).

### Pitfall 3: GraphQL points exhaustion / wrong mental model
**What goes wrong:** Assuming a 50-repo aliased query costs 50 points and rationing batches too hard, OR assuming it's free and hammering the 2,000-pts/min secondary cap.
**Reality (verified):** Point cost = (connection requests)/100 rounded → an aliased `repository()` batch with shallow connections is ~1 point. ~146 batches for 7,300 repos ≈ ~146 points — well under 5,000/hr. But keep the inter-batch delay (scrape-pulse uses `BATCH_DELAY_MS = 100`) so ~146 serial queries can't trip the 2,000-pts/min secondary limit.
**How to avoid:** Reuse `fetchRepoBatchGraphql` + a small inter-batch sleep verbatim. Don't re-derive the batching.

### Pitfall 4: Wrong PAT on the GraphQL pass
**What goes wrong:** Using the fine-grained `SCRAPE_PAT` for the GraphQL refresh → 403 on every batch (fine-grained PATs are rejected by GitHub's GraphQL endpoint — documented in github-graphql.js:1-9 and the retired commit 1e5d1a5 episode).
**How to avoid:** GraphQL step uses `GITHUB_TOKEN: ${{ secrets.SCRAPE_PAT_CLASSIC }}` (classic PAT). REST discovery/walk stays on `SCRAPE_PAT`. The CRITICAL DIAGNOSTIC FIX (github-graphql.js:175-187) now logs the body on non-OK so this is diagnosable if it recurs.

### Pitfall 5: Flipping `PLUGINS_ENABLED` before a branch measurement → history-snapshot loss
**What goes wrong:** If the plugin step still overruns, the job dies at "Run plugin discovery" BEFORE the skills history-snapshot commit. `data/history/<today>.json` is unreplayable — that day of star data is permanently lost (CLAUDE.md Pitfall 5; this is the original gating reason).
**How to avoid:** Measure on a feature branch first (branch runs are publish/deploy-gated to main, so they exercise scrape→filter→build without touching prod — daily-scrape.yml:388,431,451,567). Only flip the flag on main after the warm run is green AND under budget. Structure as a plan gate, not a code task.

### Pitfall 6: Breaking MCP discovery in a walk refactor
**What goes wrong:** `filter-mcps.js` derives EVERY mcp_server record from `components["mcp-servers"].entries[]` + `component_summary.mcp_servers` on the repo-level raw record (verified filter-mcps.js:60-124). It has a `MIN_MCP_REPOS = 10` pre-flight that FATALs if fewer than 10 repos carry MCP components. Any walk change that drops or renames the `mcp-servers` component key makes filter-mcps.js exit 1.
**How to avoid:** Preserve `COMPONENT_DIRS` including `'mcp-servers'` (scrape-plugins.js:243) and the `inventory[dir]` shape. If moving to a GraphQL walk (D), explicitly alias the `mcp-servers/` directory `Tree.entries`. Verify on the branch run that `filter-mcps.js` reports ≥10 MCP repos.

### Pitfall 7: NDJSON streaming rule
**What goes wrong:** Adding a `JSON.parse(readFileSync('data/plugins-raw.ndjson'))` or `JSON.stringify(records, null, 2)` for the refresh pass → V8 ~536 MB string crash at scale AND a `check:patterns` lint failure.
**How to avoid:** All reads via `readNdjsonRecords`, all writes via `writeNdjsonStreaming`. `plugins-raw.ndjson` is ~26 MB today and growing.

## Code Examples

### §1 — Seed processedSet from the cached OUTPUT (the fix for Pitfall 1)

```javascript
// scripts/scrape-plugins.js — replace loadCheckpoint() (currently line 318-320)
// loadCheckpointFrom is already exported + NDJSON-correct (line 307). Merge
// OUTPUT (the cached, completed corpus) with PARTIAL (same-job mid-run resume).
function loadCheckpoint() {
  const fromOutput = loadCheckpointFrom(OUTPUT_PATH);   // cached + bootstrapped — the real corpus
  const fromPartial = loadCheckpointFrom(PARTIAL_PATH); // same-job checkpoint, may be empty
  // Prefer completed OUTPUT records; let a fresher PARTIAL override if present.
  const byName = new Map();
  for (const r of fromOutput.repos) byName.set(r.repo_full_name, r);
  for (const r of fromPartial.repos) byName.set(r.repo_full_name, r); // partial wins (newer)
  const repos = [...byName.values()];
  return { repos, processedSet: new Set(repos.map(r => r.repo_full_name)) };
}
```

Add a regression test: write N records to `OUTPUT_PATH` via `saveCheckpointTo`, call `loadCheckpoint()`, assert `processedSet.size === N`. (This is the test the measurement would have caught.)

### §2 — Engagement refresh of known plugin repos (mirror scrape-pulse.js)

```javascript
// New pre-walk pass in scrape-plugins.js. Requires GITHUB_TOKEN = SCRAPE_PAT_CLASSIC
// on this step (GraphQL rejects fine-grained PATs).
import { fetchRepoBatchGraphql } from './lib/github-graphql.js';

const BATCH_SIZE = 50, BATCH_DELAY_MS = 100;

async function refreshKnownRepos(records) {            // records = cached plugins-raw corpus
  const names = [...new Set(records.map(r => r.repo_full_name).filter(Boolean))];
  const fresh = new Map();
  for (let i = 0; i < names.length; i += BATCH_SIZE) {
    const { freshByRepo } = await fetchRepoBatchGraphql(names.slice(i, i + BATCH_SIZE));
    for (const [name, fields] of freshByRepo) fresh.set(name, fields);
    await new Promise(r => setTimeout(r, BATCH_DELAY_MS));   // stay under 2000 pts/min
  }
  // Map GraphQL field names → plugins-raw record field names (stars/forks/etc).
  for (const r of records) {
    const f = fresh.get(r.repo_full_name);
    if (!f) continue;
    r.stars = f.repo_stars; r.forks = f.repo_forks; r.open_issues = f.repo_open_issues;
    r.pushed_at = f.repo_pushed_at; r.topics = f.repo_topics; r.archived = f.repo_archived;
    r.license = f.repo_license; r.language = f.repo_language; r.description = f.repo_description;
    r.default_branch = f.repo_default_branch ?? r.default_branch;
  }
}
```
(~146 batches for ~7,300 repos ≈ ~146 GraphQL points, ~2-4 min. Note the field-name
mapping: github-graphql returns `repo_*`-prefixed keys; plugins-raw records use the bare
`fetchRepoMetadata` shape — stars/forks/open_issues/pushed_at — so map explicitly.)

### §3 — pushed_at re-walk gate (change-detection, mirror Track 2's skip)

```javascript
// In the main loop, AFTER seeding processedSet (§1) and refreshing (§2).
// Record walk-time pushed_at when a repo is walked:
record.walked_pushed_at = meta.pushed_at;   // add to the record built at line 405

// Decide whether a KNOWN repo needs re-walking:
const known = byName.get(repoName);                 // from the cached corpus
const freshPushedAt = known && fresh.get(repoName)?.repo_pushed_at;
const changed = known && freshPushedAt && known.walked_pushed_at
  && freshPushedAt > known.walked_pushed_at;
if (processedSet.has(repoName) && !changed) {
  continue;   // unchanged known repo — keep cached components for free
}
// else: new repo OR pushed-since-last-walk → fall through to the component walk
```

### §4 — (Optional, D) GraphQL batch component-walk shape

```graphql

    mk:  object(expression: "HEAD:.claude-plugin/marketplace.json") { ... on Blob { text } }
    skills:   object(expression: "HEAD:skills")      { ... on Tree { entries { name type path } } }
    agents:   object(expression: "HEAD:agents")      { ... on Tree { entries { name type path } } }
    commands: object(expression: "HEAD:commands")    { ... on Tree { entries { name type path } } }
    hooks:    object(expression: "HEAD:hooks")       { ... on Tree { entries { name type path } } }
    mcp:      object(expression: "HEAD:mcp-servers") { ... on Tree { entries { name type path } } }
  }
  # r1: ... up to ~25-30 repos/query (keep node count modest; still ~1 point)
}
```
Caveat: GraphQL `Tree.entries` is single-level; the REST walk already only lists
the component dir's immediate entries (scrape-plugins.js:266-273), so parity holds.
The path variants (`dir`, `.claude-plugin/dir`, `.claude/dir`) would each need an
alias if you want full parity with walkComponentDirs' fallbacks.

## Open Questions

### Q1 — Cross-run skip fix: which mechanism? → RESOLVED: seed from cached OUTPUT
Three options: (a) seed `processedSet` from OUTPUT, (b) also cache the `.partial`, (c) `loadCheckpoint` fall back to OUTPUT.
**Recommendation: (a) seed from OUTPUT, merging `.partial` for same-job resume** (Code Examples §1). Rationale: OUTPUT is ALREADY cached + bootstrapped + is the authoritative completed corpus; `.partial` is a within-run artifact. (b) adds a redundant cache entry for a file that duplicates OUTPUT. (c) is a subset of (a). Confidence: HIGH.

### Q2 — Staleness vs freshness → RESOLVED: GraphQL refresh (B), every run
(a) GraphQL batch refresh of known repos, (b) accept staleness + periodic full re-walk, (c) both.
**Recommendation: (a) every run for engagement signals + (C) pushed_at gate for component changes.** This mirrors skills exactly (Track 1 refreshes daily; Track 2 catches structural changes). Cost is ~3 min on the separate GraphQL budget — there's no reason to accept staleness. A periodic (e.g. weekly) FULL re-walk is a cheap belt-and-suspenders for repos whose `pushed_at` somehow didn't change but components did (rare); recommend a weekly full re-walk via `workflow_dispatch` or a `day-of-week % 7` shard as a safety net, NOT the primary mechanism. Confidence: HIGH.

### Q3 — Completeness / change-detection → RESOLVED: repo-level pushed_at gate
Catching a known repo that ADDS a component: use the fresh `pushed_at` (from B) vs a stored `walked_pushed_at` (Code Examples §3). This is the Track-2 blob-sha idea at repo granularity. **Verified: GitHub REST `git/trees?recursive=1` returns the full inventory in ONE call** (Track 2 uses it, scrape-discover-repos.js:152-168) — so an alternative to the multi-call `walkComponentDirs` is a single recursive tree fetch per changed repo, filtering paths under the component dirs. That would cut the per-changed-repo walk from ~6 calls to ~1 (ETag-cacheable, 304-free on warm). **Recommend switching `walkComponentDirs` to a single recursive-tree scan** for changed repos — it's strictly cheaper and reuses the proven Track-2 pattern. Confidence: HIGH (tree recursive verified in-repo + official REST docs).

### Q4 — Is GraphQL NEEDED for the per-repo walk? → RESOLVED: NO (skip-fix is enough)
GraphQL economics (verified): aliased `repository()` batch = ~1 point/query (cost = connection-requests/100 rounded). ~25-30 repos/query is comfortable; 5,000 pts/hr is effectively unlimited for our volumes. GraphQL CAN return component-dir inventory in batch via `object(expression){ ... on Tree { entries } }` (verified — see Code Examples §4) and plugin.json/marketplace.json via `... on Blob { text }`. **But it is NOT needed for budget once A lands** — the warm walk only touches the daily delta. Recommend GraphQL ONLY for the engagement refresh (B), and defer the GraphQL component-walk (D) unless the new-repo delta proves large. One caveat if D is pursued: GraphQL `Tree.entries` is single-level (the REST recursive=1 convenience doesn't exist in GraphQL), so each component dir needs its own alias. Confidence: HIGH.

### Q5 — MCP servers → RESOLVED: same walk produces them; preserve the component shape
`filter-mcps.js` reads the SAME `plugins-raw.ndjson` and derives mcp_server records from `component_summary.mcp_servers > 0` + `components["mcp-servers"].entries[]` (verified filter-mcps.js:41,60-124,143-148). No separate MCP discovery cost — MCPs are a byproduct of the existing component walk. The ONLY MCP-specific risk is dropping the `mcp-servers` component in a refactor (Pitfall 6); the `MIN_MCP_REPOS=10` pre-flight will FATAL if you do. Verify ≥10 MCP repos on the branch run. Confidence: HIGH.

### Q6 — Budget ceiling for plugin discovery → see Budget Projection
Plugin pipeline warm subtotal ~21-46 min. The real uncertainty is the GROWN skills baseline (~260-290 min at 50k), not plugins. The branch measurement must confirm the COMBINED total under 360 with margin. If tight, split to weekly (3.2-CRON-AUDIT Option B) or move the walk to GraphQL (D). Confidence: MEDIUM on the absolute total (skills baseline has drifted since the last full audit — measure to confirm); HIGH on the plugin increment being small.

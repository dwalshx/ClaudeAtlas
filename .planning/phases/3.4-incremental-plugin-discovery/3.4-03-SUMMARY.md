# Phase 3.4 Plan 03: Incremental Plugin Discovery — Completeness Gate Summary

**Repo-level `pushed_at` re-walk gate (`shouldRewalk`) that re-walks only KNOWN plugin repos whose components may have changed, backed by a single recursive `git/trees?recursive=1` component scan (replacing ~6-18 contents calls/repo) with the `mcp-servers` component preserved, plus a weekly UTC-Sunday full re-walk safety net.**

## Accomplishments

- **Closed the completeness gap (Change C):** a KNOWN repo that ADDS a component (new skill/command/agent/MCP) is now re-discovered. `shouldRewalk(known, freshPushedAt, opts)` consumes Plan 02's fresh `pushed_at` Map and re-walks a known repo only when its fresh `pushed_at` advanced past the stored `walked_pushed_at` (or the stamp is missing, or it's the periodic-full shard). Unchanged known repos keep their cached components for free.
- **Cheaper walk:** `walkComponentDirs` now issues ONE `git/trees/{branch}?recursive=1` GET per changed repo and derives the whole component inventory from the tree (mirrors Track 2's `listSkillPaths`), replacing the COMPONENT_DIRS × 3-variants × contents-API loop. ETag-cacheable / 304-free on warm.
- **MCP preservation verified (R-5 / Pitfall 6):** the recursive walk still emits `components['mcp-servers'].entries[]` (`{name, type, path, size}`) and `component_summary.mcp_servers`, so `filter-mcps.js`'s `mcpComponentEntries` + `MIN_MCP_REPOS=10` pre-flight keep working. Sanity-checked against a fabricated tree (immediate children only, legacy `.claude/` variant resolved).
- **Safety net (CONTEXT discretion):** weekly full re-walk on UTC Sundays, with a `PLUGINS_FULL_REWALK=1` override and a `[gate] periodicFull=...` log line so Plan 04 can measure both the cheap steady-state and the worst-case full sweep.
- **No duplicate inflation:** re-walked known repos overwrite their prior `allRepos` record in place (via `indexByName`), keeping OUTPUT free of duplicate `repo_full_name`s.

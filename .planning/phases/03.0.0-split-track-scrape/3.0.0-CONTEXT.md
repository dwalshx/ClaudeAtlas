# Phase 3.0.0 — Split-Track Scrape Architecture

**Status:** Planning
**Authored:** 2026-04-20
**Precursor to:** Phase 3.0 (Comprehensive Agent Tooling Index)
**Blocks:** All Phase 3.0 sub-phases (3.1–3.9) — daily pipeline must be reliable before 3.0 can start

---

## Why now

The current single-pass scrape (`scripts/scrape.js`) cannot fit in GitHub Actions' **6-hour platform cap** on hosted runners.

Evidence from 2026-04-18 manual run (`24615067547`):
- Cancelled at exactly 6h 5m 0s (platform cap)
- Reached 25,950 of 32,083 skills (81%) before kill
- "Save ETag cache" step never ran — `if: always()` post-steps don't execute when GitHub force-kills the runner at platform cap
- All downstream steps (filter, embed, upload, build, deploy, commit) skipped
- **No data committed.** Daily snapshot for 2026-04-18 lost.

The earlier `f7d293d` fix (timeout bump 350→420 + save-on-cancel) only protects against soft cancellations. Hard platform-cap kills bypass it.

Math says the scrape is rate-limit-floored:
- ~4,320 skills processed/hour (warm cache, observed)
- 32,083 skills total
- **Minimum 7.4 hours just to touch each skill once**, before filter/embed/build/deploy
- Cannot fit in 6h regardless of optimization

## Goal

Daily scrape always completes in <30 min by splitting work into two tracks with different cadences and budgets:

- **Track 1 (Star Pulse):** light, daily, refreshes engagement signals on known repos
- **Track 2 (Discovery):** heavy, runs in two modes (incremental daily, full weekly), finds new SKILL.md files

Together they give full coverage without ever needing to fit a full-corpus scrape in 6h.

## Architecture

### Track 1 — Star Pulse (daily, fast)

**New script:** `scripts/scrape-pulse.js`

For every repo currently in `data/skills.json`:
- `GET /repos/{owner}/{name}` (single request per repo, ETag-supported, 304s are free against rate limit)
- Update fields on existing skill records: `repo_stars`, `repo_forks`, `repo_open_issues`, `repo_pushed_at`, `repo_updated_at`, `repo_archived`
- Do NOT touch: `body_markdown`, `frontmatter`, `quality_score`, `category`, or any other content-derived field

Write today's snapshot to `data/history/YYYY-MM-DD.json` (existing format, see CLAUDE.md).

**Sizing:**
- 826 repos today → cold ~1h, warm <5 min
- 20k repos post-3.0 → cold ~4h, warm ~15 min
- Always fits in 6h, even fully cold

**This is the moat-feeder.** Daily star snapshots are the foundation of `/trends`, leaderboards, and any time-series analysis. They MUST run reliably every day.

### Track 2 — Discovery (two modes)

**Refactor `scripts/scrape.js` to accept `--mode={incremental,full}`:**

**Mode: incremental** (daily, runs after Track 1)
- Code search: add `pushed:>3d` filter to all queries (was: no filter)
- 3-day buffer for safety; misses no recent content
- Expected output: 50–500 candidate skills per day
- Runs full pipeline (parse, score, categorize) but only on the small candidate set
- Merges into existing `skills-raw.json` (preserves existing entries)
- Estimated time: <30 min

**Mode: full** (weekly, Sundays)
- No `pushed:>` filter — full discovery sweep like today's scrape
- Allowed to take its 6h budget
- If killed at platform cap, the bootstrap cache + properly-saved partial cache still helps the next run converge
- Catches: dead-but-existing skills we missed, repos that change activity classification (e.g., un-archive)
- This is the safety net, not the primary feeder

### Daily snapshot integrity

The user surfaced a real risk: `pushed:>` filter alone misses stable-but-trending repos (zero recent pushes, lots of new stars).

**Resolution:** Track 1 catches these. Every indexed repo gets metadata refresh daily regardless of whether anyone pushed code. Snapshot writes from Track 1's data, not Track 2's. Snapshot is always complete.

### Workflow split

**Modify `daily-scrape.yml`:**
1. Restore ETag cache
2. Run Track 1 (`scripts/scrape-pulse.js`) → writes snapshot, updates skills.json star fields in-place
3. Run Track 2 incremental (`scripts/scrape.js --mode=incremental`) → discovers new SKILL.md, appends to skills-raw.json
4. Run filter (existing `scripts/filter.js`) → produces skills.json
5. **Re-merge Track 1 freshness into skills.json** (see "Merge semantics" risk below)
6. Continue: embed, upload-vectors, build, deploy, commit
7. Save ETag cache

**New `weekly-discover.yml`:**
- Cron: `0 3 * * 0` (Sundays 3 AM UTC)
- Steps: Restore cache, run `scripts/scrape.js --mode=full`, save cache, commit `data/skills-raw.json`
- Deliberately does NOT run the rest of the pipeline — daily-scrape's normal Track 2 incremental will pick up new entries the next day. Keeps weekly run minimal and resumable.
- 7-hour timeout (will hit 6h platform cap; that's expected and acceptable)

**Keep `bootstrap-etag-cache.yml`** as insurance for cache loss.

## Constraints

- **Free-tier GHA only.** No paid runners or larger runners.
- **Same secrets/bindings:** `SCRAPE_PAT`, `OPENAI_API_KEY`, `CF_API_TOKEN`, `CF_ACCOUNT_ID`, `PUBLIC_POSTHOG_KEY`.
- **Schema preservation:**
  - `data/skills.json` record shape unchanged (Track 1 only updates existing fields)
  - `data/history/YYYY-MM-DD.json` shape unchanged (per CLAUDE.md spec)
  - `data/skills-raw.json` shape unchanged
- **Filter calibration unchanged.** No drift from Phase 1 filter rules without re-validation (per CLAUDE.md).
- **Zero-downtime rollout.** Live site keeps serving through every deploy.

## Risks (must be addressed in PLAN.md)

### R1: ETag cache strategy

Track 1 hits `GET /repos/...`, Track 2 hits code search + `GET /repos/...` + `GET /trees/...` + raw content. They overlap on repo metadata.

**Decision:** **shared ETag cache.** Both tracks read/write the same `data/etag-cache.json`. Repo metadata fetches benefit from cross-track caching (Track 1's daily refresh keeps repo etags hot for Track 2 weekly's enumeration).

### R2: Race condition between Track 1 and Track 2

Both tracks write to `data/skills.json`. If they run concurrently (or Track 2 overwrites Track 1's fresh stars), we lose the daily refresh.

**Decision:** **strict sequential ordering** in `daily-scrape.yml`:
1. Track 1 first → updates skills.json star fields
2. Track 2 incremental second → appends new entries to skills-raw.json
3. Filter reads skills-raw.json + EXISTING skills.json → merges
4. Filter must preserve Track 1's freshly-pulled fields when rebuilding skills.json

This means **`scripts/filter.js` needs a small change**: when it sees a skill in skills-raw.json that already exists in the current skills.json, prefer the current `repo_stars`/`repo_forks`/`repo_open_issues`/`repo_pushed_at`/`repo_updated_at`/`repo_archived` values (from Track 1) over the values in skills-raw.json.

### R3: Merge semantics in filter

Concrete change to `scripts/filter.js`:

```js
// In the per-skill loop, after parsing skills-raw.json record:
const existing = currentSkillsBySlug.get(skill.slug);
if (existing) {
  // Track 1 may have updated these — preserve from existing skills.json
  skill.repo_stars = existing.repo_stars;
  skill.repo_forks = existing.repo_forks;
  skill.repo_open_issues = existing.repo_open_issues;
  skill.repo_pushed_at = existing.repo_pushed_at;
  skill.repo_updated_at = existing.repo_updated_at;
  skill.repo_archived = existing.repo_archived;
}
```

Plus: re-score the skill with the fresh stars/recency. (Quality score depends on stars and recency; updating those without re-scoring would leave stale scores.)

### R4: Star history backfill stays separate

`data/star-history.json` (45 MB, 305 Featured) is a one-shot from `scripts/backfill-star-history.js`. Track 1 does NOT replace it.

**Decision:** Backfill remains a one-shot. New Featured skills (post-3.0.0) get backfilled lazily — either by a re-run of the backfill script or by detecting new entries and queueing them. **Out of 3.0.0 scope.** Rolls into Phase 3.x ops or Phase 4+.

### R5: First post-deploy run

When 3.0.0 ships:
- The daily cron already has the bootstrap cache from 2026-04-18 (etag-cache-bootstrap-1, 499 MB)
- First Track 1 run: warm via that cache. <5 min.
- First Track 2 incremental: `pushed:>3d` filter, finds maybe 100-300 new skills. <30 min.
- Total: ~35 min. Easily fits in 6h.
- Subsequent runs: warmer. ~10 min total.

The first weekly Sunday Track 2 full run will be cold-ish (parts of the corpus haven't been touched in 5+ days). That's fine — it has its own 6h budget and the convergence model.
